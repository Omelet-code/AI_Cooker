# F3-D 技术说明：采购状态与金额展示

本文按当前前端实现讲解采购确认、商品匹配和报价回看的数据流。后端事实由 5b09 的 T16/T17 接口提供；本切片没有实现后端或真实商家连接。

## 代码地图

- `frontend/src/modules/shopping/types.ts`：预览、逐行确认、清单、匹配、成本和未知操作的前端类型。金额、用量及数据库大整数 ID 使用字符串。
- `validation.ts`：把 HTTP `unknown` 数据逐字段解析并校验 schemaVersion、状态、归属、普通十进制格式、单位和 null。TypeScript 类型声明本身不能证明服务器实际 JSON 正确。
- `api.ts`：只调用真实 `/api` 相对路径；共享 apiClient 自动加 `/api` 并处理 Cookie、CSRF。采购 POST 沿用共享默认短超时，不改全局请求配置。
- `state.ts`、`store.ts`：管理来源、当前清单/报价、确认草稿、独立读取/写入代次、停止本地等待及未知结果；Pinia Store 注册退出清理。
- `navigation.ts`：成功清单导航仍要求服务器来源与当前选择完全相符；两个未知操作入口共用冻结原始路由构造器。
- `ShoppingLines.vue`：逐行选择已有/需买；仅待确认用量行开放十进制文本及允许单位。
- `ShoppingView.vue`：页面入口、预览确认、清单回看和明确触发的模拟商品匹配。

## 请求顺序与快照

1. 从已选套餐入口进入 `/shopping/new`，携带会话 ID、餐单 ID、期望版本和方案 ID。参数只用来请求预览，不代表权威材料。
2. GET 服务器 shopping-preview。页面核对服务器回显来源；用户必须为每一行（可选行也包括）显式选择 `HAVE_ENOUGH` 或 `NEED_BUY`。
3. POST `/shopping-lists` 保存采购需求。每行发送 lineKey、可用性、可空数量和可空单位；整体带 requestId、版本、方案和 sourceFingerprint。无参考量的空数量按未知保存，不当成 0。
4. 清单创建成功后跳 `/shopping/:listId`。页面 GET 清单及 `/product-matches/latest`；null 代表没有已存报价，读取过程不发写请求。
5. 用户选择六位城市码并点匹配后，才 POST `/product-matches`。服务器商品、价格、目录版本、采购组及金额作为不可变报价快照返回。页面给清单 `/shopping/:listId` 和当前保存报价 `/shopping/:listId?matchId=:matchId` 固定链接；复制/收藏后可指定回看旧报价，否则读取 latest。

后端没有全量清单索引接口，所以 `/shopping` 只接受已知清单编号或来源入口；不能把浏览器临时数组称为持久历史。

## 超时、幂等与上下文隔离

每次写操作在发送前冻结原请求并登记 owner、原路径、requestId、清单/来源上下文和原始路由（报价操作包括 matchId；建单来源 query 只放四个来源标识）。双击被 busy 和 pending 状态挡住。网络错误、超时、主动停止本地等待、离开导致取消等待、5xx 或无法解析的 2xx 都意味着结果未知：保留原操作，提供“回到原上下文”和用户确认后的原键核对。停止本地等待会 abort 客户端请求并让该写入代次失效，但不声称服务器已停止。重放复用同一路径和同一 payload；城市或确认内容变化不会被偷偷拼进旧键。两个返回入口使用同一原始路由，不会丢失 matchId。

读取和写入分别有独立 generation。同上下文再次读取会让前一次读取失效；清单 GET 与第二段报价 GET 都先存局部结果，只在 owner、页面上下文、读取代次仍匹配时发布。catch/finally 也使用同一条件，因此旧取消不会清掉新读取的 busy，旧错误不会污染新页。切清单、切报价、换来源会使迟到响应失效；账号代次能识别 A→B→A，避免只比账号字符串造成旧响应误入新页面。旧写在同账号离开原上下文后仍保留未知原键，但响应不再改新页状态或导航。退出时共享会话清理器清掉采购私有内存。没有把请求正文、凭证或 token 存进 Web Storage。

AbortSignal 与发布代次解决不同问题：AbortSignal 请求底层停止等待/传输，服务端即使已收到请求也可能继续处理；generation 在应用层拒绝迟到的成功、失败和 finally，保证它不能发布到新上下文。即使网络栈忽略中止或响应已经排队，发布检查仍有效；即使有 generation，若不 abort 仍会白等与占用资源。二者互补，不能互相替代。

## 金额与单位

数量、价格由服务器以普通十进制字符串给出。前端不使用 `Number`/`parseFloat` 算权威价格，也不把指数形式或数字类型静默转字符串。用户输入仅限大于 0、最多 8 位小数的文本。

G/KG 仅互换，ML/L 仅互换；COUNT/CUSTOM 只允许原单位。原单位未知时，用户可显式选 G/KG/ML/L。对用户标记“已有足量”的行，不伪造菜谱消耗量为零。

页面独立列出需求估价、Mock 折算消耗成本、整包采购支出、已知小计与未知数、预算状态。每个采购组显示合并后的数量、包数和整包支出。组金额用于解释服务端支出构成，不再与摘要中的总支出相加。金额 null 显示“未知”；`0.00` 显示零。预算状态为 UNKNOWN 时不承诺满足预算；超预算时保留清单并明确提示。

## Mock、可选项和链接

模拟报价必须醒目标出 Provider/realData 状态、目录版本和城市。没有匹配商品、缺货、单位不兼容、数量待确认和报价未知按后端行状态展示。没有购买 URL 时按钮/链接不可用；前端不拼造平台地址，也不代表商品真实有货、可下单或已支付。

原始材料文本使用普通 Vue 插值，不使用 `v-html`。商品快照若 URL 不是 HTTP(S)，页面不生成可点击链接。

## 新技术学习点

- 运行时 schema 校验：JSON 来自网络，应从 `unknown` 开始检查。可学习 Zod 等 schema 工具的优劣，但本项目此任务没有新增依赖。
- AbortController 与请求代次：AbortSignal 尽力结束客户端等待；owner/context/read/write generation 在结果发布前复核，阻止成功、catch 和 finally 污染新上下文。代次不停止网络，AbortSignal 也不证明服务端事务回滚。
- 幂等键与未知结果：客户端超时并不说明服务器失败，安全重试必须使用原 key 与原输入。
- Vue Router `watch` 与 Pinia 状态：路由参数变化会触发读取；成功状态先发布再改路由，避免 watch 将成功请求误认为用户中途离开。
- 十进制定点金额：数据库 numeric 与 Java BigDecimal 通过字符串往返，避免二进制浮点误差。

## 面试问答

1. 为什么金额不用 `Number`？IEEE-754 二进制浮点不能精确表示很多十进制小数；展示和回传原字符串可避免隐式精度损失。
2. 网络超时是否代表后端没有写入？不是。服务端可能已提交，只是响应没有到达。
3. 为什么未知重试要复用 requestId？服务器以同一 key 识别同一逻辑操作；换 key 可能创建重复清单或新报价。
4. 为什么选择城市不能直接改报价结果？商品与价格属于服务端目录事实，客户端只提交允许的城市码和请求编号。
5. AbortSignal 和代次号分别解决什么问题？AbortSignal 停止客户端等待；代次号在发布前验证请求仍属于当前账号、上下文及同上下文最新一轮，拒绝旧成功/失败/finally。两者都不能证明服务端已停止处理。
6. `latest` 返回 null 是什么？当前清单还没有保存过匹配快照，是合法状态，不是网络错误。
7. 为什么整包采购支出不能加行级商品支出？包组已汇总购买单位；再次累加各行对应包价会重复计算同一包装。
8. 页面测试通过是否意味着真实商品接口已验收？不是。替身验证前端协议和状态行为，不验证部署、数据库或商家数据质量。
