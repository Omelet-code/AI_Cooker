## 1. 任务目标与边界

目标是让已导入的结构化菜谱具备语义检索能力：按 `recipe_id` 回查 `recipe`、`recipe_ingredient`、`recipe_step`、`recipe_tool`，拼接为可独立嵌入的文本块，调用阿里云百炼 `text-embedding-v4` 生成 1024 维向量，写入 `recipe_search_document`，并记录模型、维度、模板版本与内容哈希，使重复执行可以跳过未变化的块。

本次明确未做：词法召回与向量召回的 SQL、RRF 融合、面向用户的检索 API、检索评测集、用户自定义菜谱上传、DeepSeek 调用。

## 3. 关键实现与设计选择

**跨模块契约。** `retrieval` 只依赖 `recipe` 的 `RecipeIndexProjectionService` 与 `RecipeIndexProjection` DTO。事实回查集中在 `recipe` 模块，检索侧不接触菜谱 Mapper 或 Entity，符合模块化单体的依赖方向要求。

**chunk 设计。** 每道菜谱生成 `overview`、`ingredients`、`tools` 各一块以及一到多个 `steps` 块。`steps` 按连续 3～5 个完整步骤切分，另设 4000 字符上限；单个超长步骤整体保留，不做字符截断，避免烹饪动作失真。所有块都以“菜名 + 分类”开头，使孤立步骤命中后仍能还原所属菜谱。

**只依赖 `EmbeddingModel`。** 百炼没有与 Spring Boot 4 / Spring AI 2 兼容的官方 starter，因此项目内实现适配器，业务代码只注入 `EmbeddingModel`。未引入 `VectorStore`、`ChatClient` 或 TextSplitter，切分规则由结构化字段决定，以保证可解释。入库请求固定 `text_type=document`、`dimension=1024`、`output_type=dense`，每批最多 10 条文本。`dimensions()` 直接返回配置值，避免探测维度产生额外付费调用。

**版本化与幂等。** 复用已有向量要求四个条件同时满足：内容哈希、模板版本、模型、维度，且状态为 `READY`。因此修改拼接模板只需递增 `document-template-version` 即可触发重建。写入使用 `ON CONFLICT (recipe_id, chunk_type, chunk_no)` 的幂等更新。

**失败隔离。** 每批调用独立捕获异常，失败批次保留文本与哈希、清空向量、状态置 `FAILED`，其余批次与菜谱继续执行；过期块只有在整道菜谱本次全部成功时才删除，避免一次网络抖动导致可检索文本缩减。`failure_message` 只写入脱敏分类，例如“百炼服务请求失败，HTTP 状态码：401”，不写第三方异常原文、请求正文或 Key。

**向量写入方式。** 以 pgvector 文本字面量传入并 `CAST(... AS vector)`，绕开 ORM 对 pgvector 类型支持不完整的问题；`tsv` 由数据库生成列自动维护。

**真实运行中修正的两个问题。** 其一，`RestClient` 直接以 `JsonNode` 为响应类型时，因百炼网关的响应媒体类型不稳定而抛出 `HttpMessageConversionException`，改为按 `String` 接收后用 Jackson 解析；其二，该轻量依赖组合不会自动注册 `ObjectMapper` Bean，适配器改为自建实例。两处修改都限制在适配器内部。

**迁移文件的处理。** 原计划给 `V2` 补行内 SQL 注释，实测触发 `Migration checksum mismatch for migration version 2`，因为 Flyway 校验和包含注释内容。已将 `V2` 恢复为已应用时的内容，列语义改由文档承载；后续新增迁移可正常写注释，但不应回改已应用文件。

## 6. 风险与后续建议

**词法通道的输入尚未验证。** 块内容在入库前会把所有空白折叠为单行，`ts_rank` 的分词输入因此是单行文本；同时 `steps` 块带有“步骤N：”前缀，`overview` 块包含分类名。这些设计对关键词命中是帮忙还是干扰，需要在 T5 用真实查询抽样确认。建议 T5 的第一个动作是先跑几条手工 SQL 观察 `tsvector` 与 `ts_rank` 的实际取值，再定召回与排序参数。

**真实调用无法进入自动化测试。** 当前对百炼的验证依赖手工触发任务加真实 Key，CI 中无法覆盖。建议 T5 引入 Mock Server 或适配器级测试，把外部依赖挡在自动化测试之外，符合“不得让常规自动化测试依赖真实收费 API”的约束。

**失败块没有自动重试。** 失败块保持 `FAILED` 且可被下次任务覆盖，需要人工重跑索引命令；因为任务幂等，重跑是安全的。

**步骤块数量对排序的影响。** 长菜谱会产生更多 `steps` 块，ADR-004 已规定先按 `recipe_id` 取最佳 chunk 再做 RRF，T5 实现时必须遵守，否则长菜谱会被系统性放大。

**建议的派发方式。** T5 与 T6 由新会话承接更合适：T5 的验证方式是检索质量与 SQL 行为，与 T4 的实现思路不同，独立会话更容易质疑本切片的设计假设；T6 作为评测与验收，也应与实现分离。
