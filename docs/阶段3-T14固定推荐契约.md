# T14 固定 RAG 推荐契约

日期：2026-10-02。版本：`s3-recommendation-v1`。用户要求“检验并推进”，T13经独立复审签收后，本轮仅冻结并交原后端实现T14。此契约不是已实现、部署或收费调用证据。F3-B另行派发；T15工具循环/SSE与3B采购不在本次范围。

## 1. 目标、路径与职责

固定流程：可信身份与会话校验 → 注册/取得一次开始资格 → 有限历史与上一有效约束 → 模型JSON理解 → Java校验/合并 → 生产 `RecipeSearchService.search` → 当前用户 `RecipeReadService.detail` → 模型JSON选择及理由码 → 候选核验/服务器渲染 → 短事务保存助手与快照/终态。

- `agent`负责发送接口、编排、模型DTO、资源计数与候选选择；Controller只调用项目Service。
- `policy`提供确定性约束合并、健康提示、允许的理由码/固定文本与输出检查；不依赖持久层。
- `conversation`负责有限历史、结果快照和原有短事务状态机；通过本模块Service向agent提供DTO，不反向依赖agent类型、Mapper或实现。
- `retrieval`与`recipe`只用现有公共Service，注入可信当前userId；不修改T5排序/SQL/向量版本，不绕过检索生产入口或跨模块Mapper。

T14采用同步HTTP，不引入线程池/后台任务。理由：先让请求流、幂等和事务可直接审查；T15再冻结异步/SSE。不能同步执行完却宣称POST返回的是异步接纳202。

## 2. 新增HTTP与既有接口兼容

复用Cookie/CSRF、ApiResponse、字符串ID、UTC时间、no-store；客户端不传userId、模型地址、Key、模型名或任意工具。

### POST `/api/conversations/{id}/turns`

输入仅 `{ requestId: string, content: string }`，UUID规范格式、正文非空白且最多4000 Unicode码点，精确保留原文。沿用T13同键/原文/哈希与单会话单活动轮次规则。

响应 `RecommendationTurnView { turn: TurnView, result: RecommendationResult | null }`：

- 新建且同步处理结束：201，包括业务执行FAILED（原因在turn.error，不伪装请求校验错误）。
- 同键同内容、既有终态：200，仅回读，不重调模型/检索。
- 同键既有PENDING/RUNNING：202，仅回读，Location指向下方结果读取接口；不取得第二次执行资格。并发首次请求仍由登记created与start资格保证执行一次。
- 同键异内容/不同键在途409；校验400；越权/不存在404；认证/CSRF保持既有规范。数据库暂不可用等基础设施失败可按既有安全500处理，不能假称成功落库。
- `cooker.agent.execution-enabled`默认false。关闭时对合法当前用户会话返回503 `AGENT_EXECUTION_DISABLED`，不登记轮次、不解密Key/调用供应商。测试显式开启并注入模型/向量替身；真实启用/收费联调仍需独立批准，不修改开发运行环境。

### GET `/api/conversations/{id}/turns/{turnId}/recommendation`

200返回同一 `RecommendationTurnView`。按当前用户及会话/轮次归属读取持久化快照，不调用模型、检索、解密、恢复或重新计算。未归属404。PENDING/RUNNING/FAILED或T13旧轮次无推荐快照时result=null。

T13原GET turn的TurnView和消息接口不改变；新读取接口避免破坏已冻结字段。无POST messages别名，不发布events/stream。GET会话历史正文继续由chat_message读取；结构化卡片通过推荐结果接口读取。

## 3. 推荐结果与事实边界

```text
RecommendationResult {
  schemaVersion: 1,
  outcome: "RECOMMENDED" | "NO_MATCH" | "CLARIFICATION" | "UNSUPPORTED",
  answer: string,
  constraints: RecommendationConstraints,
  recipes: RecipeRecommendation[],
  noticeCodes: string[],
  metrics: ExecutionMetrics
}
RecommendationConstraints {
  query: string,
  maxCookingMinutes: number | null,
  availableToolNames: string[] | null,
  excludedIngredientNames: string[],
  availableIngredientNames: string[],
  budgetYuan: string | null
}
RecipeRecommendation {
  recipeId: string, name: string, summary: string | null,
  estimatedMinutes: number | null, reasonCodes: string[]
}
ExecutionMetrics {
  modelGatewayAttempts: number, retrievalCalls: number,
  queryEmbeddingRequests: number | null, elapsedMs: number,
  modelUsages: [{ attempt: number, promptTokens: number | null,
                 completionTokens: number | null, totalTokens: number | null }]
}
```

最多5道检索候选，最终1～3道；非RECOMMENDED时recipes=[]。answer为服务器依据枚举、已验证字段和固定中文模板生成的纯文本，不直接展示模型任意自由文本、Markdown/HTML、医疗或购买链接。助手正文同一份answer入库，最多8000码点。未知字段为null，不填0。模型可以选择顺序/理由码，但不可填菜名、材料、做法、价格等事实；详情始终来自RecipeReadService且提交前再次验证可见性。

允许理由码：`RETRIEVAL_MATCH`（仅表示命中，不保证清淡等偏好已结构化证实）、`TIME_CONFIRMED`（数据库时间非空且满足上限）、`TOOLS_COMPATIBLE`（按已登记必需厨具与用户集合检查）、`AVAILABLE_INGREDIENT_MATCH`（明确名称匹配，不能声称食材齐全/足量）。只允许本候选确实满足的码；模型越界ID、重复ID、错误码/不成立理由、空选择或不合法JSON → MODEL_INVALID_RESPONSE，不能放过或额外收费修复。最多选择3项。

noticeCodes至少覆盖：`BUDGET_NOT_VERIFIED`、`AVAILABLE_INGREDIENTS_NOT_INVENTORY`、`PREFERENCE_NOT_GUARANTEED`、`GENERAL_DIET_ONLY`。预算不为空必有预算未验证提示，已有食材不为空必须说明未维护/抵扣库存；匹配名称不是过敏安全认证，也不宣称疾病适宜或可治疗。没有候选不得自动放宽约束，NO_MATCH固定提示用户主动修改条件。CLARIFICATION/UNSUPPORTED用固定中文文案，不直接采用模型澄清文本。

## 4. 模型理解与约束合并

调用T12 ModelGateway的JSON模式，明确要求输出JSON。结构化输入仅作为数据，不提升为system指令；外部菜谱/用户文本均不可信。模型输出严格DTO解析、未知字段/尾随JSON拒绝、Bean Validation及业务校验；不能仅凭JSON语法合法就调用Service。

第一请求的输出契约：intent为RECOMMEND/CLARIFY/UNSUPPORTED，query为合并后的语义查询，changes包含下列五个字段的 `{action: KEEP|SET|CLEAR, value, evidence}`：maxCookingMinutes、availableToolNames、excludedIngredientNames、availableIngredientNames、budgetYuan。所有字段及action明确存在；KEEP/CLEAR的value=null，SET需符合类型。SET/CLEAR的evidence为当前原文中精确存在的非空片段（最长200码点）；KEEP的evidence=null。证据片段有助于拒绝凭空修改，但不是语义抽取正确性的数学保证，需固定样例检验。

- KEEP保留上一有效值；SET整体覆盖该字段，不默认为追加；CLEAR恢复默认值。时间默认null；厨具默认null，**SET []表示明确没有任何厨具，CLEAR/null表示未知、不设厨具过滤**；两个食材列表默认[]；预算默认null。
- 时间SET为整数1～1440；预算SET为十进制金额字符串0～10000、最多两位小数，用BigDecimal校验；数组最多20项，各名称非空且最多80码点，规范去空白/去重，不自动推断足量/单位。
- query非空，最多512码点；输入当前消息4000码点不能悄悄被截断替换。intent为CLARIFY/UNSUPPORTED时query可保留上一值或安全默认“家常菜”，不执行检索；clarificationCodes仅固定枚举TIME_AMBIGUOUS/TOOLS_AMBIGUOUS/EXCLUSION_AMBIGUOUS/REQUEST_AMBIGUOUS，最多4项，按码生成固定问题。模糊不确定的硬条件必须先澄清，不能假装已识别。
- 当原文说“这次20分钟/时间不限/不要鸡蛋/不再限制厨具”，以当前SET/CLEAR覆盖旧约束；没有提及的字段KEEP。失败轮次不能覆盖上一有效约束；澄清/不支持轮次也不得提交尚未确认的变更，以先前有效约束作为result.constraints。

上一有效约束来自当前用户/当前会话最新RECOMMENDED或NO_MATCH成功快照，不用无限历史重新猜，不跨会话。T13旧成功记录没有快照时用默认约束。

映射T5：limit=5、categoryCodes空、viewerUserId=可信当前用户；maxCookingMinutes来自合并值，有时间上限时includeUnknownCookingTime=false；availableToolNames保留null与[]差异；排除食材走既有名称/别名过滤。已有食材与预算不传虚构T5参数，不改RRF；清淡/软/少油等只作为语义偏好，不称已严格过滤。候选经详情Service读取后再校验可证实的硬条件，未知时间不能通过已声明时间上限。

第二请求输出仅 `{ selections: [{ recipeId: string, reasonCodes: string[] }] }`；候选数据给当前ID/真实精简字段及服务器预先计算的允许理由码，不给原始Markdown/任意地址/Key。严格校验上述字段后渲染，不接受任意回答正文。

## 5. 有限历史、资源与失败

- conversation新增只读Service能力获取最近最多6个完整SUCCEEDED用户/助手对，按序号恢复顺序，限定当前用户/会话、排除本轮/失败/未完成/未来轮次。从SQL有界取，不遍历全量历史。
- 每次网关沿用T12最多16条消息/20000码点（包含system、当前输入、结构化约束、候选）；逐对移除最旧历史，不切断消息对或篡改当前输入。精简候选字段有长度上限，不把8000字菜谱全文拼进Prompt；必要信息仍超限则RESOURCE_LIMIT，不静默丢弃硬条件。
- 最多2次网关调用，最多1次生产检索，即最多1次query Embedding请求；无结果/澄清/不支持在第一请求后结束，无第二请求。失败不额外修复/重试。GET、同键回读和非法/越权输入的调用数为0。
- metrics里的modelGatewayAttempts是网关方法调用次数，不等于供应商实际HTTP/计费次数（凭证预检也可能失败）；retrievalCalls是Service次数。T5未公开实发Embedding统计，不为测量而改T5，queryEmbeddingRequests=null，测试替身计数另作证据；不填假0。每次尝试usage未知保持null，不能伪称免费或实付金额。
- 同步整轮90秒为**阶段边界软预算**：用单调时钟在每个外部阶段前后检查，耗尽不启动下一阶段、不写成功。T12当前连接5秒/读30秒，T5查询连接3秒/读5秒；这些不是硬总耗时保证。T13的120秒DB截止与条件成功写仍保留。不得用Future取消包装未终止网络后声称硬取消，也不新增异步线程或承诺90秒墙钟必结束；传输总deadline/全局并发控制留T15或专项演进。用可控时钟测试超预算后零新增调用与迟到不成功，不用长sleep。
- agent编排方法本身不加@Transactional；ModelGateway/检索调用时无外层事务。注册/开始/结果成功或失败分开短事务，父会话→轮次→消息锁顺序保持。
- 模型错误映射现有TurnError允许码；JSON/选择/理由非法用MODEL_INVALID_RESPONSE，检索失败用RETRIEVAL_FAILED，软预算用RESOURCE_LIMIT，未知安全错误用EXECUTION_FAILED；异常原文/Key/Prompt不落库或回传。T5允许的词法降级保留，不冒充必然走了向量。
- 只由新登记created=true并取得一次start资格的路径执行。旧PENDING即使未过期也不因重放再次执行。完成/失败条件冲突只回读权威状态，不覆盖已有终态、不自动重试外部调用。落库失败不可凭内存答案返回SUCCEEDED；数据库不可用时报告安全错误，可能遗留RUNNING，后续按T13期限恢复。

## 6. 数据快照：V9与事务归属

只新增 `V9__create_conversation_recommendation.sql`，不修改V1～V8。新增conversation模块表 `conversation_recommendation`：turn_id BIGINT主键、conversation_id/user_id BIGINT、schema_version整数=1、constraints JSONB、result JSONB、created_at TIMESTAMPTZ；通过(turn_id,conversation_id,user_id)复合外键关联conversation_turn，CASCADE。JSONB两列必须为非空object；归属/版本保留关系列。失败/未完成无快照，成功结果一轮唯一。

JSONB只存上述校验后的业务对象与必要usage，最大序列化UTF-8合计64KiB，超限RESOURCE_LIMIT；不得保存原始模型响应、系统Prompt、供应商异常、工具正文、reasoning或Key。用户输入/历史仍在chat_message。snapshot中的recipeId是历史引用：不能外键强依赖未来可删除菜谱，也不能据此授予访问权限；访问详情重新做可见性校验。

conversation新增专属Service DTO/方法（类名自定）保存RecommendationSnapshot及读取。成功写入必须在同一个本地事务、同一父行锁下完成：唯一ASSISTANT、快照、条件RUNNING→SUCCEEDED、会话时间；任一步失败全部回滚。复用原succeed能力时不能在另一个独立事务先完成消息再保存快照；跨模块agent只调用Service，不能访问conversation Mapper。T13内部普通succeed保留原契约、不强制所有旧测试都生成推荐快照。既有GET turn字段保持不变。

V9升级测试覆盖V8用户/会话/消息保留，以及原T13外键/并发/恢复回归。旧测试中硬编码迁移总数可做最小兼容调整并逐文件说明；原T13复合外键测试的23503/对照断言不可删弱。

## 7. 验收矩阵

真实HTTP/认证/CSRF/Service/Mapper/临时PG；模型替身、QueryEmbeddingService替身，只替换外部依赖，至少一组走真实RecipeSearchService.search和真实详情，不以Mock整个检索服务代替全部端到端证据：

1. RECOMMENDED有效ID/固定事实/快照/消息一致，回读跨应用上下文仍一致；V8→V9保留旧数据。
2. 同键同内容并发仅执行一轮；终态/在途回读零外部调用，异内容409/异键忙；拒绝后无多余消息或快照。
3. A/B全部发送/推荐读取/历史隔离；私有菜谱、非本轮ID、幻觉/重复ID不可返回，模型输入无userId/Key/任意地址。
4. KEEP/SET/CLEAR、厨具null/[]、上一约束来源、失败/澄清不覆盖、时间未知被排除；无候选不自动放宽。
5. 非法JSON/unknown字段/超限/无证据/错误理由、超调用数拒绝；无结果/澄清/不支持最多1次模型、零或1次检索；有限历史去最旧完整对。
6. 预算/已有食材未知不夸大；喉咙等输入只有一般偏好及固定健康声明；恶意菜谱/用户Prompt注入不能新增工具或输出治疗承诺/未知链接。
7. 在模型和检索替身中断言没有外层事务；快照/助手后置写失败完整回滚；模型失败留下FAILED且无ASSISTANT/快照；迟到成功不能覆盖恢复终态。
8. gate默认关闭、零调用/零落库；每步软预算拒绝后续调用；日志/异常不泄露正文/Key，usage缺失为null。

完整JDK21离线测试、打包、diff及新增文件空白检查；报告实际数字/跳过。没有开发库或真实收费验收，不挪用T6质量/时延数据。每T教学要求继续适用：真实类方法/代码流、两种设计对比、新知识清单、至少8道面试追问、5自检题和2练习。
