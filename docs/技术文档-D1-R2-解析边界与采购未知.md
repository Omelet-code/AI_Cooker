# D1-R2技术文档：解析边界与采购未知

日期：2026-10-08。实际源码5b09；最终数据库 `cooker_rebuild_d1r2_20261007`。实际统计、绑定和执行记录见[工作报告](工作报告-D1-R2-解析重导与采购绑定.md)。

## 1. 数据处理顺序为什么重要

本轮修复的是确定性Markdown解析的边界。原代码先在整行找“数值+单位”，再把数量前文本当名称，这对普通“盐10g”有效，却可能把米饭说明中的“第一个指节”取成1个，或者把“盐量=兔肉斤数*”当材料名称。

v3先辨别器具、产出/操作说明、水位说明、依赖公式，再进入原数量标准化规则。顺序不同，事实含义不同：说明中的数字不应进入可靠材料量，公式系数也不等于本餐需求。

| 输入形式 | v3处理 | 保留信息 |
| --- | --- | --- |
| 圆碟子/蒸架带尺寸 | 从食材排除，材料工具词典不改变T5厨具词典 | 整份原Markdown |
| 蒸锅用水1000ml、米100g、锅巴20g | 普通材料正例保留 | 名称、原行、数量单位 |
| 鸡蛋的用量为1个 | 分离“的用量为”，既有标准量路径 | 鸡蛋1 COUNT及原句 |
| 油5mL每个鸡蛋 | 每个对象的比例依赖不求总量 | 油、null数量和原句 |
| 每份原料可制作7.5kg底料 | 整批产出不是食材，回退可靠必备列表 | 原文、产出警告、真实必备材料 |
| 北方大米，食指/指节水位说明 | 取逗号前明确材料名，不扫描说明数量 | 北方大米、null量/单位、原行 |
| 盐量=兔肉斤数*2克 | 提取左侧单材料名，不求值 | 盐、null量/单位、完整公式 |
| 小葱/大葱/洋葱总量=… | 保留组合整体，不分配比例 | 组合名、null、完整公式 |
| 小龙虾=1kg | 右侧纯数字+单位，走原确定规则 | 1000 G，只换算一次 |

没有LLM解析、网络同步、修改HowToCook快照或补猜事实。人数规则仍为约量取给定值、范围取下限；冲突、无人数、份数/尺寸/整批产量不换算人数。多规格表格和组合配方不选任意列。

## 2. 三层数据和版本边界

`recipe_source_document`保存完整原文、来源版本和诊断；recipe及材料/食材/步骤表保存确定或明确未知的结构化事实；recipe_search_document是后续可重建检索投影。

规则版本从v2变为 `d1-r2-parser-v3`，sourceVersion仍原真实 `1.6.0-a0b14bd`。规则版本描述解析实现，来源版本描述上游快照，不能混用。旧库的同源SUCCESS文档会跳过，因此不能换假版本绕过去重。

本轮使用准确空库真实导入：V1～V15、372文档/菜谱、3102材料、976食材；第二次372跳过，只有批次新增。旧cooker和首版重建库保留，不drop/truncate覆盖。

5份目标数据库原文与只读源文件逐字符一致；rawLine保留原公式、说明和数量。正常content_hash仍是业务标识，但本轮没有追加原文件或全库哈希复审。原文留存不等于所有字段都能被可靠结构化。

扩展已安装不等于检索就绪：当前投影0行，也没有向量。D1-C需复审后另卡启动，使用真实投影Service/Builder和document Embedding，不复制旧向量、用替身伪READY或附带query收费评测。

## 3. 事务、幂等和独立入口

RecipeRebuildTool只允许最终库、5433和root；显式URL与专用进程环境一致，连接后再核对真实catalog/URL/角色。原旧库与首版重建库均被拒绝，非法URL错误使用固定中文脱敏。

最小上下文复用原导入Service和MyBatis-Plus Mapper，DataSourceTransactionManager与SpringManagedTransactionFactory使用同一DataSource。单文件Service真实事务代理必须存在。临时PG测试后置触发SQL失败，证明失败文件来源/食材/菜谱回滚而其他文件提交；不是仅检查@Transactional注解。

批次不是整库大事务。每文件事务失败可隔离，批次记录成功/失败路径；入口失败不能被理解为整个新库已回滚。创建后失败保留现场，不自动删库重来或改sourceVersion。

同源SUCCESS跳过不覆写事实和人工审定。有限审定后再重跑，12个REVIEWED状态仍保留，材料/食材/步骤等数量不变。新增一条导入批次是记录执行，不破坏业务幂等。

一次性导入进程不会改变IDE、前后端或其他进程连接。凭证只进入导入子进程，原User/System变量和主应用默认配置不变；没有装配模型或启动8080/5173服务。

## 4. 采购未知必须沿原事实解释

三层纯计算链路为：

`MealMaterialCalculator → ShoppingDemandCalculator → ProductMatchCalculator`

本轮仅修改中文reason，数量、单位、状态枚举和HTTP字段不变。材料层区分原人数、量/单位、公式或水位、标准食材待审；缺口和商品QUANTITY_PENDING追加提示时先保留原reason，避免只剩“用量待确认”，更不能说“食材不存在”。

| 情况 | 来源依据/状态 | 处理 |
| --- | --- | --- |
| 原菜谱人数未知 | scale UNKNOWN，原份数未知或无效 | 参考量null，不拿目标人数补原基准 |
| 量/单位未知或冲突 | scale UNKNOWN或ORIGINAL_ONLY | 保留原文/区间，不默认0或1、不取中点 |
| 公式/水位依赖 | null事实及原因 | 不求公式、不把指节/比例数字取成总量 |
| 标准食材未审定 | 材料/来源行中文reason及Pending | 保留来源，不当REVIEWED合并；有ID不代表已审定 |
| 目录无商品/城市不支持 | NO_PRODUCT及Provider原因 | 保留未匹配，不猜名称或替代食材 |
| 单位维度不支持 | UNIT_UNSUPPORTED | g/ml/count不互换，不猜密度 |
| 缺规格/价 | QUOTE_UNKNOWN | 总额保持未知，不当免费商品 |

用户确认是独立事实：原份数未知但明确输入10g，允许保存确认量并进入匹配；不能因此把原菜谱servings改成3。原始行、确认行、汇总和报价分别保留，不改历史材料或模型输出。

所有未确认的参考量仍需人工确认；待采购数量null不会进入Provider。HAVE_ENOUGH表示用户已确认足量，缺口可为0，但不是证明原消耗量为0。没有读持久库存或扣库存。

## 5. 数量和成本规则没有改变

kg/L在解析入库时已转G/ML，之后用标准unitCode计算，不能再从rawLine看到kg/L乘1000。仅明确同维转换支持G/KG、ML/L；COUNT及CUSTOM不能推质量或体积。

同标准ID且语义相容的已知缺口才汇总。商品阶段先按相同商品/城市/单位合需求，再对包装数上取整；成本为用量比例折算，purchaseOutlay为整包支出，两者不可混为同一个“价格”。

本轮最终目录测试：两条optional不同的10g鲜虾分别保留来源，商品阶段合为20g；300g/18元的包买1包，消耗成本1.20元、整包支出18元。预算1元判OVER_BUDGET且保留清单，不自动换菜。未知项则总额null，展示已知小计且预算UNKNOWN；null不是0。

生抽原文3g与目录500ml仍不可匹配体积商品；芹菜3根与500g包也不能换算。语义审定12个ID不授权密度、同义词或单位猜测。

## 6. 有限语义审定和固定目录

审定依据来自任务卡固定12种语义、原商品及最终库相关菜谱材料。采用明确最终ID，分别核对规范名和sourceKey/rawLine；标准ID表不是自动名称匹配规则。

Review-MockBindings-D1R2.sql只在最终库执行，校验12个ID/精确规范名原状态；事务内UPDATE 12，另外964食材仍UNREVIEWED。重复执行拒绝，没有建立别名、改数量或全库REVIEWED。临时PG在动态测试端口使用同名隔离数据库模拟脚本，另留一条未审定行证明没有扩大全库；与宿主5433最终库严格区分。

新目录保留旧商品所有量价/包装/城市/productId，只有ingredientId与catalogVersion变化。鲜虾138不等于泛称虾，西红柿614没有合并成其他别名；productId里旧数字只是字符串标识，不能当新数据库主键。

Provider仍只接收服务端明确ingredientId、单位、数量和城市。无匹配ID的同名材料不会得到商品，目录默认未知不会伪造价；realData=false、provider=MOCK、purchaseUrl=null。配置已准备但未被0f47运行服务加载，测试成功不等于生产目录已激活。

## 8. PostgreSQL与MySQL对照

| 本项目实现 | MySQL迁移时的对应考虑 |
| --- | --- |
| BIGINT identity生成主键 | 可采用AUTO_INCREMENT，但跨库ID同样不稳定 |
| numeric与Java BigDecimal | DECIMAL也应保留精度和null，不使用浮点表达金额 |
| JSONB存原诊断/快照 | JSON也需保留关系列和用户边界；SQL函数不可直接照搬 |
| PG事务、唯一约束和外键 | 同样要数据库约束和真实隔离验证，不能只靠前端去重 |
| DO块校验及UPDATE RETURNING | 此审定脚本是PG专用，须重写目标引擎的校验/返回路径 |
| zhparser、tsvector、pgvector | 本项目投影/向量SQL依赖PG扩展，换引擎需重设计检索方案，不能直接复用迁移 |

本轮没有换数据库或技术栈。对照用于理解哪些是通用事务思想、哪些是PG具体实现。

## 10. 面试问答

**1. 为什么要先分离说明再匹配数量？**

说明里的数字可能是尺寸、步骤或比例，不是材料总量；先判断语义边界，才可把数字作为事实。指节中的“一”就是反例。

**2. 等号是不是都代表公式？**

不是。右侧纯数字+单位如小龙虾=1kg仍是明确量；右侧依赖肉重、比例或其他材料时不求值，只提取明确左侧名称并保留null。

**3. 为什么不拆组合原料？**

组合总量没有说明各自比例，拆开会编造独立事实。保留组合原行和未知比产生错误采购量可靠。

**4. 为什么新规则不用新的sourceVersion？**

来源版本描述原快照，不描述解析器。改假版本绕SUCCESS会破坏一次性导入语义；本轮用新空库和独立规则版本。

**5. 怎么证明@Transactional真的生效？**

既检查真实代理，也让步骤插入抛SQL异常，核对失败文件关联写入回滚，其他文件仍提交。只看注解或Mock Mapper不足以证明。

**6. 用户确认10g后原份数是不是就已知？**

不是。确认量是本餐用户事实，原菜谱人数仍null；它可以授权明确ID的匹配，不能反写源菜谱或改历史。

**7. 食材审定能否解决商品单位不一致？**

不能。标准语义、数量和维度是不同问题；生抽g与ml不能凭常识补密度，只有同维明确换算允许。

**8. 同名商品为什么不能直接匹配？**

名称可能有别名、品种和数据库重建后的ID漂移。Provider只按明确ID；人工核验目录是一次有边界的配置审定，不是运行时猜测。

**9. 未知成本为什么不能以0参与预算？**

0是已确认没有支出，null是证据缺失。未知项只能列已知小计和UNKNOWN预算，不承诺满足上限。

**10. 数据重导成功能否直接宣布向量/网页完成？**

不能。结构化、索引、运行连接和真人闭环分别验收；D1-C也须先通过当前复审，再在条件收费卡内执行。
