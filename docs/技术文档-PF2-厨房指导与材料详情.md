# PF2 技术学习说明：厨房指导与材料详情

## 1. 组件职责

- `MealOptionCard` 负责候选阅读和显式选择。它接收餐单固定上下文，提供材料详情深链，不保存材料事实或触发读取。
- `KitchenMaterialsView` 解析受保护路由和 query，显示只读详情与回工作台链接。
- `materialsState` 是材料页面的专属读取状态，依赖 `KitchenApi.getMeal` 这一既有接口；它不暴露任何写 API。
- `guidePresentation.ts` 是纯展示投影：把已解析的指导快照按 `recipeId` 关联事实、讲解和补充，并形成去重引用列表。
- `MealGuidePanel` 只负责把投影呈现为整餐备菜、逐菜事实/讲解、公共安排/提醒、模型补充和末尾参考链接。
- `KitchenAssistantView` 继续持有原厨房业务状态和采购门槛，仅增加材料返回时的只读餐单定位，并把已确认方案摘要放在独立右栏。

## 2. 逐菜投影和事实边界

`MealGuideView.recipes` 是服务器保存的原菜谱事实快照；`content.recipes` 是按 `recipeId` 返回的指导讲解。展示投影按这两个 ID 关联，而不是按菜名或数组位置猜测。材料引用量来自对应餐单材料快照，原始量、参考折算和未知状态分别显示。

整餐 `preparation` 不塞入某一道菜。`cookingOrder` 与 `cautions` 继续留在公共整餐区，避免用自然语言推断其适用菜。单菜可选补充只在唯一匹配菜谱时放入该菜卡；跨菜补充保留在公共区。补充中的 `recipeIds` 表示适用范围，不是菜谱证据，因此不会生成参考链接，也不会进入原始材料。

集中引用只遍历 `preparation`、逐菜 explanations、`cookingOrder`、`cautions` 的结构化 `evidence`。每个证据的 `recipeId` 必须能在同一个指导快照的 `recipes` 中找到，才加入末尾链接集合；`stepNos` 和 `ingredientIds` 数据及解析校验没有变化。

## 3. 只读材料读取与异步隔离

材料 URL 固定携带 `conversationId`、`mealId`，query 携带 `version`、`optionId`。状态读取开始时先校验标识、版本格式和当前账号；随后调用 `getMeal(conversationId, mealId, signal)`。响应发布前再次确认请求代次和账号，并匹配响应会话、餐单、版本与方案。

`UNAVAILABLE` 不发布任何餐单/方案快照；旧版本不匹配或方案不存在时显示明确错误，不回退到当前版本或其他方案。`CHANGED` 只显示服务器仍允许读取的原版本快照，并显式标记事实已变化。

每次新路由上下文或账号读取都会增加本地 generation 并中止前一等待。成功、异常和 `finally` 都先检查 generation、AbortController 与 owner；因此忽略 AbortSignal 的迟到响应也不能覆盖新上下文。本地中止只代表前端不再等待，不代表服务器取消了 GET。

回到厨房时使用只读 `showMeal(mealId)` 恢复餐单，并比较返回版本/方案上下文；没有任何隐式 SELECT、GUIDE 或采购请求。原厨房状态机中的 UUID、payload、未知操作核对和账号归属代码未改。

## 4. 响应式布局

宽屏采用历史、正文、所选摘要三栏；到窄屏宽度时摘要改为正文下方，手机宽度下三部分纵向排列。候选卡与材料详情的材料行会在小屏改为单列。此处通过组件局部样式处理，没有修改全局设计系统或增加依赖。

## 5. 可讲清的设计问题

**为什么详情页重读服务端，而不传整份材料对象？**

链接只传不可变来源标识和版本上下文，页面重新使用账号受保护的 GET。这样刷新和复制深链仍能校验权限、版本和事实可用性，不依赖前端缓存冒充历史快照。

**generation 与 AbortSignal 各自解决什么？**

AbortSignal 尽量停止本地等待；generation 是发布结果前的逻辑隔离。即使底层忽略取消或响应已经返回，旧结果仍因代次不匹配而被丢弃。

**为什么不把整餐提醒分配到菜卡？**

服务端证据可以覆盖多道菜。根据文本猜测归属会丢失共同安排或制造错误事实，所以公共内容继续独立显示。

**为什么模型补充不生成菜谱引用？**

适用 `recipeIds` 只表示建议面向哪些菜，不证明建议内容来自原菜谱。引用集合只接受通过解析的 `evidence.recipeId`。

**为什么所选方案摘要依据 Store 的 `selectedOptionId`？**

按钮点击只表示用户意图。只有服务端确认后的餐单快照才能决定右侧显示哪套方案，避免先乐观发布未成功选择。

## 6. 验证边界

Vitest 使用合法 fixture 和延迟 Promise，覆盖来源关联、引用去重、版本/方案/账号隔离、无效深链、`CURRENT`/`CHANGED`/`UNAVAILABLE` 及读取失败。它不验证已部署后端、真实浏览器窄屏像素、数据库访问或真实模型输出；这次均未执行。
