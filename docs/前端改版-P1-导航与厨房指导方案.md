## 2. 导航与兼容

顶栏建议：浏览菜谱、烹饪助手、采购清单、个人档案、模型设置。用户未要求移动模型设置，本轮保持独立入口。

个人档案内部子导航：用餐设置、我的收藏、做菜历史。复用当前 DiningProfileView、FavoritesView、CookedRecipesView，不改认证、默认人数保存、收藏或做菜统计接口。

建议新增档案子路由 `/settings/profile/favorites`、`/settings/profile/cooked-recipes`。已有 `/favorites`、`/cooked-recipes` 和路由名称须兼容，不能使旧详情返回、未确认做菜操作和刷新链接失效。优先通过同一布局及路由别名实现；若重定向，须保留必要的query/hash和原操作上下文。

统一助手默认使用 `/kitchen`。工作台提供“旧版推荐记录与操作核对”入口，保留 `/chat`、`/chat/:conversationId`、原状态和接口。旧消息不是餐单，不转换ID、不删除记录、不自动迁移、不自动产生模型请求。现有待核对横幅仍准确返回原模块与原操作。

## 3. 厨房工作台布局

- 未选择：展示两套方案的菜名、评价和明确选择按钮；材料用详情入口查看。
- 已选择：中间为整餐概述、整餐备菜、逐菜指导、必要的整餐共用提示、末尾参考菜谱；右侧为已选方案摘要及材料详情入口。
- 左侧对话/本餐历史保留；宽屏可采用三栏，小屏将历史和方案摘要收起或上下排列，不能为了右侧栏挤压正文或出现横向溢出。
- 右侧摘要以服务端 `selectedOptionId` 为准，不以本地点击提前宣布选择成功；指导失败时保留已选摘要和显式重试入口。
- 不新增“直接换选已保存方案”行为。继续沿用现有新餐/修订权限和状态约束，历史版本不得因展示改版恢复写操作权限。

## 4. 逐菜指导与引用边界

已核对现有 MealGuideView：`recipes` 保存原菜谱事实，`content.recipes` 提供带recipeId的逐菜讲解，`preparation`、`cookingOrder`、`cautions` 的文本块含结构化evidence，`optionalSuggestions` 保存模型补充。可先做前端投影，无需改变生成接口或Prompt。

每道菜卡按recipeId关联以下内容：

1. 原菜谱材料：保留未知量、单位、可选和参考折算说明，不伪造实际用量。
2. 原菜谱做法：保留原步骤及顺序。
3. 小厨详细讲解：展示该recipeId的已保存讲解，标签与原步骤区分，避免把解释当成新的原始事实。
4. 本菜提示：单菜依据的提示可归入本菜。跨多菜的烹饪顺序和注意事项保留在紧凑的“整餐安排与提醒”区，不按文本猜测归属、不丢弃内容。
5. 可选模型补充：适用单菜的放入本菜并明确标注；跨菜/整餐建议保留公共区。补充不是原菜谱事实，不自动加入采购材料。

整餐备菜独立保留。跨菜的时间安排只作为已有指导展示，不新增对总耗时、预算或营养达标的保证。

集中参考链接以已验证的evidence.recipeId去重，解析到当前指导快照内的菜谱名称，再链接现有菜谱详情页。模型补充适用菜谱不等于它已获得原菜谱事实支持，不能混为事实引用。

只简化可见引用，不删除接口中的stepNos/ingredientIds，不放松前端解析或服务端依据校验。历史指导仍显示保存快照；事实CHANGED时保留提示，详情链接代表当前菜谱，不能以当前事实替换旧快照。UNAVAILABLE时继续隐藏被服务端判为不可用的内容。

## 5. 材料详情页

建议新增受保护只读路由 `/kitchen/:conversationId/meals/:mealId/materials`，query包含 `version`、`optionId`。菜单按钮完整携带该上下文；现有 `getMeal` 可用于读取并校验返回的版本和方案归属。

- 展示本方案合并材料、逐菜原始材料、参考量及待确认原因，保留UNKNOWN，不把未知当0。
- 未选方案也可查看，但查看不得隐式选择、生成指导或创建采购清单。
- 旧版本不匹配、方案不属于餐单或不可用时显示明确提示，不静默换成当前版本/其他方案；无法独立读取的旧版本先提示回历史核对，不用前端缓存冒充服务器快照。
- 页面刷新与深链依靠已有GET，不新增后端接口；读取动作不调用模型。
- 返回链接恢复原会话和餐单。若现有工作台不支持固定mealId定位，可增加只读路由query接线，不改变写请求及幂等键。
- 采购入口仍沿用现有CURRENT、已选择、人数有效、无未确认操作等门槛；材料详情不是另一条绕过确认的采购路径。
