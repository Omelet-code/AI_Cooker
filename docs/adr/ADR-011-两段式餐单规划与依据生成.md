# ADR-011：两段式餐单规划与依据生成

- 日期：2026-10-03，Asia/Shanghai。
- 状态：业务决定已确认；U1/U2实现与非收费验收已签收，UF1由用户确认完成并跳过独立复审。2026-10-04用户允许完整后端基线整合后派发U3，kitchen-meal-v1工程数值/HTTP/V11已终审，见 `../阶段3-U3餐单与选择契约.md`；U4/UF2及真实收费/部署未授权。下文工程待终审指后续切片，不否定已冻结U3。
- 契约：`../阶段3-厨房助手升级契约.md`。

## 背景

用户实际测试指出“四菜一汤”需要数量、角色、随机搭配，而不是相关菜谱列表。用户要求默认两套组合及食材，通过鼠标选择后，由LLM依据详细菜谱生成完整指导；人数取本餐显式输入或个人档案默认设置，采用“小厨”基础人设。长期自动记忆不在当前范围。

## 候选方案

| 方案 | 成本与特点 | 判断 |
| --- | --- | --- |
| 只放宽旧模板/改Prompt | 改动少，但3推荐上限、缺餐单结构和食材证据仍在 | 不足以满足目标 |
| 结构化组餐＋点击选择＋依据生成 | 复用现有网关、事实与PG，业务和费用边界可独立测试 | 采用 |
| 自主多步规划＋工具循环＋长期Memory | 灵活，但增加调试、成本、状态与安全负担 | 后置 |

## 决策与理由

1. 新餐单资源保留旧T14/F3-B接口与历史，先冻结业务规则再实现，避免把生成字段直接塞进旧结果破坏兼容。
2. 随机任务通过硬条件资格池和受控分角色抽样；语义任务仍调用生产混合检索，不为了随机强行Embedding，也不改旧RRF。
3. 方案阶段只输出两组真实ID和说明，服务器组装材料。点击后才读取所选完整详情，允许LLM依据生成文本；与ADR-010固定模板是新增能力边界，不追溯否定旧验收。
4. 事实、数量、权限、材料计算和幂等属于服务器；人设、解释、备菜建议属于模型；补充建议单独标注。引用检查不等于语义正确，增加人工内容验收。
5. 人数档案显式配置、本餐结构化短期状态与历史存储相互区分，不引入长期自动Memory。
6. 每次模型等待不持有PG事务，动作和选定方案用数据库版本/唯一条件保证；读取和重放不生成。新预算重新冻结，收费另批，测试阶段限制服务器可执行动作。

## 影响与复审

需增加个人档案、菜谱角色审计、餐单状态/快照、点击选择、详细指导与前端。任务见专属计划，原T15/SSE及采购暂缓，不自动取消采购目标。现阶段不新增框架、支付、库存或用户自定义菜谱入口。

若事实分类不足、所选详情超过上下文或无法在截止前完成，应报告真实差距，由用户决定缩减或延期，不静默补造事实、减少材料或额外收费重试。更换模型、自动长期记忆或自主工具规划时重审。
