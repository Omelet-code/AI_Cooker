# ADR-004：混合检索与向量版本化

- 状态：拟议（阶段 1 未启用）
- 日期：2026-09-25

## 背景

菜谱查询同时包含精确实体和模糊意图。例如“鸡蛋”需要可靠匹配原料，“想吃点清淡的”需要语义召回。只使用关键词会漏掉语义表达，只使用向量又可能弱化菜名和原料的精确命中。

## 决策

1. `recipe` 模块拥有菜谱事实数据，`retrieval` 模块拥有可重建的检索冗余数据。
2. 词法通道使用菜名/原料精确匹配与 PostgreSQL `pg_trgm`。
3. 语义通道使用 pgvector cosine distance。
4. 硬过滤后两路各召回 30 条，使用 `1/(60 + lexicalRank) + 1/(60 + vectorRank)` 融合；未进入某通道的候选不计算该通道项。
5. 百炼模型固定为 `text-embedding-v4`、1024 维，通过 DashScope 原生 HTTP 接口调用；入库使用 `text_type=document`，查询使用 `text_type=query`，输出固定为 dense。
6. 检索文档记录模板版本、模型、维度、内容哈希和生成时间。
7. 内容哈希未变化时不重新向量化；模型或维度变化必须重建完整索引。
8. 数百条菜谱先使用精确向量扫描，不创建 HNSW/IVFFlat。
9. 检索查询只读取状态为 READY 且模型、维度和文档版本与当前配置一致的索引记录。

## 结果

- 精确实体和自然语言意图可以互补；
- 排序不依赖不同分值体系的脆弱归一化；
- 检索索引可以删除并从菜谱事实数据重建；
- 需要维护评测集、索引状态和向量版本迁移流程。

## 触发复审的条件

- 菜谱超过 10,000 条；
- 向量候选查询 p95 超过 150ms；
- 更换 Embedding 模型或维度；
- 引入 Elasticsearch/OpenSearch；
- 评测证明固定权重 RRF 无法达到质量门槛。

## 备选方案

### 只使用向量检索

拒绝。菜名和原料等精确条件的稳定性不足，也难以解释。

### 直接相加 trigram 分数和 cosine 相似度

拒绝。两类分数分布不同，数据变化后需要重新归一化和调参。

### 立即创建 HNSW

后置。当前数据规模无法证明收益，反而增加索引参数、写入成本和学习负担。
