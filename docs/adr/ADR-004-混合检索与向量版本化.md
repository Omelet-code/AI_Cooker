# ADR-004：混合检索与向量版本化

- 状态：已接受（T4 索引投影已启用；T5 混合检索已授权；T6 评测待后续授权）
- 日期：2026-09-25

## 背景

菜谱查询同时包含精确实体和模糊意图。例如“鸡蛋”需要可靠匹配原料，“想吃点清淡的”需要语义召回。只使用关键词会漏掉语义表达，只使用向量又可能弱化菜名和原料的精确命中。

## 决策

1. `recipe` 模块拥有菜谱事实数据，`retrieval` 模块拥有可重建的检索冗余数据。
2. 词法通道使用菜名/原料精确匹配与 PostgreSQL 中文全文检索；`zhparser` 负责将 `content` 自动生成 `tsvector`，并保留 `pg_trgm` 作为后续短文本模糊匹配补充。
3. 语义通道使用 pgvector cosine distance。
4. 硬过滤后两路各召回 30 条，使用 `1/(60 + lexicalRank) + 1/(60 + vectorRank)` 融合；未进入某通道的候选不计算该通道项。
5. 百炼模型固定为 `text-embedding-v4`、1024 维。业务代码只依赖 Spring AI `EmbeddingModel`；项目内 DashScope 适配器负责原生 HTTP 调用。入库使用 `text_type=document`，查询使用 `text_type=query`，输出固定为 dense。
6. 每道菜按 `overview`、`ingredients`、`tools` 和 `steps` 构建检索块；步骤块由连续 3～5 个完整步骤组成，绝不按字符截断单个步骤。每个块都包含菜名与分类上下文。
7. 检索文档记录模板版本、模型、维度、内容哈希和生成时间。
8. 内容哈希未变化时不重新向量化；模型或维度变化必须重建完整索引。
9. 数百条菜谱先使用精确向量扫描，不创建 HNSW/IVFFlat。
10. 查询只读取状态为 READY 且模型、维度和文档版本与当前配置一致的索引记录。每条召回通道先按 `recipe_id` 保留最佳 chunk，再按 `recipe_id` 执行 RRF，禁止步骤块数量累计抬高菜谱分数。
11. HowToCook 系统菜谱和用户自定义菜谱使用同一索引结构与 Embedding 流程；索引投影携带来源类型、所有者和可见性，查询必须先执行权限过滤。

## 结果

- 精确实体和自然语言意图可以互补；
- 排序不依赖不同分值体系的脆弱归一化；
- 检索索引可以删除并从菜谱事实数据重建；
- 用户自定义菜谱同样具有向量检索能力，同时不会泄露给其他用户；
- 需要维护评测集、索引状态和向量版本迁移流程。

## 触发复审的条件

- 菜谱超过 10,000 条；
- 向量候选查询 p95 超过 150ms；
- 更换 Embedding 模型或维度；
- 引入 Elasticsearch/OpenSearch；
- 评测证明固定权重 RRF 无法达到质量门槛。

## 备选方案

### 只使用向量检索

拒绝。菜名和原料等精确条件的稳定性不足，也难以解释。

### 直接相加 trigram 分数和 cosine 相似度

拒绝。两类分数分布不同，数据变化后需要重新归一化和调参。

### 立即创建 HNSW

后置。当前数据规模无法证明收益，反而增加索引参数、写入成本和学习负担。
