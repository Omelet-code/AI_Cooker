# ADR-003：HowToCook 快照导入与宽容解析

- 状态：已接受
- 日期：2026-09-25

## 背景

HowToCook 使用社区维护的 Markdown。官方提供示例模板，但历史菜谱可能缺少可选字段、使用不同单位或存在章节格式差异。若运行时直接读取 GitHub master，导入结果会随上游变化且受网络可用性影响。

## 决策

1. 阶段 1 固定 HowToCook `1.6.0`，commit `a0b14bd`。
2. 导入器只读取开发者准备的本地快照，不负责在线下载仓库。
3. 使用 `recipe_source` 表示来源路径的稳定身份，使用 `recipe_source_document` 保存每个来源版本、SHA-256 和完整原始 Markdown。
4. 解析采用宽容策略：缺失可选字段产生 warning；缺失菜名或操作步骤才判定失败。
5. 数量或单位无法标准化时保留原始行，结构化字段允许为空。
6. 单文件失败不回滚整个批次，导入结果必须提供可审计报告。
7. 重复版本、路径和内容哈希不得产生重复菜谱；同一路径升级版本时更新原有 recipeId，并保留新的原文快照。

## 结果

- 导入可复现，测试可以使用固定 fixture；
- 上游格式变化不会静默污染全部数据；
- 后续用户自定义菜谱可复用同一解析模型；
- 需要额外维护 warning、失败状态和重导逻辑。

## 备选方案

### 运行时调用 GitHub API

拒绝。会把网络、限流和版本漂移引入核心导入流程。

### 严格模板校验，任一字段缺失即失败

拒绝。会损失大量仍可使用的社区菜谱，也不利于展示真实数据治理能力。

### 用 LLM 直接解析全部 Markdown

阶段 1 拒绝。成本、稳定性和可重复性较差；未来只能作为人工确认前的补全建议，不能覆盖确定性解析结果。
