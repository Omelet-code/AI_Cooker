# ADR-003：HowToCook 一次性种子导入与统一模板解析

- 状态：已接受（阶段 1 数据导入基线）
- 日期：2026-09-25

## 背景

HowToCook 使用社区维护的 Markdown。官方提供示例模板，但历史菜谱可能缺少可选字段、使用不同单位或存在章节格式差异。项目只需要它提供初始菜谱，不需要持续跟随上游。后续用户会按照同一模板维护私有自定义菜谱，因此解析和存储模型必须能够复用，同时保证用户数据隔离。

## 决策

1. 阶段 1 固定 HowToCook `1.6.0`，commit `a0b14bd`。
2. HowToCook 只作为系统级公开种子数据，在项目初始化时通过显式入口导入一次；不实现定时、实时、增量、Webhook 或 GitHub API 同步。
3. 导入器只读取开发者准备的本地快照，不负责在线下载仓库。初始化失败允许使用同一快照幂等重试，但这不属于数据同步。
4. 解析器面向“HowToCook 兼容模板”，不与 GitHub 下载或系统种子导入入口绑定，后续用户自定义菜谱复用同一解析器。
5. 所有菜谱统一保留三层数据：`recipe_source_document` 中的原始 Markdown；`recipe` 及关联表中的当前结构化事实；`recipe_search_document` 中可重建的词法文本、Embedding 元数据和向量。
6. `recipe_source` 区分 `SYSTEM_HOWTOCOOK` 与 `USER_CUSTOM`。系统来源无用户所有者且公开；用户来源绑定 `owner_user_id` 并默认私有。
7. 解析采用宽容策略：缺失可选字段产生 warning；缺失菜名或操作步骤才判定失败。数量或单位无法标准化时保留原始行，结构化字段允许为空。
8. 单文件失败不回滚整个批次，导入结果必须提供可审计报告。
9. HowToCook 初始化完成后视为只读；若未来需要升级快照，必须通过新的 ADR 和显式迁移任务，不复用运行时同步机制。
10. 后续用户自定义菜谱的创建和修改追加原始文档版本、更新当前结构化事实，并按内容哈希重建该菜谱的检索投影。

## 结果

- 导入可复现，测试可以使用固定 fixture；
- 运行时不受 HowToCook 上游可用性和版本变化影响；
- 后续用户自定义菜谱可复用同一解析模型和三层数据管线；
- 系统菜谱与用户私有菜谱的来源、所有者和可见性边界明确；
- 需要额外维护 warning、失败状态、初始化完成标识以及用户菜谱版本。

## 备选方案

### 运行时调用 GitHub API

拒绝。会把网络、限流和版本漂移引入核心导入流程。

### 定时或实时同步 HowToCook

拒绝。项目只需要一次性种子数据，持续同步会增加冲突处理、删除语义、向量重建和运行稳定性成本。

### 严格模板校验，任一字段缺失即失败

拒绝。会损失大量仍可使用的社区菜谱，也不利于展示真实数据治理能力。

### 用 LLM 直接解析全部 Markdown

阶段 1 拒绝。成本、稳定性和可重复性较差；未来只能作为人工确认前的补全建议，不能覆盖确定性解析结果。
