# UF2 技术学习说明：餐单与指导状态

## 代码分层

- `KitchenAssistantView.vue` 负责页面组合、输入和用户动作，不直接拼 HTTP 请求。
- `kitchen/api.ts` 负责路径、超时、取消信号和请求/响应转换；它复用项目共享 `apiClient` 的 Cookie、CSRF 与统一错误处理。
- `kitchen/validation.ts` 在运行时检查服务端 JSON。TypeScript 类型只在编译阶段约束代码，不能证明网络响应符合类型，因此关键字段、枚举、ID 归属和版本仍要检查。
- `kitchen/state.ts` 是业务状态机，协调加载、请求、幂等上下文、轮询、路由/账号代次以及显示状态；`store.ts` 将状态接入 Pinia。
- `MealOptionCard.vue` 展示两套餐单和材料事实；`MealGuidePanel.vue` 展示已保存指导、引用及独立可选建议。

## 为什么 SELECT 与 GUIDE 分成两步

选择餐单是确定性的服务端状态变更；生成指导会调用模型，可能耗时或产生费用。先提交 SELECT 并重新读取当前餐单，只有确认选中版本和事实仍有效，才发送 GUIDE。两步各用一个 requestId，避免“选中失败但指导已请求”以及把选择重试误当成新生成。

GUIDE 的动作响应只包含动作状态和餐单快照，完整指导通过保存的 guide ID 再 GET。历史回看因此只读数据库中的快照，不会因为刷新重复调用模型。

## 幂等、未知结果与取消

幂等键解决“请求已到服务器，但客户端没有收到响应”的歧义。客户端为每个 POST 先生成 UUID，再冻结对应 payload；超时或网络中断后必须保留这一对值。自动换 UUID 重试会被服务端视为新动作。

前端请求中止只代表停止本地等待，不代表服务器回滚或模型调用取消。因此未知状态展示核对入口：如果有 action ID，只对该动作做有界 GET 轮询；如果没有 ID，则需要用户确认后才允许用原 requestId 和 payload 再发，以便服务端按幂等键返回原结果或继续原动作。

## 快照事实、证据与建议

餐单版本中的菜名、原料、步骤、工具和材料参考量是服务端返回的事实快照。模型指导的说明通过 `recipeId`、步骤号和 `recipeIngredientId` 指向这些事实；前端用站内锚点定位证据。模型的 `optionalSuggestions` 单独显示为补充内容，不能混成菜谱原文。

`CURRENT` 表示可按当前事实进行操作；`CHANGED` 只允许历史回看并提示修订；`UNAVAILABLE` 意味着引用事实不可用，界面必须隐藏相关内容并清除旧缓存，不能把上一次读取的数据继续展示。

材料金额/数量类字段是十进制字符串。前端只显示服务端计算值，不用 JavaScript 浮点数重算；未知量以 `null` 表达，并明确提示核对。

## 学习点

1. Vue 组合式状态、Pinia store 与 `AbortController` 如何协作。
2. 用 requestId + 不可变请求体处理 POST 幂等和网络结果未知。
3. 用运行时解析器建立 HTTP 边界，而不是把 JSON 强制断言成接口类型。
4. 用版本号和证据 ID 保持快照一致性与引用可追溯性。
5. 把“原始事实”“模型解释”“可选建议”分层表达，避免界面混淆事实来源。

## R1～R3 修复为什么必要

**请求版本与返回版本有不同职责。** `expectedVersion` 表示用户修改时所见版本，相当于乐观锁条件；后端在登记 REVISE 时创建下一版本。因此请求 7 合法返回动作/餐单版本 8，不能要求返回仍为 7。SELECT/GUIDE 只针对现有版本操作，不递增。旧幂等结果若已落后于当前已知版本，只结束原核对，不覆盖当前餐单。修订测试也必须模拟真实 7→8 协议，不能让替身复制请求版本来掩盖错误。

**取消信号和请求代次必须同时使用。** `AbortController` 可以停止本地等待，但替身或已完成的异步操作仍可能交付迟到结果。账号/会话代次无法区分同一会话中的餐 30 和餐 31，因此状态层另设 `mealGeneration`；换餐、新餐、刷新都递增它。每个 POST/GET 结果应用前检查账号、会话、餐单代次及目标，旧代次既不写界面也不继续 GUIDE。原选择点击链还需核验 GET 返回的是请求中的原版本和原选项，不能把新版本当作原点击的授权延续。

**核对上下文与新请求有不同入口。** 模块记录原账号、会话、餐单、requestId 和不可变 payload。只有回到原上下文才可核对；未知 CREATE 尚无餐单 ID 时回到新餐输入区。已知 action ID 用 GET，未知 ID 经明确确认才能原键 POST；核对 SELECT 不会顺便生成指导。未确认动作会阻止同目标直接生成新 UUID，避免旧请求仍在执行时出现第二条链。

**未知指标不能伪造为零。** 后端在语义候选调用之前将 `semanticSearchCalls` 设为 null，调用中途失败时无法确定实际次数；这与确定没有调用的 0 不同。类型与解析器都保留 `number | null`，只接受非负安全整数或 null。否则合法 FAILED 会被误判为无效响应，使 pending 无法正常结束。

本次新增 `kitchen-repair.test.ts` 在实际状态机与解析器边界做正确行为回归，并补四菜一汤两套方案的解析/页面渲染。历史复现探针中“断言缺陷存在”的通过只证明曾复现问题，不能充当修复通过证据。当前测试使用替身，不等于真人浏览器联调。

## 面试问答

**问：收到 HTTP 201，为什么不能直接认为生成成功？**
答：业务动作可能以 `FAILED` 终态返回；应解析响应体中的动作状态，并在 `PENDING`/`RUNNING` 时按动作 ID 查询。

**问：POST 超时后为什么不能生成新 UUID 重试？**
答：服务器可能已处理原请求。新 UUID 会创建另一项业务动作；保留原键和原 payload 才能进行幂等核对。

**问：为什么选中方案后还要重新 GET 餐单？**
答：动作响应可能是较早快照或被幂等复用。重新读取并检查版本、事实状态和选项，避免基于旧事实触发生成。

**问：TypeScript 类型为什么不能取代响应校验？**
答：服务端响应是运行时外部数据，编译器不会验证实际 JSON。解析器可在接触业务状态前拒绝结构错误、类型错误和归属不匹配。

## 自检

- 页面打开、刷新、历史回看是否只有 GET？
- SELECT 与 GUIDE 是否各有 UUID，并且 GUIDE 只在 SELECT 当前状态核验成功后发送？
- 超时/断网后是否保留原请求键和正文，没有自动重发？
- 指导是否来自保存的 guide ID，而非把动作响应误当完整指导？
- `CHANGED` 和 `UNAVAILABLE` 是否分别做到只回看与彻底隐藏旧事实？
- 材料小数是否一直作为字符串处理，未知量是否保留 `null`？
- 修订 7→8 是否展示第 8 版并关闭 pending，旧重放是否保留更高版本？
- 在同会话换餐/新餐后，迟到 SELECT/GET/GUIDE 是否都被原代次隔离？
- 未知操作是否只能在原上下文核对，核对 GET/POST 是否不会自动追加 GUIDE？
- 未确认同目标操作是否阻止直接换 UUID，null 调用量是否仍表示未知？
