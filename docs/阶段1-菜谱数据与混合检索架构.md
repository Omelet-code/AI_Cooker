## 1. 阶段目标

阶段 1 建立一条用于项目初始化、可诊断且失败后可幂等重试的菜谱检索链路：

```text
固定版本 HowToCook 快照（一次性种子）
        ↓
Markdown 宽容解析
        ↓
菜谱结构化存储 + 原文留存
        ↓
生成检索文档与 Embedding
        ↓
结构化过滤 + 词法召回 + 向量召回
        ↓
RRF 融合排序
        ↓
返回数据库中真实存在的菜谱候选
```

本阶段结束时，系统应能针对“想吃清淡的”“有鸡蛋和西红柿”“只有微波炉”等文本和结构化约束返回可解释的菜谱候选，但暂不接入聊天 Agent、用户库存、预算和商品采购。

## 3. 阶段 1 技术决策状态

T1～T5 的数据版本、导入、检索投影、Embedding、召回与融合决策已经冻结。T5 的实现边界与验收见 `阶段1-T5混合检索任务契约.md`；T6 已授权建立评测，不改变生产排序和其他冻结决策。

| 决策点 | 阶段 1 选择 | 原因 |
|---|---|---|
| 数据版本 | HowToCook `1.6.0`，commit `a0b14bd` | 可复现，避免 master 漂移 |
| 数据获取 | 开发者预先准备本地快照，导入器读取本地目录 | 运行时不依赖 GitHub 可用性，不把网络下载混进解析事务 |
| 同步策略 | 部署初始化时一次性导入，无自动同步 | HowToCook 只承担种子数据角色，避免把外部仓库生命周期耦合到业务运行时 |
| 解析策略 | 宽容解析，原文必存，字段解析失败记录 warning | 上游 Markdown 存在格式差异，不能因一个字段失败丢掉整道菜 |
| 主键 | `BIGINT GENERATED BY DEFAULT AS IDENTITY` | 对学习项目最直接；微服务拆分后各服务独立数据域，不要求全局连续 ID |
| 时间类型 | `timestamptz` | 避免部署到 Linux 后出现时区歧义 |
| Embedding | 百炼 `text-embedding-v4`，1024 维，float | 中文能力、成本和维度平衡；维度必须与 `vector(1024)` 一致 |
| Embedding 接入 | Spring AI `EmbeddingModel` 接口 + 项目内 DashScope HTTP 适配器 | 保持 Spring AI 2 / Boot 4 兼容，同时支持 `text_type=document` |
| 中文词法检索 | `zhparser` 生成 `tsvector`，后续配合原料精确匹配 | 中文词元在 PostgreSQL 内完成，投影列可用 GIN 索引 |
| 向量检索 | cosine distance，精确扫描 | 数据量只有数百道菜，先建立正确基线 |
| 融合算法 | Reciprocal Rank Fusion（RRF） | 不需要把词法分数和向量距离强行归一化，易解释、易调参 |
| 异步方式 | 阶段 1 同步导入 + 可重试索引状态 | RabbitMQ 后置；失败记录状态，可人工重建 |

## 4. 模块职责与依赖

### 4.1 `recipe` 模块

负责：

- HowToCook 兼容 Markdown 模板解析；
- 菜谱、原料、工具、步骤和来源原文持久化；
- HowToCook 一次性种子导入、失败重试幂等和解析诊断；
- 为后续用户自定义菜谱复用同一解析模型和三层存储契约；
- 对外提供只读的菜谱详情与检索投影。

不负责：

- 调用 Embedding API；
- 编写向量和融合排序 SQL；
- 理解用户自然语言意图。

### 4.2 `retrieval` 模块

负责：

- 接收 `RecipeIndexDocument`；
- 生成并版本化检索文本；
- 调用 `EmbeddingProvider`；
- 保存检索文档、向量和索引状态；
- 执行结构化过滤、词法召回、向量召回和 RRF 融合；
- 输出带解释字段的候选结果。

不负责：

- 直接访问 `recipe` 模块 Mapper 或 Entity；
- 修改菜谱事实数据；
- 保存用户对话和长期记忆。

### 4.3 调用方向

```text
导入入口
  └─ RecipeImportService
       ├─ 写入 recipe 自有表
       └─ 提交后发布 RecipeChangedEvent
              └─ RecipeIndexService.upsert(RecipeIndexDocument)
                     └─ EmbeddingProvider

查询入口
  └─ RecipeSearchService
       └─ retrieval 自有 Mapper/XML
              └─ 返回 recipeId + 排名解释
                     └─ RecipeQueryService 批量补齐展示详情
```

事件仅承载 ID、版本和必要投影，不传递 Entity。索引失败不能回滚已经成功导入的菜谱，应写入失败状态并允许重试。

| `visibility` | `String` | 系统菜谱为公开，用户自定义菜谱默认私有 |
| `sourceDocumentId` | `Long` | 当前原始文档版本 ID |
| `name` | `String` | 菜名 |
| `categoryCode` | `String` | 来源目录分类编码 |
| `summary` | `String` | 简介，可为空 |
| `difficulty` | `Integer` | 1～5，可为空 |
| `estimatedMinutes` | `Integer` | 可为空，不能凭空推断 |
| `servings` | `Integer` | 份数，可为空 |
| `caloriesKcal` | `Integer` | 热量，可为空 |
| `ingredientNames` | `List<String>` | 规范名优先，否则原始名 |

### 5.2 `RecipeSearchCriteria`

| 字段 | 必填 | 说明 |

| `categoryCodes` | 否 | 允许的菜谱分类 |

| `excludedIngredientNames` | 否 | 排除原料，使用规范名和别名匹配 |
| `viewerUserId` | 否 | 阶段 1 为空，只查系统公开菜谱；后续登录用户查询时用于包含本人私有菜谱 |

## 6. 数据架构

### 6.1 `recipe` 模块拥有的表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `recipe_import_batch` | source_type、source_version、status、统计、started_at、finished_at | 一次导入的审计和统计 |
| `recipe_source` | source_type、source_key、source_uri、owner_user_id、visibility | 菜谱来源的稳定身份；系统来源无所有者，用户来源绑定创建者并默认私有 |
| `recipe_source_document` | source_id、source_version、content_hash、raw_markdown、parse_status、parse_warnings JSONB、import_batch_id | 某个来源版本的原文快照与解析诊断 |
| `recipe` | source_id、source_document_id、name、category_code、summary、difficulty、estimated_minutes、servings、calories_kcal | 当前生效的菜谱主体；同一 source 只保留一个稳定 recipeId |
| `ingredient` | canonical_name、normalization_status | 规范原料；未知项允许以待复核状态进入 |
| `ingredient_alias` | ingredient_id、alias_name | 原料别名，别名全局唯一 |
| `recipe_ingredient` | recipe_id、ingredient_id、raw_name、amount_min、amount_max、unit_code、unit_label、optional、raw_line、sort_order | 菜谱用料 |
| `cooking_tool` | canonical_name | 规范厨具 |
| `recipe_tool` | recipe_id、tool_id、optional | 菜谱工具 |
| `recipe_step` | recipe_id、step_no、content | 操作步骤 |

数量和单位解析失败时，`raw_line` 必须保留，结构化数量字段允许为空。`optional` 来自明确的“可选”等文本，不允许由模型猜测。

HowToCook 初始化后视为系统级只读种子数据，不因 GitHub 上游变化自动追加版本。后续用户自定义菜谱每次创建或修改都追加 `recipe_source_document`，更新当前 `recipe` 结构化事实，并触发自己的检索投影重建。`owner_user_id` 在身份模块表建立前只作为可空逻辑标识，后续迁移再补充外键约束，`recipe` 模块不得直接访问身份 Mapper。

阶段 1 只规范化质量、体积和计数三类单位：`G`、`ML`、`COUNT`。`个/株/盒` 等原始计数单位保留在 `unit_label`；无法安全换算的单位使用 `CUSTOM`，不做勺、杯、适量之间的推断换算。完整库存单位换算模型留到阶段 2 冻结。

未命中别名字典的原料，以清理空白和括号品牌说明后的名称创建 `UNREVIEWED` 规范项并记录 warning；禁止使用 LLM 自动合并原料。人工确认后通过别名迁移合并。

### 6.2 `retrieval` 模块拥有的表

| 表 | 关键字段 | 用途 |
|---|---|---|
| `recipe_search_document` | recipe_id、source_document_id、chunk_type、chunk_no、content、tsv、content_hash、embedding_model、embedding_dimension、embedding、embedding_status、indexed_at | 当前有效的 chunk 化检索冗余文档、中文全文索引和版本化向量 |

约束：

- `(recipe_id, chunk_type, chunk_no)` 唯一，每道菜可保存多个步骤块；
- 向量列固定为 `vector(1024)`；
- `content_hash` 未变化时不得重复调用收费 Embedding API；
- 查询只允许读取 `embedding_status=READY` 且模型、维度、文档版本与当前配置完全一致的记录；
- 查询必须同时执行可见性过滤：系统公开菜谱始终可见，用户私有菜谱仅对其所有者可见；
- 模型、维度或文档模板变化必须执行全量重建，不能把不同版本向量混在同一候选集合；
- `failure_message` 必须脱敏，不记录 API Key 或完整外部响应。

### 6.3 索引

- `recipe.name`：普通唯一/查询索引；
- `ingredient.canonical_name`、`ingredient_alias.alias_name`：唯一索引；
- `recipe_source(source_type, source_key) WHERE owner_user_id IS NULL`：系统来源部分唯一索引，避免 PostgreSQL 中 `NULL` 破坏唯一性预期；
- `recipe_source(owner_user_id, source_key) WHERE source_type = 'USER_CUSTOM'`：用户来源部分唯一索引，保证每个用户命名空间独立；
- `recipe_source_document(source_id, source_version)`：唯一索引，保证同一快照重复导入幂等；
- `recipe(source_id)`：唯一索引，保证一个来源只有一个当前结构化菜谱；
- `recipe_search_document.tsv`：GIN 全文索引，由 `zhparser` 自动生成；
- 阶段 1 不创建 HNSW/IVFFlat；先使用精确 cosine 距离并保存基准数据。

当数据量超过 10,000 条，或本地基准中向量候选查询 p95 超过 150ms，才创建新的 ADR 评估 HNSW。

## 7. Markdown 解析规则

### 7.1 稳定章节

解析器识别以下内容：

- 一级标题：菜名；
- 标题后的简介段落；
- `预估烹饪难度`；
- `预估卡路里`；
- `## 必备原料和工具`；
- `## 计算`；
- `## 操作`；
- `## 附加内容`。

分类来自 `dishes/<category>/...` 路径，不从正文猜测。

### 7.2 宽容策略

- 缺少菜名或操作步骤：该文件标记 `FAILED`，不生成可检索菜谱；
- 缺少难度、卡路里、份数或时间：菜谱仍可导入，相应字段为空并记录 warning；
- 数量、范围或单位无法标准化：保留 `raw_line`，结构化字段为空；
- 未知章节：保留在原始 Markdown，不自动丢弃；
- 单文件失败不得中止整个批次；
- HowToCook 同一路径和内容哈希在初始化重试时直接跳过；
- HowToCook 初始化成功后不再检查上游内容变化，也不自动升级快照；若未来确需升级，必须新增 ADR 和显式迁移任务；
- 后续用户自定义菜谱修改时追加 `recipe_source_document` 历史版本，更新原有 `recipe` 及子表，并触发索引重建，不创建新的 recipeId。

### 7.3 原料与工具区分

HowToCook 的“必备原料和工具”是混合列表。阶段 1 使用可版本化的厨具词典进行确定性分类；无法判定的条目先按原料保存并产生 warning，禁止调用 LLM 静默分类。

## 8. Embedding 文档模板

阶段 1 的检索文本模板版本为 `1`，按结构化字段构建四类 chunk：

```text
overview：菜名、分类、简介、难度、用时、份数、热量
ingredients：菜名、分类、规范原料列表
tools：菜名、分类、厨具列表
steps：菜名、分类、连续 3～5 个完整步骤
```

规则：

- 去除 Markdown 图片、HTML 注释和链接 URL；
- 保留链接显示文本；
- 合并连续空白；
- 单个步骤块不超过 4,000 字符；超长单步骤整体保留，禁止按字符截断烹饪动作；
- 入库使用 `text_type=document`，查询使用 `text_type=query`；
- 输出固定为 `dense`，阶段 1 不使用百炼返回的 sparse 向量；
- 普通测试使用 Fake Provider，不调用真实收费 API。

## 9. 混合检索算法

### 9.1 候选召回

1. 先执行分类、时间、厨具和排除原料等硬过滤；
2. 词法通道先按 `recipeId` 取最佳检索块，再召回前 30 道菜谱；先按匹配层级、再按分数排序：
   - 层级 0：菜名完全匹配；
   - 层级 1：原料规范名或别名完全匹配；
   - 层级 2：`tsv` 中文全文检索匹配；
   - 层级 3：菜名 `pg_trgm` 模糊匹配；
   - 极短查询优先精确匹配，必要时使用受限 `ILIKE`；
3. 向量通道用 `text_type=query` 生成查询向量，按 cosine distance 升序；先按 `recipeId` 取最近块，再召回前 30 道菜谱；
4. 使用 `1/(60 + lexicalRank) + 1/(60 + vectorRank)` 计算 RRF；未进入某通道的候选不计算该通道项；
5. 按 RRF 降序；分数相同时依次按词法匹配层级、词法分数、`recipeId` 升序稳定排序；
6. 截取最终前 10 条，并保留排名解释。

硬过滤必须分别作用于词法和向量候选查询，再进行各自的 Top 30 截断；禁止先召回再过滤，否则可能导致候选不足。

### 9.2 为什么不直接相加分数

trigram 相似度和 cosine distance 的数值范围及分布不同，直接相加会导致调参依赖当前数据集。RRF 只使用各通道名次，适合作为第一版稳定基线。

### 9.3 与熟悉技术的对应关系

| 熟悉方式 | 阶段 1 对应方式 |
|---|---|
| MySQL `LIKE` | PostgreSQL `ILIKE`，只用于极短查询或兜底 |
| MySQL 普通索引 | PostgreSQL B-tree 唯一/过滤索引 |
| MySQL 全文检索 | 当前中文场景以 `zhparser + tsv` 为主，精确匹配与 `pg_trgm` 补充 |
| 单一 SQL 排序 | 两路候选 SQL + RRF 融合 |
| DAO 查询 | MyBatis-Plus Mapper + XML 中显式的 pgvector/pg_trgm SQL |

## 10. 阶段验收标准

### 10.1 数据导入

- 固定版本快照可被完整扫描；
- 导入只能通过显式项目初始化流程触发，不存在定时任务、GitHub API 轮询或运行时自动同步；
- 至少 95% 的真实菜谱文件成功形成可检索菜谱；
- 每个文件都有来源路径、版本、SHA-256 和原始 Markdown；
- 初始化失败后使用同一快照重试不产生重复数据；初始化成功后不再把重复执行作为常规业务操作；
- 单文件解析失败不会回滚其他文件；
- 导入报告给出成功、跳过、warning、失败数量及失败路径。

### 10.2 Embedding 与索引

- 内容哈希未变化时不重复调用 Provider；
- 模型名、维度、文档版本和生成时间均可追踪；
- Provider 超时或限流时写入可重试失败状态；
- Fake Provider 下可稳定执行自动化测试；
- 不在日志和数据库错误字段中出现 API Key。

### 10.3 检索质量

- 建立至少 30 条固定评测查询；T6 当前候选数据集为 40 条，覆盖精确菜名、原料及别名、短中文/模糊、自然语言偏好、厨具、时间和排除原料；
- Hit@3 不少于 75%，Hit@5 不少于 80%；另报 Recall@5、MRR@10 和分组指标；
- 所有硬过滤约束违规数为 0；
- 本地完整数据集检索 p95 小于 300ms，Embedding 网络耗时另报；
- 每条结果能说明来自词法召回、向量召回或两者共同召回。
- 标签版本及整体审定范围必须随报告记录；整体认可不代表逐条审定记录。

## 14. 实现会话评审门禁

主架构会话验收 T1～T6 时，除任务自身验收标准外，还必须检查以下门禁：

### 14.1 架构边界

- Controller 未直接调用 Mapper；
- `retrieval` 未引用 `recipe` 的 Mapper、Entity 或 XML；
- 跨模块传递的是冻结 DTO 或事件，不是数据库实体；
- 除受控的 Spring AI `EmbeddingModel` 接口模块外，未引入 `VectorStore`、JPA、消息队列或其他阶段外框架。

### 14.2 数据与事务

- Flyway 迁移可在全新 PostgreSQL 上一次成功执行；
- `recipe_source` 保证系统来源和用户来源身份隔离，初始化失败重试不会生成新 recipeId；
- 每个菜谱文件独立事务，单文件失败不污染其他文件；
- 原始 Markdown、来源版本、内容哈希和解析 warning 可审计；
- HowToCook 不存在定时、实时、增量或 GitHub 上游自动同步代码；
- 三层数据职责清晰：原始文档不可丢、结构化事实可查询、检索投影可重建；
- 删除或更新子表时不存在旧原料、步骤和工具残留。

### 14.3 外部模型

- 普通自动化测试只使用 Fake Provider；
- DashScope API Key 不出现在日志、异常、测试快照或数据库错误字段；
- 超时、限流、返回维度错误均有明确状态和测试；
- 查询不会读取模型、维度或模板版本不匹配的向量。

### 14.4 检索正确性

- 硬过滤在各召回通道 Top 30 截断前执行；
- cosine distance 排序方向、NULL 向量和无向量降级有测试；
- RRF 公式及稳定排序与本文一致，没有针对评测样本硬编码；
- 评测报告同时列出质量、违规数和延迟，不只给出总通过结论。

任何一项门禁不通过，任务退回原实现会话修改；主架构会话不直接代写业务实现。
