## 2. 业务范围与分层

- 用户显式设置、读取和清空默认用餐人数；已有用户未设置时为null，不自动填2。
- 这是个人设置，不是模型记忆；不读历史聊天推断人数。
- 未来本餐显式人数优先、档案次之；U1只提供档案能力，不实现该餐单编排。
- 新增独立Service接口与impl；Controller仅调用Service，Mapper属于identity。复用当前认证用户，不接收客户端userId。
- 现有 `identity.vo.UserProfile` 已是 `{id,username}` 登录响应，必须原样保留。新档案使用不同类型，如 `DiningProfileView`，不能重名覆盖旧类型或改 `/users/me`。

## 3. 精确HTTP契约

| 方法 | 路径 | 请求 | 成功data |
| --- | --- | --- | --- |
| GET | `/api/users/me/profile` | 无 | `{ "defaultDiningCount": null或整数 }` |
| PUT | `/api/users/me/profile` | `{ "defaultDiningCount": null或整数 }` | 与GET相同，返回实际保存值 |

- 两种成功均HTTP200，沿用 `{code:"OK",message:"成功",data:...}`；个人信息响应 `Cache-Control: no-store`。
- `defaultDiningCount` 字段必须存在，显式null表示清空；`{}`、空body、顶层null、数组、未知字段均400 `VALIDATION_ERROR`。
- 非null只接受JSON整数；字符串`"2"`、小数`2.0`/`2.5`、布尔、对象/数组、0、负数、超过32位有符号整数范围均400；不得由Jackson自动截断或类型转换。拒绝未知字段包含`userId`，并测试数据未发生变化。
- 不擅自新增产品最大人数：当前为可表示的正32位整数。该技术范围不代表支持数十亿人组餐；后续餐单资源上限须另定，本次不承诺任意人数的生成能力。
- 未登录或无效身份沿用401；写请求CSRF不合法403 `CSRF_INVALID`。未登录PUT补有效CSRF测试身份401，另测缺CSRF403，不能误报安全过滤顺序。
- API不提供其他用户ID路径或请求字段。Service核验认证身份对应用户仍存在，失效账号不产生档案或回传他人数据。
- PUT为完整替换该单一设置，不是事件追加；重复相同值不新增行，清空可重复。无需新的requestId/事件表。并发不同值按数据库最后成功写入为准，不新增餐单CAS。
- 严格JSON校验只作用于该新接口/DTO，不能改变全局ObjectMapper或破坏旧接口。

## 4. 数据及内部接口

专属迁移：`V10__create_user_profile.sql`，本卡独占V10。V8/V9已在df67占用；禁止改写V1～V9、使用V8/V9做本任务迁移或开启out-of-order绕过版本顺序。

`user_profile`：

- `user_id BIGINT PRIMARY KEY REFERENCES app_user(id) ON DELETE CASCADE`：用户一对一，复用用户主键，不增加无用途的自增ID。
- `default_dining_count INTEGER NULL`，CHECK为null或大于0。
- `created_at`、`updated_at`：TIMESTAMPTZ、非空，数据库/服务端维护，客户端不提交。

GET无档案行返回defaultDiningCount=null，不创建记录。PUT使用参数化原子UPSERT；清空写null，保留最多一行。主键已承担用户查询索引，不新增重复索引。

新增 `UserDiningProfileService`（名称可等价），提供当前用户读写与供未来agent使用的显式用户读取接口；后一接口是内部可信调用，不开放任意用户HTTP查询。跨模块只返回专属DTO/值，不返回Entity/Mapper。内部读取不能在后台任务错误依赖线程SecurityContext，解释其信任边界。
