# D1-A 技术文档：解析规则与数据治理

日期：2026-10-07。教学依据为5b09实际代码和D1-A新人数策略v2执行证据；原R1为已被用户覆盖的历史规则。阅读本文件不代表已完成理解验收；最后自检需要亲手解释或演练。

## 1. 三层数据为何必须分开

原始层recipe_source_document保存原Markdown、来源版本和hash，是重解析依据。结构化事实层recipe/recipe_ingredient保存可查询名称、数量、单位、可选标志和原行；食材ID属于服务器事实，不由模型猜测。检索投影层recipe_search_document保存chunk和向量，是派生数据，不能把新事实搭配旧向量宣称READY。

D1-A只改善解析规则并输出比较提案。数据库中的旧事实仍然存在；旧餐单、指导、报价是历史快照，不随解析器升级自动改写。一个函数解析成功，只表示最低结构条件满足，不保证每个材料已标准化。

```mermaid
flowchart LR
  A[公开系统原文与旧事实] --> B[PG强制只读一致性快照]
  B --> C[同一个HowToCook解析器]
  C --> D[原行映射与语义比较]
  D --> E[manifest：applied=false]
  E --> F[人工审定与主架构复审]
```

这里没有数据应用、模型或索引重算箭头。

## 3. 为什么旧正则失败，怎样最小修复

旧AMOUNT要求“名称＋空格＋阿拉伯数字＋单位”。“小龙虾 = 2斤”的等号进入名称，“香叶 = 两片”“姜，13g。”不满足格式时整句降级为名称。导入器随后创建UNREVIEWED词典项，因此语法误读会传播到标准ID、材料和检索文本。

新规则先定位材料章节，再查找明确数量片段，最后独立清理名称尾部分隔符。逗号不是全局删除对象：“青葱，葱白”的部位必须保留。中文数字支持确定整数、小数、半单位；“二百五”省略位值、“一小把”不作为明确值。重复单位的范围与多个并列量分开：5g-10g有明确范围连词，2片，450g是不同量组。

主句数量与括号备注也分开。鸡蛋2个（约100g）保留2个，不推断鸡蛋密度；备注仍完整留在rawLine。原教程250g等备注不覆盖主句量。约10ml、10ml左右以及“100ml*份数”的动态公式不生成确定总量。遇到不能表达的新语义仍保留未知/待复核，而不是为减少null伪造值。

章节状态有工具区、可选区和必备区。计算区没有可靠用料列表时读取必备区，排除器具和标题；不从操作步骤收集量，因为其中可能是分批量、重复量或仅剩余量。工具排除词独立于旧工具投影，不扩大T5的厨具筛选事实。

多规格表格可能代表6寸/8寸/基准份的不同配方；桂林十八酿代表多种组合。现有一个recipe配一组材料的schema无法表达变体，本次不选择某列、不把所有候选拼成一张必买单，也不擅自增加schema。

## 4. 标准数量、标签与原文双轨

| 原文 | 结构化数量/编码/标签 | 原文保留/限制 |
| --- | --- | --- |
| 面粉1kg | 1000 / G / g | rawLine仍是1kg，不能再乘1000 |
| 水半升 | 500 / ML / ml | 不推断人数 |
| 料酒5mL | 5 / ML / ml | 大小写不是维度差异 |
| 盐10克 | 10 / G / 克 | 标签与数量一致，合法现存标签无需强制改成g |
| 小龙虾2斤 | 2 / CUSTOM / 斤 | 地域未冻结，不换成1000g |
| 香叶两片 | 2 / CUSTOM / 片 | 不变成克，不与瓣/根混加 |
| 黑鳕鱼2片，450g | null / 未选单位 | 保留名称部位与两组原量，待复核 |

金额和数量用BigDecimal：构造自十进制文本；用compareTo判断数值相同，避免1.0和1因scale不同误报；计算人数比例用既有6位HALF_UP且始终需要人工确认。manifest把数值写成普通十进制字符串，避免精度损失和科学计数法漂移。解析快照时启用USE_BIG_DECIMAL_FOR_FLOATS，不先读成double。

材料计算没有新增自动单位换算。它只兼容mL等大小写；原G/kg或ML/l错配仍拒绝参考折算。改变clearUnit让G/kg直接通过，会把1000kg这样的错误标签继续传播，甚至在采购端再次乘1000。正确位置是解析/受控事实治理，原历史对象必须保留。

## 5. 新人数策略：人、份、尺寸与整批产量

用户明确覆盖原R1的约人数/范围必须null策略；依据0f47《阶段D1-人数折算策略》。servings是材料参考比例的原菜谱基准，当前采用规则版本d1-a-parser-v2，保留原文及warnings依据，不表示精确食量或足量/自动采购承诺。

| 原人数表达 | 基准 | 预览依据 |
| --- | ---: | --- |
| 2人、两人 | 2 | EXPLICIT_PEOPLE |
| 约2人、每份（约 2 人份）、大概2人、2人左右 | 2 | APPROXIMATE_PEOPLE_AS_BASELINE |
| 2到3人、2-3人、二至三人 | 2 | RANGE_MIN_AS_BASELINE |
| 无人数、非法/倒置/冲突、份/产量/尺寸 | null | UNKNOWN_REQUIRES_REVIEW |

人数区间必须完整识别两个端点，转为正整数，并验证上限不小于下限，之后才取下限。2到3.5人、2到-3人、3到2人均未知；不能只验证2、不把倒置范围交换、不从末端3补出基准。二百五等位值不明确、分数/非整数和溢出仍拒绝。多个候选采用后的基准不同则冲突；同值重复可保留。

约量检查只看紧邻人数的前后缀，可识别空格、约为/大概可供、括号、人份左右/上下。“原料约50克，供2人食用”“2人食用，约20分钟完成”仍属于明确2人；材料约量和耗时不能污染人数。材料约量本身仍未知，斤/单位政策完全不变。

人数左边界防止从小数、分数、材料比率中截取尾数字。Markdown行首“- 2 人 1 顿”是列表项，仍解析2；“-2人”是非法数。真实217号半成品意面锁定了这个区别，并补充列表/序号正例。350号葱煎豆腐是动态份数材料比率，仍不充当确定总人数。

解析器先校验全部基准，成功后才向warnings发布“人数依据=APPROXIMATE_PEOPLE_AS_BASELINE”或“人数依据=RANGE_MIN_AS_BASELINE”的带版本标记，文字说明原约量/范围、采用值和人工确认边界。预览器读取同一解析器的标记，null优先未知；非null中范围标记优先于约量标记，其余为明确。这样不用改ParsedRecipe/ParsedIngredient，也不在预览器复制一套人数解析规则。若以后变更标记，必须同步依据回归，不能凭用户原文中的任意标签直接认定类型。

真实153/177/180/192均“每份（约 2 人份）：”，现在2/约人数依据；264“约为二人”同样为2。全量372道最新依据为明确47、约人数5、范围24、未知296。R1未知325→v2未知296，29道新恢复基准；与开发库旧快照310比较恢复16、转未知2。具体29个ID及前后依据可查v2-preview-verification.json，不以旧133项测试作为新策略证据。

基准与用户本餐人数分开。原文2到3人取2，目标3人参考比例是3/2；该结果仍需人工确认，不能拿用户目标人数补缺失原基准。份、蛋糕尺寸、整批饼数不换算成人数；未知不补1。本轮未修改材料计算或前端交互。

原R1拒绝约人数/范围的规则、325及其日志/报告保留在v2-before，初次D1-A证据另在r1-before；旧失败对应旧契约，不再作为新策略拒收依据。

## 6. 只读与可追溯预览如何成立

Spring的readOnly提示不能代替数据库保护。本次容器会话设置default_transaction_read_only=on，事务显式REPEATABLE READ READ ONLY；JDBC入口同时检查autoCommit=false、isReadOnly=true、隔离级别和PG事务状态。固定SQL是参数化PreparedStatement的SELECT，不访问账户表，没有FOR UPDATE，也没有插入/更新接口。结束ROLLBACK。

REPEATABLE READ让同一快照中的原文、旧用料和字典保持一致；这不代表读取后永远不会变化，将来D1-B仍要核对hash/规则版本/事实基线。20秒查询超时和2秒锁超时避免诊断无限等待。

preview验证原文SHA-256，再以rawLine和出现次序匹配旧用料ID。旧sort_order保留，parsedSortOrder单列；重复原行不共用ID，新增漏料的lineId为null而不是伪造。所有变化有原文hash、原始物理行、规则版本、旧/新字段和审定标识。2153个未变行比较完全相等，物理行映射缺失0。重复预览对同一快照输出一致。

52组尾等号同名只列所有旧ID和名称，不rename、不改外键、不删旧ID、不把UNREVIEWED标REVIEWED。候选标准ID来自精确词典名称，不按模糊名字推断酱油=生抽；未发现确定ID就保持待审定。

影响chunk候选仅用于后续核对。改材料名可能影响ingredients和overview；不能只重算ingredients，也不能立即重算全部1850向量。准确内容hash和费用数属于D1-C，本次保留所有旧投影与向量。

## 7. 与MySQL常见实现对照

| 常见MySQL做法 | 本项目对应及注意点 |
| --- | --- |
| DECIMAL存金额/数量 | PostgreSQL NUMERIC＋Java BigDecimal；原文和单位仍必须独立，DECIMAL不能解决语义错误 |
| UPDATE/TRIM/REPLACE批量清洗名 | 先纯解析和逐ID提案；全表rename可能撞唯一键或破坏历史引用，不能代替人工审定 |
| SELECT … FOR UPDATE | 用于关键写事务锁定；只读预览不需要行锁，PG READ ONLY下会失败25006 |
| 开只读事务作为报表 | 本任务同时固定一致性隔离和SQL边界，不能只依赖应用层readOnly标志 |
| JSON存诊断或快照 | PG JSONB保留诊断/历史；关键可查询事实仍在关系列，不把全部材料塞入JSON |
| 重建派生索引 | 本项目还有带版本/内容hash的向量；新文本配旧向量会制造不一致与额外收费 |

这些是概念对照，不是在本任务引入MySQL或替换既有数据库。

## 9. 面试追问与参考回答

1. **为什么不把所有null都补齐？** 原份数、缺失人数、配方变体等是原始信息不足，不是数据库缺字段。补1会错误影响人数折算、采购支出和预算承诺。
2. **清理逗号为什么危险？** 逗号既可能分隔数量，也可能描述葱白/带皮等属性。先识别数量片段，再清理名称边界，原始行始终保留。
3. **怎么防止kg二次换算？** 标准quantity/code/label同时转为1000/G/g，消费者只处理基准量；原1kg保存在rawLine，旧错配仍拒绝参考折算。
4. **BigDecimal.equals和compareTo有何区别？** equals比较值和scale，compareTo比较数值大小。语义diff用compareTo或规范十进制形式，避免1与1.0造成假变化。
5. **为什么需要数据库强制只读？** 应用标志或代码约定可能被绕过。PG READ ONLY真实拒绝写入和锁查询，结合固定SELECT、公开过滤和隔离测试更可靠。
6. **readOnly和REPEATABLE READ分别解决什么？** 前者限制写入，后者保证读取基线一致；两者都不能替代后续应用前的hash/版本复核。
7. **为什么不重新跑导入修复现有数据？** 同路径/版本SUCCESS会幂等跳过；伪造版本会破坏固定快照语义。治理要保留原ID和旧快照，必须是另外授权的受控应用任务。
8. **两个ID去掉等号后同名能直接合并吗？** 不能。唯一键、标准化状态、别名语义和历史/Mock引用都可能冲突；D1-A只建议并保留全部ID。
9. **多规格表格应如何处理？** 本次列诊断、保留原文，不选列。需要变体schema和明确选择语义时，应停在范围边界另行冻结契约。
10. **解析器修好为什么还不能说采购修好？** 开发库尚未应用，标准ID/人数/单位/城市与Mock目录覆盖还会限制采购；供应商请求和真人页面也未验。
