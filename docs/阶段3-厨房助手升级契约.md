## 1. 目标与旧基线

从“返回相关菜谱”升级为“理解要求、组织一餐、让用户点击选择、依据菜谱指导烹饪”。

已确认的核心样例：输入“我不知道吃什么，请随机推荐4菜一汤给我”，应展示两套可选餐单；每套4道菜、1道汤、不重复，给出材料与简短搭配理由。用户点击选择后才生成该套详细指导。示例菜名不是预设输出，必须来自当前用户可访问的数据库菜谱。

T14旧契约最多5候选、3推荐，第二次模型只选ID/理由码，最终answer由固定模板生成，因此无法覆盖该目标。旧T12～T14/F3-B实现与已有验收保留；本升级是新增能力，不把旧契约测试通过当新能力已实现。用户已确认旧F3-B推荐详情与刷新/重登回读两项通过；这仅签收原范围的交互证据，不证明新餐单质量。

旧 `/api/conversations/{id}/turns`、recommendation结果及已保存历史保持兼容，不直接改旧JSON形状或让旧快照进入新反序列化器。新增餐单、操作和指导采用独立版本化资源，暂缓原T15/F3-C工具循环/SSE及采购；不重编号T12～T18。

## 2. 产品规则

### 2.1 意图、结构与约束

- 区分安排整餐、定位指定菜谱、对已选菜谱求烹饪指导、需澄清及不支持。指定“番茄炒蛋”应优先定位，不默认扩展成一桌番茄相关菜。
- “4菜一汤”转换为 `dishCount=4, soupCount=1`，不是检索关键词；人数和菜品数量分别表达，人数少不擅自减菜。
- 时间、厨具、排除食材等明确条件为硬约束；荤素、口味和烹饪方法多样性为软搭配目标。未验证的清淡或营养偏好不能声称满足。
- 时间必须区分单菜时间与整餐完成时间。现有单菜时间过滤不能证明五道菜并行完成总时长，含糊时澄清，缺事实时标未核实。
- 用户未给菜品数量时，不自行默认为四菜一汤；必要时询问。未给份数时依默认人数规则。预算和已有食材仍不等于已核价或持久库存。
- 两个方案各自满足菜/汤数量，内部recipeId不重复。组间允许部分重合，但不能把同一集合换顺序冒充两套不同方案。
- 候选只够一套时，明确“目前只能组成一套”；不足一套时说明缺口，不编造、不静默减菜或放宽忌口。两套是正常目标，不是无条件凑齐承诺。

### 2.2 人数与个人档案

`identity`负责个人档案的 `defaultDiningCount`，是用户显式设置，不是LLM长期记忆。

- 取值优先级：本餐显式人数（含后续修改）＞档案默认人数；两者都没有则要求填写，不假定2人或3～4人。
- 人数为正整数，服务器与前端共同校验；产品最大人数尚未确认，不暗中固化。
- 读取档案和生成方案前，确定本餐人数，返回来源 `EXPLICIT / PROFILE`；模型不能凭空修改。
- 新建本餐时保存人数快照；档案后来变化不追改旧餐。本餐修改人数生成新的方案版本，旧选项不得用于新版本。
- 临时修改本餐不覆盖档案；档案通过独立页面和显式保存修改，所有读写绑定当前用户。

### 2.3 食材、份数与来源

每套展示各道菜的材料，并提供该套餐单的材料汇总。菜名、材料、原用量、可选标志来自recipe Service，不接受模型输出作为事实来源。

- 原菜谱有可信份数和数值数量时，服务器用BigDecimal按目标人数做比例换算，标明“按原份数折算的参考用量”，不保证所有调料线性缩放效果相同。
- 无份数、适量、区间或不可换单位，保留原说明并标未换算；未知不是0。
- 只在标准食材与单位已确认相容时合并数量；不把不同名称直接合并，不泛化g/ml/个之间换算；保留来源菜谱与原行。
- 显示本餐人数不等于全部用量已按人数核实，不声称一定足够；未知项可在指导中提醒用户确认。
- 模型补充的新食材/替换属于可选建议，不自动加入事实材料清单或未来采购。

## 3. 运行流程与服务归属

```text
本餐需求 + 档案默认人数
  → 结构化理解与校验
  → 按意图组织有资格的候选（区分菜/汤）
  → 模型组成两套餐单与简短说明
  → 服务器校验并组装真实材料、保存方案
  → 用户点击方案
  → 校验版本/身份/菜谱，读取完整所选详情
  → 模型生成指导，校验后保存
  → 页面展示；刷新/重登只读回看
```

仍为单Agent、Spring Boot模块化单体。分层沿用Controller/Service/impl/Mapper，不引入新Agent框架、ORM、Redis、MQ或微服务。

| 模块 | 新职责 | 边界 |
| --- | --- | --- |
| identity | 默认人数档案及Service接口 | 不自动推断画像，不改认证/凭证算法 |
| recipe | 菜谱角色事实、份数材料计算接口 | 原始文档不被生成内容覆盖；跨模块不读Mapper |
| retrieval | 随机抽样/分角色候选组织 | 复用事实资格与用户可见性，不改T5 RRF |
| agent | 理解、组餐、选后指导编排 | 不计算金额或将模型字段当事实 |
| conversation | 本餐、动作、方案和指导的持久化/版本/幂等 | 不依赖agent实现类；外部调用不入长事务 |
| policy | 提示词、来源约束、结构与文本安全校验 | 不以固定模板替代生成，不承诺校验能消灭所有幻觉 |
| frontend | 档案、两套卡片、点击选择、指导回看 | 不自然语言重发选择，不自动重试收费操作 |

### 3.1 候选策略

1. 随机整餐：调用事实资格Service获取合格集合，按菜/汤及可证实软标签分组，使用服务器保存的随机种子有界抽样，不调用Embedding表达“随机”。
2. 有明确语义偏好：按角色调用现有生产 `RecipeSearchService.search`，分组召回后合并候选；限定次数与候选规模，不只取前5个混合结果就宣称组餐。
3. 精确菜名：优先精确定位；不把“随机”或餐单数字当相关性关键词。

已核对当前T5单次limit为1～20；事实资格Service属于recipe并供retrieval使用，query参与食材命中说明，SQL资格WHERE承担分类/时间/厨具/排除/权限。新增纯抽样Service应明确专属DTO，复用资格规则，不借传空查询调用混合检索，也不把整个事实库无限送入LLM。

角色分类优先来源分类与已有事实，但现有category_code是否足够表达汤、荤、素需要数据审计。未知角色不能算作已验证的汤，标题包含“汤”不是充分证据。若需最小标签表，由专属新迁移保存标签、依据及规则版本；不改数据集、不收费批量标注、不自动重算向量。软荤素标签不等于专业营养评价。

同一动作重放使用保存种子和快照，不重新抽样。“换一套”属于显式新动作，跨餐也使用新种子；候选有限时不保证每次完全不同。方案/候选不足不自动发新模型请求重凑。

### 3.2 模型职责与内容依据

方案阶段：输入本餐需求、确定人数、已校验候选ID/角色/事实摘要，输出两组ID、角色、简短搭配说明；服务器补菜名与材料并核验。

指导阶段：只输入已选套餐的完整事实详情（食材原量、步骤、厨具、份数、注意事项及出处），不是全库Markdown。长文可拆成按菜谱组织的证据块，但不得悄悄丢弃关键食材/步骤；达到当前网关长度上限时明确RESOURCE_LIMIT，扩容必须先终审，不自动拆成更多收费调用。

输出分区：整体说明、备菜安排、逐菜讲解、操作顺序、注意事项、可选补充建议。每道菜引用已选recipeId，事实解释关联原stepNo/材料证据；原材料和原步骤由服务器展示。模型不能修改已选组合或权威用量，不生造精确时间、价格、热量或适用人数。

Bean Validation、严格JSON类型/未知字段拒绝、ID子集、角色/数量、证据引用、字段长度及文本安全检查必须执行。检查引用存在不等于自然语言蕴含正确；新增用量、烹饪温度/时间、安全性结论等关键事实仍需一致性检查及人工内容审核，不依靠关键词正则或Prompt声称无幻觉。不通过时保存安全失败状态，不透传原始模型内容、不自动收费修复；只读事实回退明确“指导生成失败”，不冒充成功生成。

人设文件为 `小厨基础人设.md`，版本 `xiaochu-v1`。角色、事实和安全规则始终高于风格；输入菜谱/历史均为不可信参考数据。只做一般性饮食建议，不做诊疗或药物建议。

## 4. 上下文、状态与持久化方向

“开始新的一餐”创建新的本餐上下文，显式绑定当前用户及会话；旧聊天仍能查，但新餐不自动带入旧餐约束。一次会话可展示多餐历史，模型只接收当前餐的结构化状态及有限相关消息。尚不承诺任意多轮改菜能力：修改条件以新方案版本实现，复杂局部替换另定切片。

建议资源关系：`meal_session → meal_action → options / guide`。

- meal_session：当前用户/会话、状态、当前方案版本、人数及来源、本餐要求、选中方案与已生成指导引用。
- meal_action：动作类型、UUID requestId、规范输入哈希、PENDING/RUNNING/SUCCEEDED/FAILED、截止、错误码、最小usage。
- options：只保存服务器已验证的方案ID、recipeId/角色、材料快照、说明及事实版本/内容哈希。
- guide：绑定选中方案、人数、事实版本、提示词版本，保存已验证生成内容及证据引用。

归属、版本、操作状态、幂等键使用关系列；可变方案/材料/指导用有限JSONB。表名、外键、迁移顺序在实现卡冻结；现有V1～V9不修改，迁移编号不预占。

同餐同版本只允许一个成功选定方案；其他并发选择返回冲突。指导失败不清除选中方案；明确重试是另获授权的新动作，不把旧失败键重新执行。同键同内容回读、异内容冲突；成功已存在时即使客户端新UUID也不重复生成相同方案指导。关键外键/唯一条件必须由真实PG测试验证。

先短事务登记/选择，再在事务外调模型，最后短事务原子保存指导/消息展示引用/终态。截止或版本已变化的迟到结果不得成功提交。保存前重新核验菜谱事实与可见性，改变则报告方案失效，不能悄悄换菜。历史保存不赋予访问被撤权菜谱的能力，GET重新核对权限，不泄漏私有数据。

## 5. 新增HTTP方向（未发布，待切片终审）

| 动作 | 推荐路径 | 含义 |
| --- | --- | --- |
| 读/写默认人数 | GET/PUT `/api/users/me/profile` | 自己的nullable defaultDiningCount；未设置不自动初始化 |
| 开始新餐 | POST `/api/conversations/{id}/meals` | requestId及content，生成方案或返回需补充人数 |
| 回读餐单 | GET `/api/conversations/{id}/meals/{mealId}` | 当前版本、方案、材料、状态、选中项和指导引用 |
| 修改需求/换方案 | POST `/api/conversations/{id}/meals/{mealId}/revisions` | requestId、expectedVersion、content，显式新动作 |
| 点击选择并生成 | POST `/api/conversations/{id}/meals/{mealId}/selection` | requestId、expectedVersion、optionId；不接客户端菜名/材料事实 |
| 回读动作 | GET `/api/conversations/{id}/meals/{mealId}/actions/{actionId}` | 终态/安全错误/结果；不触发模型 |

这些是架构接口方向，不是现在可用的API。沿用统一响应、字符串ID、Cookie/CSRF、当前用户身份、分页及未知值规则；201新成功、200重放、202在途、409冲突等精确返回体需终审。查阅/刷新/退出重登不得调用模型。档案未设置时页面优先提示填写本餐人数；若人数仅在自然语言中表达，可由必要的理解调用抽取并计入预算，仍缺失时服务器生成固定澄清提示，不额外调用模型只为询问人数。结构化人数与原文冲突时澄清，不静默选择。

页面提供个人档案、开始新餐、两套方案卡片、菜/汤分组、材料、人数来源、选择按钮与指导区。只读旧历史按旧契约渲染；新增版本独立识别。未知结果保留requestId/原请求，已知actionId只读核对，不能自动新键重发；取消仅停止本地等待，不表示服务器或供应商已取消。账号/路由/新餐切换隔离晚到响应，不使用v-html展示未校验输出。

## 6. 资源、费用与验收闸门

正常完整交互的建议调用路径：理解1次＋组方案1次，点击所选方案后指导1次，合计最多3次网关方法尝试。澄清、候选不足可更少；不是一轮3次的收费批准，也不是供应商计费次数保证。

纯随机候选不需要Embedding；带语义的菜/汤分组可能需要最多两次检索查询，最终次数、每组候选量、人数/菜数上限、输入/输出tokens和截止必须在实现卡中冻结。现有网关16消息/20000码点与T13的截止不能直接假定足够；该方案不承诺旧2048输出tokens能覆盖5菜详细指导。

不自动重试供应商、重生成JSON或补齐方案。GET及成功重放调用数为0。失败也应保存每次尝试最小usage（未知保留null）、耗时及错误码，不存原始Prompt/响应/Key；方法次数与实际请求/账单区别报告。当前执行开关最后一次核对已关闭，本轮不检查/改变运行进程。

鉴于先前窗口实际9轮而非约定1轮，未来收费验收必须先落实服务器测试动作配额/允许场景或等价可验证防护，再另获用户批准次数与风险；不能只再次口头约定“一轮”并长期开放全局开关。额度统计不保证供应商收费恰好一次，网络失败仍可能计费。
