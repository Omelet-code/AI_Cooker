## 1. 目标和依赖

从已选套餐读取可信材料，用户明确确认足量已有/需要购买与未知用量后，生成并保存缺口清单，可只读回看。T16不匹配商品、不提供虚构报价；价格未接入时保持未知。确认已有不等于持久库存，无自动扣减。

基线为5b09当前已验U1～U4和U5 R1～R5，V1～V12保留。使用Spring MVC、MyBatis-Plus、PG、Flyway和现有认证/CSRF，不新增框架。跨模块只依赖Service。

## 2. 来源读取及一致性

仅允许给conversation新增一个采购专用公共读取接口和其DTO，建议`MealPersistenceService.readShoppingSource(user, conversation, meal, version, option, lock)`。`lock`仅可信内部调用，不能来自HTTP。返回类型化的来源标识、人数/预算、所选方案完整材料快照、菜谱ID/事实指纹；不把通用Map暴露为新的采购HTTP契约。

只读取当前用户所属、当前版本、状态SELECTED且option与selectedOptionId一致的套餐；事实CURRENT、人数为已知正整数才允许新预览/创建。材料取该方案服务器保存的完整materials，不解析指导、模型摘要或前端事实。复核所选菜谱可见性及事实指纹，不能悄悄换成新事实。无需先生成指导，不能因读采购来源登记餐单动作、调用恢复或触发模型。

预览为无写读取；新创建在shopping事务内通过公共接口按既有conversation父行→meal顺序持锁，锁与新清单提交同属一个事务，避免餐单修订/选择与创建串版本。不跨模块访问Mapper。提交前复核所选事实；这不宣称数据库外修改或未来编辑流程下无条件串行化，后续菜谱写入口需要遵循独立一致性契约。

`sourceFingerprint`为服务器规范化来源摘要：含来源ID/版本/选项、人数/预算、所选菜谱指纹及完整材料语义；使用SHA-256和固定规范化规则，金额十进制表示差异不改变语义摘要，不含展示更新时间、模型指导或可变个人档案。它用于冲突检测，不替代认证/授权。未知/缺失/非当前材料安全失败，不猜测字段。

## 3. HTTP接口

复用项目统一响应/错误格式，schemaVersion=1；全部受登录保护，写入保留CSRF。HTTP ID为正整数字符串、版本为正整数、请求UUID必须合法；不接受客户端userId/原菜谱/商品价格/任意URL。

- `GET /api/conversations/{conversationId}/meals/{mealId}/shopping-preview?expectedVersion=…&optionId=…`：200，返回来源和可确认材料行；零写入/模型/Embedding。
- `POST /api/shopping-lists`：请求包含requestId、conversationId、mealId、expectedVersion、optionId、sourceFingerprint、confirmations。首次201，同键同内容200，返回完整清单。同步完成，无后台任务。
- `GET /api/shopping-lists/{id}`：200，只读历史清单。不提供T16更新、删除、商品匹配或自动重新生成接口；用户要改变确认结果需显式用新UUID创建新清单，旧清单保留。

预览`source`含conversationId/mealId/version/optionId/diningCount/budgetYuan/sourceFingerprint。`lines`每行含稳定`lineKey`（recipeId:recipeIngredientId）、recipeId、recipeIngredientId、ingredientId可空、name、rawLine、optional、originalAmountMin/Max可空、unitCode/unitLabel、referenceAmount可空、scaleStatus、reason可空、needsConfirmation。上述值来自服务器快照；完整原始材料和来源另保存在清单证据快照，不被确认值覆盖。

confirmations必须覆盖所有预览原料行且不重复、不混入其他来源：每项lineKey、availability（HAVE_ENOUGH或NEED_BUY）、可空confirmedAmount/confirmedUnitCode。HAVE_ENOUGH需明确足量确认，不从自然语言availableIngredientNames自动继承。可选原料保留optional标记并同样确认，T16不引入自动删料/替代料。

明确可靠且无需确认的referenceAmount直接作为需求量，不接受客户端覆写；只有needsConfirmation=true或折算不可用的行允许用户确认数量。允许未知继续以NEED_BUY保存，标QUANTITY_PENDING，不伪造0。HAVE_ENOUGH允许原需求量未知，采购缺口为已确认的0，不宣称原菜谱消耗量为0。填写数量必须同时填写单位且数值严格合法；反之两者均null。单位限原单位或明确同维转换，原单位缺失可显式选白名单单位；不得把个/把/袋换g、把g换ml，未知名称不由用户输入映射到其他标准食材。

数量输入仅普通十进制字符串，>0且≤1000000000、最多8位小数；拒绝JSON数字/科学计数法、NaN、负数及静默类型转换。已存在原事实不受输入上限改写；换算后超精度/范围保持待确认或明确400，不截断为0。换算仅g/kg、ml/l；其余相同且明确单位可保留，不额外推算密度。

响应`source`、`lines`保留逐菜材料/确认来源；`items`为采购汇总，含稳定行引用、标准食材ID可空、单位、requiredAmount可空、shortageAmount可空、状态HAVE_ENOUGH/NEED_BUY/QUANTITY_PENDING及原因。仅同一已确认标准ingredientId、兼容单位与optional语义相同的NEED_BUY确定用量可合并；未知量、未归一食材各自保留。缺口为0的已有项仍可回看，但不列入待采购项。

清单状态DRAFT（有待确认数量）或READY_FOR_MATCHING（待采购数量明确）；matchingStatus=NOT_MATCHED，商品/购买链接不输出虚构值。费用为currency=CNY、estimatedDemandCost=null、consumptionCost=null、purchaseOutlay=null，并列knownSubtotal=0.00、unknownItemCount及budgetStatus。只在没有任何待采购成本项（全部足量已有）时三金额可为0.00；不是未知价格当0。

budgetStatus为NOT_SET/UNKNOWN/WITHIN_BUDGET/OVER_BUDGET；未知项>0则有预算时UNKNOWN。已确认规则：超预算保留清单并提示，不自动换菜或放宽预算；未知只展示可估算小计和未知项，不承诺满足预算。T16公开链路没有报价，不能伪造超预算实价结果；T17接报价后补完整金额。

401未登录，403沿用CSRF；404资源不属于当前用户/不可访问；400 VALIDATION_ERROR；409 MEAL_VERSION_CONFLICT、MEAL_NOT_SELECTED、MEAL_BUSY、MEAL_FACTS_CHANGED、SHOPPING_SOURCE_CHANGED或SHOPPING_REQUEST_CONFLICT。供应商/模型无关异常不得作为错误原因。服务端和测试保持严格类型、未知字段/尾随JSON/重复键拒绝，不改共享解析配置来实现局部校验。

## 4. 持久化、幂等与历史

独占新增`V13__create_shopping_demand.sql`，派发前已核对5b09仅V1～V12；若实现开始发现V13已占用，停止报告，不改他人迁移或自行换序号。shopping_list及shopping_list_item使用BIGINT identity，与现有主键一致。关系列包含user_id、来源conversation/meal/version/option、request_id、input_hash、source_fingerprint、状态及时间；明细含行顺序、食材标识/单位/需求及缺口数量、确认状态。原行/确认/汇总来源和来源证据可以JSONB保存，核心归属/状态/数量不得全部藏在JSONB。

数量numeric(24,8)，预算/最终金额numeric(18,2)；纯成本计算中间保持BigDecimal充分精度，最终金额HALF_UP到2位。原始事实JSONB保留原精度/未知，不能为了列精度覆盖原数据。FK及CHECK/索引/删除策略在工作报告解释，保持既有conversation/meal/option归属一致，不只用全局ID证明来源。

`UNIQUE(user_id,request_id)`，input_hash规范化包括来源/版本/指纹和全部确认，确认数组按lineKey排序，数量按普通十进制语义规范化。同键同内容复用旧清单，优先于当前餐已修订的冲突判断；同键异内容409。使用唯一约束/受控原子插入应对并发，不仅靠前端按钮；不能在PG已失败事务中捕获唯一异常后继续查询。失败回滚无半份清单。

GET及重放重新核验用户和原菜谱可见性；若原菜谱不可访问返回404且不泄漏原文。如果当前事实已变化但仍可访问，保留历史数量/预算/确认快照，factsStatus=CHANGED；正常CURRENT。不因档案人数、当前选餐、事实或未来报价变化自动改写旧清单。所有写入与日志不涉及Key、Prompt、完整用户正文或供应商请求。
