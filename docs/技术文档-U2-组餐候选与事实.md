# U2：组餐候选与材料事实技术学习

日期：2026-10-03；kitchen-facts-v1 / meal-role-v1。工作树 5b09，基线 HEAD `4d7360d`；这是内部 Service 能力，不是两套餐单或指导生成的完整实现。

## 1. 代码归属和实际调用流

|层级|实际代码|职责|
|---|---|---|
|retrieval Service|MealCandidateService / impl.MealCandidateServiceImpl|验证请求、分角色抽样或调用既有T5、返回前复核|
|retrieval DTO|MealCandidateRequest / MealCandidateResult|模式、可信用户、资格条件、角色数量、种子、排名和不足|
|recipe Service|RecipeMealFactsService / impl.RecipeMealFactsServiceImpl|账号存在、资格池、权限边界、批量事实、指纹、材料|
|recipe 规则/计算|MealRoleRules / MealMaterialCalculator|版本化角色及纯BigDecimal参考量|
|recipe Mapper|MealFactsMapper / mapper/recipe/MealFactsMapper.xml|四种批量事实SQL，每条有可见性条件|

没有新增 Controller，因此不存在前端可任意指定 viewerUserId 的 HTTP 路径。未来编排必须先完成认证及任务归属，再调用可信内部接口。此服务仍通过 `UserDiningProfileService.readForUser` 核验账号存在，但不使用返回的默认人数，不依赖线程 SecurityContext，也不跨读 identity Mapper。

随机流：

```text
MealCandidateRequest(RANDOM, viewer, filter, roles, seed)
→ 参数/账号验证
→ 请求角色分类并集 ∩ 用户分类
→ RecipeMealFactsService.eligiblePool(filter, 1000)
→ 既有 RecipeSearchEligibilityService.eligibleRecipes
→ 完整ID集合超过1000则RESOURCE_LIMIT
→ 批量事实和角色 → ID排序 → 按角色种子shuffle → limit
→ 所有候选组完成后逐组recheck → 返回候选及shortage
```

语义流：

```text
SEMANTIC非空query（最多1000码点）
→ 每角色分类交集
→ 既有 RecipeSearchService.search（每角色一次，limit≤20）
→ 去重/事实角色过滤，保留T5顺序
→ 全部外部检索结束后recheck
→ 不足如实返回，不再次检索或补Embedding
```

材料流：`materials(viewer, 1～20唯一ID, targetDiningCount)` → 账号核验 → 四条批量 SQL → 整批可见性核验 → 当前事实指纹 → 逐行参考折算 → 按严格标准键汇总/待确认。任一不存在或无权菜谱统一 `RECIPE_NOT_FOUND`，不返回部分菜谱。

## 2. 随机与相关检索的区别

RANDOM 是从满足硬条件的完整资格池抽样，不衡量文本相关性。基于稳定 recipeId 顺序、种子及角色独立常量调用 `Collections.shuffle`，同输入、种子、事实版本可复测。不同种子允许重合，候选数量是池规模，并非本餐菜数。

SEMANTIC 把实际语义交给已有生产 T5，保留 lexicalRank/vectorRank/rrfScore/rank 和命中依据。U2 不读取 retrieval Mapper，不改 RRF。汤分类中的粥被角色规则剔除后，即使剩一条也不再发一次检索。

用户分类不能被角色范围覆盖。比如用户仅允许 soup，DISH 交集为空，直接返回空组；不能把空 IN 列表送既有SQL，因为既有空分类列表表示“无分类限制”。RANDOM 将两角色分类求并集后只读一次池，1000上限作用于总池，不允许每组各1000后合成2000。

## 3. SQL资格与批量可见性

硬条件复用原资格 SQL：最长时间、是否包含未知时间、必需厨具、食材标准名/原名/别名排除、系统公开/本人私有。`availableToolNames=null` 不限制厨具，`[]` 表示没有可用厨具，只能选没有必需厨具的菜谱。未知时间只有满足原查询选项时才能参与，不能改成0。

新增事实SQL每条都包含以下边界，并使用 MyBatis `#{}` 参数绑定：

```sql
((s.source_type = 'SYSTEM_HOWTOCOOK'
  AND s.owner_user_id IS NULL AND s.visibility = 'PUBLIC')
 OR (s.source_type = 'USER_CUSTOM'
  AND s.visibility = 'PRIVATE' AND s.owner_user_id = #{viewerUserId}))
AND r.id IN (...参数化ID...)
```

四个查询分别读菜谱/源文档、原料及标准化状态、步骤、厨具。材料和步骤按菜谱及排序字段稳定排序，厨具按ID排序，Java按recipeId分组；没有每个原料再查询标准名称的循环。`MealFactRows` 仅用于本模块 Mapper；跨模块返回的是 `MealRecipeFacts`。

池上限是 SQL 返回后的应用检查，不是数据库扫描硬上限。本切片没有新增分页、SQL LIMIT、导入或迁移，不能宣称超过1000的数据库绝不会被扫描。

## 4. 事务与返回前复核

候选入口 `@Transactional(propagation=NOT_SUPPORTED)` 会挂起调用方事务，T5可能等待Embedding时不持有该事务。事实读取、资格池与复核使用 `REQUIRES_NEW + REPEATABLE_READ`：每次都是独立短事务，四条事实SQL看到一致快照，复核不会复用外部调用之前的旧事务快照。

这里没有声明 `readOnly=true`，因为所复用的身份公开接口使用 `SELECT ... FOR KEY SHARE` 防止核验期间账号删除；PostgreSQL只读事务不允许该锁。U2不写业务数据，短事务结束即释放账号锁。

复核再次执行原资格Service，读取可见事实并比较指纹。删除、转为他人私有、资格不符、结构化事实或角色变化的旧候选会被剔除，输出不足；不补选。第二组检索期间第一组变化的真实PG测试证明复核放在全部外部等待之后。

这不是永久有效快照，也不可能承诺返回后数据库不再变化；U3/U4最终使用前仍需复核。多组短事务不构成跨组永久原子快照。

## 5. 角色依据与源版本

`meal-role-v1.properties` 提供 category→role。`meal-role-v1-exceptions.tsv` 按系统 sourceKey＋category＋源哈希记录5个粥例外及依据。系统例外哈希失配→UNKNOWN，不回退汤；私有同路径不应用系统例外。原文审计及372文件分母见 `数据审计-U2-菜谱角色.md`。

源文档ID/哈希用于追踪原Markdown；`factFingerprint` 另对稳定排序的事实DTO（指纹字段为空）做固定结构JSON序列化及SHA-256，包含材料原行/量/标准状态、步骤、厨具、份数、时间、分类、角色版本/依据和补充原文。因此即使Markdown哈希没变，当前数据库材料、步骤、厨具或份数改变也会失效。这个指纹是内容一致性校验，不是签名或权限凭证。

## 6. BigDecimal参考折算与汇总

实际表达式位于 `MealMaterialCalculator.scale`：

```java
BigDecimal reference = item.amountMin().multiply(BigDecimal.valueOf(target))
    .divide(BigDecimal.valueOf(servings), 6, RoundingMode.HALF_UP);
```

前置条件：servings>0、min/max都存在且相等、非负、单位代码与标签明确匹配。结果状态 REFERENCE_SCALED，原字段原封保留，needsConfirmation=true。1只供3人、目标2人得到0.666667只，不自行取整。调料线性比例只供参考。

份数未知、适量或异常量输出 UNKNOWN；区间、单位未知/不一致输出 ORIGINAL_ONLY，referenceAmount 为 null，并给中文原因；未知不是0。已存量为0且符合其余条件时可以得到0，因为这是明确的原值。

既有解析器把kg/L转成G/ML数值，但仍保留kg/L标签。U2同时保留结构化数值和rawLine，不重新解释导入事实；这类代码/标签不一致条目不折算、不合并，进入待确认。新增的规范KG/kg、L/l事实可单独折算，但本服务不做任何跨单位转换。

汇总键严格是 `(REVIEWED ingredientId, unitCode, unitLabel, optional)`。同ID的G/g和G/克仍分别输出；G/kg、G/ML、COUNT/G也不合并；可选与必需分开。未确认标准ID或范围/未知量逐来源留在 pending；已确认项的汇总保留每条 recipeId、recipeIngredientId 和参考量。summaryStatus 只表达参考及待确认状态，不声称数量准确或一定够吃。

## 7. Spring Boot + MySQL经验对照

你熟悉的 Controller→Service→Mapper 在这里仍成立，只是U2暂无Controller入口。DTO是业务输入/结果，Mapper行是持久层临时对象；跨模块必须调用Service，不能为了少一层去查别人的Mapper。

MySQL项目中用 `WHERE user_id=?` 限定用户的思路，在这里扩展为“公开系统或当前用户私有”的每SQL谓词；仅验证首个查询不够。`IN` 批量读与Java分组避免N+1，同样适用于MySQL。

PostgreSQL REPEATABLE READ 使用事务快照；我们额外用 REQUIRES_NEW 保证返回前复核的新快照，不依赖数据库默认隔离级别。MySQL事务隔离也需要理解一致性读和锁读差别，不能把实现细节完全照搬。`FOR KEY SHARE` 是PG锁语义，不能简单换成MySQL同名语法。

NUMERIC与Java BigDecimal对应金额/数量的十进制表达，避免double二进制误差；SQL存原事实，Java处理参考量和严格合并规则。这里不涉及金额、购物或库存扣减。

## 8. 面试追问（含答题方向）

1. 为什么随机任务不调向量？回答资格与相关性的区别，以及零模型成本和可复测。
2. 为什么先排序再shuffle？回答数据库返回顺序未保证时，固定种子也不稳定。
3. 池上限能避免大SQL扫描吗？不能；上限在返回后，明确应用内存与扫描边界不同。
4. 为什么厨具null和空列表不同？缺省不限制与确认没有厨具是两种需求。
5. 为什么检查源哈希还不够？结构化材料可能独立修改，指纹必须包含真实事实。
6. 为什么Embedding等待不能持有事务？长连接/锁及旧快照会增加资源占用和一致性问题。
7. REQUIRES_NEW与NOT_SUPPORTED各做什么？一个挂起旧事务后开短新事务，另一个在事务外执行外部等待。
8. 为什么不用double或divide默认实现？精度及无限循环小数，需要固定scale和舍入规则。
9. 同食材ID就能合并吗？还需REVIEWED、代码/标签及optional完全一致，不能单位换算。
10. 为什么无权与不存在返回同类错误？避免泄漏他人菜谱存在性，整批安全失败。
