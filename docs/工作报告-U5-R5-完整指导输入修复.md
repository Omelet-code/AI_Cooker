## 7. 教学：为什么这样修

原始事实、结构化事实和模型输入是三个层次。原文与解析出的材料/步骤负责出处与权威事实；模型输入可以改变组织方式，前提是可恢复所有事实。例如一份原材料放在 `recipes[recipeId].ingredients[recipeIngredientId]`，折算条目只引用两个 ID，并保留自己的参考量与未知提示。这样省掉复制，不会省掉食材。

引用去重与摘要截断不同：去重可逐字段还原原对象；摘要难以证明最后一步、未知单位或出处没有丢失。本轮测试真的把紧凑材料还原并与展示材料全树比较，避免只检查字段名是否存在。

Unicode 码点与 Java 字符、UTF-8 字节、token 也不同。一个 😀 在 Java UTF-16 中占两个 char，但只算一个码点；UTF-8 通常占四字节，token 数还由模型 tokenizer 决定。因此消息上限按 codePointCount，快照边界按字节，供应商用量按响应 usage，三者分开。所有系统消息也必须计入输入。

专用档位是服务端固定入口 completeGuide 的权限边界，普通推荐仍走旧档位。不能只改 Service：网关仍会拒绝大请求；也不能只改网关：Service 会在网络前拦截。共用常量和计数函数可避免再次分叉。

小夹具只验证业务规则，覆盖不了五菜长输入这个风险。既有“1克、短步骤”会同时绕过输入总长、材料重复与字节边界，因此新夹具加入多步骤、多原料、未知折算和 pending/source，走真实创建、选择、指导与落库链路。

## 8. 面试问答与自检

1. **如何证明引用去重无损？** 原对象不变，引用可归属解析，逆向恢复材料后与原完整材料做全树相等比较；并检查全部菜谱节点及原步骤仍在输入。
2. **为什么保留 full materials 给校验器？** 校验器原来使用 original 原料及参考量判断数值，紧凑输入是传输组织方式，不能悄悄改变权威事实或输出校验语义。
3. **为什么不是直接放大全局上限？** 普通请求与完整指导的工作量不同。固定专用入口扩大指导输入预算，可保留普通推荐的既有资源边界；所有请求仍有总输入硬上限。
4. **为何系统 Prompt 必须一起计数？** 模型实际接收所有消息，遗漏系统消息会让应用允许的请求越过真实输入边界，也使 64000/64001 测试失真。
5. **为何超限不能自动重试？** 相同完整输入不会因重复请求变短，自动追加会造成收费与幂等风险。应在模型前安全失败，保留选择，原失败键只回读。
6. **如何区分输入超限与时间超限？** RESOURCE_LIMIT 是公共稳定错误码，日志用受控原因、阶段、actual/max 计数细分输入超限；时间失败不打印 INPUT_LIMIT。
7. **为什么新 Prompt 版本要在数据库列和快照里一致？** 版本是复现与追踪依据。新指导实际用 v2 而元数据写 v1 会误导排障；从服务器生成的 view 提取版本可保持一致，旧历史无需迁移。
8. **隔离构建为什么不只隔离 Jar 名称？** 编译会先更新 classes，IDE 可能读到半更新文件；测试还会写相对路径。必须同时隔离 classes、test-classes、resources、报告、工作目录和最终 Jar。

自检：能解释按 recipeId/recipeIngredientId 找到原材料；能指出未知量为何不能当零；能计算非 BMP 的码点与 char 数差别；能说明此修复为何不改变事实指纹、旧历史与模型输出结构；能复述独立回归通过与真实部署/模型质量签收之间的区别。

新增学习点：可逆输入投影、服务端固定资源档位、Unicode 多种计数单位、安全结构化诊断、Prompt 版本溯源，以及 IDE 运行 classes 时的构建隔离。
