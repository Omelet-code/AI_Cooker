# Cooker 菜谱导入数据库说明

> 范围：阶段 1 T1～T3 已实现的 HowToCook 原始 Markdown 与结构化事实导入。  
> 不包含：`recipe_search_document`、Embedding、pgvector、pg_trgm、词法检索和混合检索。

## 1. 为什么要同时保存原文和结构化数据

HowToCook 的菜谱以 Markdown 维护，阅读友好但不便于按原料、厨具、时间等条件查询。系统将每份文档拆为两层：

```text
固定快照 Markdown
  ├─ 原始数据层：完整 Markdown、来源路径、版本、SHA-256、解析诊断
  └─ 结构化事实层：菜谱主体、原料、工具、步骤
```

原文层确保上游格式存在历史差异时仍可审计、重放和改进解析器；结构化层提供后续业务查询所需的关系字段。当前阶段不创建检索投影，后续由 `retrieval` 模块独立拥有。

## 2. 结构化依据与解析技术

### 2.1 数据依据

解析遵循 HowToCook 兼容模板和冻结架构规则，而不是让 LLM 推断：

| 字段或事实 | 提取依据 |
|---|---|
| `name` | 一级标题 `# 菜名的做法`，移除末尾“的做法/做法” |
| `category_code` | 相对路径首级目录，例如 `aquatic/红烧鲤鱼.md` 的分类为 `aquatic` |
| `summary` | 一级标题后、首个二级标题前的首个有效文本段落 |
| `difficulty` | `预估烹饪难度：★★★★` 中的实心星数量 |
| `calories_kcal` | `预估卡路里：815 大卡` 中的数值 |
| `servings` | `## 计算` 内的“n 人”表达；范围只保存下限并产生 warning |
| `estimated_minutes` | 简介或计算内容里的小时/分钟表达，统一为分钟 |
| 原料与数量 | `## 计算` 下的项目符号；数量解析为最小值、最大值、单位和原始行 |
| 工具 | `## 必备原料和工具` 下的项目符号，使用可版本化的确定性厨具词典识别 |
| 步骤 | `## 操作` 下的有序 Markdown 列表 |
| 附加内容 | `## 附加内容` 的文本 |

### 2.2 技术实现

- Java 21、Spring Boot 4、MyBatis-Plus、Flyway 和 PostgreSQL 18。
- `HowToCookMarkdownParser` 是纯内存、无数据库依赖的确定性解析器，使用 Java `Pattern` 正则、标题分段和有序列表识别。
- 解析前删除 HTML 注释与独立图片行，避免模板说明和图片 URL 污染事实字段。
- 数量使用 `BigDecimal`，数据库使用 `numeric`；不使用浮点数。
- `g/kg` 统一以 `G` 表示，`ml/l` 统一以 `ML` 表示；原始显示单位仍保留在 `unit_label`。`个/只/根/瓣` 等计数单位使用 `COUNT`；勺、杯、盒、斤等不安全换算单位使用 `CUSTOM`。
- 解析不调用 DeepSeek、百炼或任何其他模型。

### 2.3 宽容解析与失败条件

缺少菜名或没有可识别的操作步骤时，文档状态为 `FAILED`，不会创建 `recipe` 及子表记录。缺少难度、热量、份数、时间，或无法标准化数量/单位时，原文仍会导入，结构化字段允许为空，并在 `parse_warnings` 中保存诊断。

## 3. 表说明

### 3.1 字段字典

以下字段以当前 Flyway `V1` 为准；所有表名和数据库字段名均采用 `snake_case`。

#### `recipe_import_batch`：导入批次审计

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `bigint identity` | 导入批次主键 |
| `source_type` | `varchar(32)` | 来源类型；当前为 `SYSTEM_HOWTOCOOK` |
| `source_version` | `varchar(128)` | 固定快照版本标识，例如 `1.6.0-a0b14bd` |
| `status` | `varchar(32)` | 批次状态：`RUNNING`、`COMPLETED` 或 `COMPLETED_WITH_FAILURES` |
| `candidate_count` | `integer` | 扫描到且未被 `template` 路径排除的候选文件数 |
| `succeeded_count` | `integer` | 成功形成结构化菜谱的文件数 |
| `skipped_count` | `integer` | 因同来源、同版本快照已成功导入而跳过的文件数 |
| `warning_count` | `integer` | 本批次累计的宽容解析与标准化 warning 数 |
| `failed_count` | `integer` | 解析或落库失败的文件数 |
| `error_summary` | `jsonb` | 预留的批次级异常摘要 |
| `started_at` | `timestamptz` | 批次开始时间 |
| `finished_at` | `timestamptz` | 批次结束时间；运行中可为空 |

#### `recipe_source`：菜谱来源身份

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `bigint identity` | 来源主键 |
| `source_type` | `varchar(32)` | `SYSTEM_HOWTOCOOK` 或后续的 `USER_CUSTOM` |
| `source_key` | `varchar(1024)` | 来源内稳定路径或业务键；系统菜谱为相对 Markdown 路径 |
| `source_uri` | `text` | 可追溯来源位置；当前保存相对路径 |
| `owner_user_id` | `bigint` | 自定义菜谱所有者；系统来源必须为空，阶段 1 尚未加身份模块外键 |
| `visibility` | `varchar(32)` | 可见性；系统来源固定为 `PUBLIC`，自定义来源预留为 `PRIVATE` |
| `created_at` | `timestamptz` | 来源首次创建时间 |
| `updated_at` | `timestamptz` | 来源最近更新时间 |

#### `recipe_source_document`：原始 Markdown 与解析诊断

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `bigint identity` | 原文版本主键 |
| `source_id` | `bigint` | 所属 `recipe_source.id` |
| `source_version` | `varchar(128)` | 该原文对应的来源版本 |
| `content_hash` | `char(64)` | 原始 Markdown 的 SHA-256 十六进制摘要 |
| `raw_markdown` | `text` | 完整未截断的原始 Markdown |
| `parse_status` | `varchar(32)` | `SUCCESS` 或 `FAILED` |
| `parse_warnings` | `jsonb` | 解析未失败但无法完整结构化的诊断列表 |
| `failure_message` | `text` | 硬失败原因，例如缺少菜名或操作步骤；成功时为空 |
| `import_batch_id` | `bigint` | 最后处理该原文的 `recipe_import_batch.id` |
| `imported_at` | `timestamptz` | 原文记录创建时间 |

#### `recipe`：当前结构化菜谱主体

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `bigint identity` | 菜谱主键 |
| `source_id` | `bigint` | 所属来源；唯一约束保证一个来源只有一条当前菜谱 |
| `source_document_id` | `bigint` | 生成当前事实的原文版本 |
| `name` | `varchar(255)` | 菜名 |
| `category_code` | `varchar(128)` | 路径首级目录解析出的分类编码 |
| `summary` | `text` | 菜名后的简介段落；可为空 |
| `difficulty` | `integer` | 预估难度 1～5；可为空 |
| `estimated_minutes` | `integer` | 预估制作分钟数；可为空 |
| `servings` | `integer` | 份数；范围表达当前保存下限；可为空 |
| `calories_kcal` | `integer` | 预估卡路里（千卡）；可为空 |
| `additional_content` | `text` | 附加说明、注意事项和参考链接文本；可为空 |
| `created_at` | `timestamptz` | 菜谱主体首次创建时间 |
| `updated_at` | `timestamptz` | 菜谱主体最近更新时间 |

#### `ingredient` 与 `ingredient_alias`：原料标准化

| 表 | 字段 | 类型 | 含义 |
|---|---|---|---|
| `ingredient` | `id` | `bigint identity` | 规范原料主键 |
| `ingredient` | `canonical_name` | `varchar(255)` | 清理空白及括号说明后的规范名称，全局唯一 |
| `ingredient` | `normalization_status` | `varchar(32)` | `UNREVIEWED` 待人工确认，或 `REVIEWED` 已确认 |
| `ingredient` | `created_at` | `timestamptz` | 规范原料创建时间 |
| `ingredient_alias` | `id` | `bigint identity` | 别名主键 |
| `ingredient_alias` | `ingredient_id` | `bigint` | 指向规范原料 |
| `ingredient_alias` | `alias_name` | `varchar(255)` | 原始别名，全局唯一 |

#### `recipe_ingredient`：菜谱用料事实

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `bigint identity` | 用料记录主键 |
| `recipe_id` | `bigint` | 所属菜谱；删除菜谱时级联删除 |
| `ingredient_id` | `bigint` | 已规范化的原料；极端异常时允许为空 |
| `raw_name` | `varchar(255)` | 从 Markdown 解析出的原始原料名称 |
| `amount_min` | `numeric` | 数量下限；无法安全解析时为空 |
| `amount_max` | `numeric` | 数量上限；单值时与下限相同 |
| `unit_code` | `varchar(16)` | 结构化单位：`G`、`ML`、`COUNT` 或 `CUSTOM` |
| `unit_label` | `varchar(64)` | Markdown 中的原始单位显示文本，例如 `g`、`个`、`盒` |
| `optional` | `boolean` | 是否由“可选/选用”文本明确标记为可选 |
| `raw_line` | `text` | 完整原始用料行，供诊断和后续重新解析 |
| `sort_order` | `integer` | 用料在原文中的顺序；同一菜谱内唯一 |

#### `cooking_tool` 与 `recipe_tool`：厨具事实

| 表 | 字段 | 类型 | 含义 |
|---|---|---|---|
| `cooking_tool` | `id` | `bigint identity` | 厨具主键 |
| `cooking_tool` | `canonical_name` | `varchar(255)` | 厨具词典名称，全局唯一 |
| `recipe_tool` | `recipe_id` | `bigint` | 所属菜谱；联合主键第一部分 |
| `recipe_tool` | `tool_id` | `bigint` | 所需厨具；联合主键第二部分 |
| `recipe_tool` | `optional` | `boolean` | 是否为可选厨具 |

#### `recipe_step`：操作步骤

| 字段 | 类型 | 含义 |
|---|---|---|
| `id` | `bigint identity` | 步骤主键 |
| `recipe_id` | `bigint` | 所属菜谱；删除菜谱时级联删除 |
| `step_no` | `integer` | 步骤顺序，从 1 开始；同一菜谱内唯一 |
| `content` | `text` | 步骤正文；有序列表的续行会拼接到所属步骤 |

### 3.2 导入审计与来源原文

| 表 | 作用 | 关键字段与约束 |
|---|---|---|
| `recipe_import_batch` | 每次显式导入或重试的审计记录 | `source_type`、`source_version`、状态及候选/成功/跳过/warning/失败统计，时间使用 `timestamptz` |
| `recipe_source` | 菜谱来源的稳定身份 | 系统来源使用 `SYSTEM_HOWTOCOOK`、公开可见、无所有者；系统来源 `(source_type, source_key)` 部分唯一 |
| `recipe_source_document` | 一个来源版本的完整原文与解析结果 | `raw_markdown text`、`content_hash SHA-256`、`parse_status`、`parse_warnings jsonb`、`import_batch_id`；`(source_id, source_version)` 唯一 |

### 3.3 当前结构化菜谱事实

| 表 | 作用 | 关键字段与约束 |
|---|---|---|
| `recipe` | 每个来源当前生效的菜谱主体 | `source_id` 唯一；保存名称、分类、简介、难度、分钟、份数、热量、附加内容 |
| `ingredient` | 原料规范项 | `canonical_name` 全局唯一；当前未人工确认的项标记为 `UNREVIEWED` |
| `ingredient_alias` | 原料别名 | `alias_name` 全局唯一，关联到规范原料 |
| `recipe_ingredient` | 菜谱用料清单 | 保存原料、数量范围、单位、是否可选、未丢失的 `raw_line` 与稳定排序；`(recipe_id, sort_order)` 唯一 |
| `cooking_tool` | 规范厨具词典项 | `canonical_name` 全局唯一 |
| `recipe_tool` | 菜谱和厨具的多对多关系 | `(recipe_id, tool_id)` 联合主键，记录是否可选 |
| `recipe_step` | 菜谱操作步骤 | `step_no` 和内容；`(recipe_id, step_no)` 唯一 |

```text
recipe_import_batch ──< recipe_source_document >── recipe_source ──1 recipe
                                      │                              ├─< recipe_ingredient >── ingredient ─< ingredient_alias
                                      └─ 导入批次审计                 ├─< recipe_tool >────── cooking_tool
                                                                     └─< recipe_step
```

## 4. 导入、事务与幂等

1. 只有同时启用 `recipe-import` profile 和 `cooker.recipe-import.enabled=true` 才能运行导入；普通应用启动不会扫描本地快照。
2. 导入器递归扫描传入的数据路径，以路径分段语义排除任意名为 `template` 的目录。
3. 读取文件、计算 SHA-256、解析 Markdown 都在数据库事务外执行，避免文件 I/O 长时间占用事务连接。
4. 每个文件由 `RecipeImportFileService` 在独立事务中写入。单文件异常回滚该文件的来源、原文和结构化事实，但外层批次继续处理后续文件。
5. 同一来源路径与来源版本已存在成功文档时，重复执行只计为 `SKIPPED`，不会重复创建菜谱或子表记录。系统快照成功后不会自动检查或同步上游变化。
6. 解析失败的原文仍写入 `recipe_source_document`，下次同一快照可在解析器修复后重试。

## 5. 本机实际导入记录

在 PostgreSQL 18 的 `cooker` 数据库中，Flyway `V1` 已成功执行。固定 HowToCook `1.6.0-a0b14bd` 快照的首次导入结果如下：

| 指标 | 数量 |
|---|---:|
| 候选 Markdown | 372 |
| 成功结构化菜谱 | 372 |
| 跳过 | 0 |
| warning | 2321 |
| 失败 | 0 |
| 原始文档 | 372 |
| 原料事实 | 3025 |
| 操作步骤 | 3511 |
| 厨具 | 25 |

随后执行的同一快照重试批次结果为：成功 0、跳过 372、失败 0；上述原文、菜谱、原料和步骤总数均未增加，验证了当前快照导入的幂等性。

## 6. 运行配置与安全注意事项

数据路径、数据库 URL、用户名和密码均通过命令参数或环境变量提供，代码和默认配置不硬编码本机路径或数据库凭据。生产环境不得继续使用本地开发账号和弱密码，应改为受限数据库用户与 Secret 注入。
