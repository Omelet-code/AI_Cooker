# U3 技术学习：餐单、版本与点击选择

日期：2026-10-04。以本树实际代码和 kitchen-meal-v1 为依据。阅读本文件并不等于已经掌握；建议先顺着一次创建请求读代码，再练习并发和失败路径。

## 1. 从熟悉的 Spring Boot/MySQL 分层开始

`MealPlanningController` 接收原始 JSON，通过 MealPolicy.parse 与 MealHttpRequest.parse 验证类型，再调用项目自己的 MealPlanningService。`MealPlanningServiceImpl` 编排理解、候选和材料；`MealPersistenceServiceImpl` 管理事务与版本；`MealMapper` 保存 PostgreSQL 数据。这仍是 Controller→Service→Mapper。区别在于编排 Service 调用其他模块公开 Service，不能直接查 recipe/identity Mapper。

生产请求流为：

```text
认证 Cookie / CSRF
  → MealPlanningController / 严格请求解析
  → MealPlanningServiceImpl.submit
      → U1 人数档案（仅新餐）
      → MealPersistenceService.register / start（短事务）
      → ModelGateway：理解 changes（无数据库事务）
      → MealPolicy：需求合并、人数冲突、澄清
      → U2 MealCandidateService：RANDOM 或 SEMANTIC
      → ModelGateway：只选择候选 ID 和说明
      → RecipeMealFactsService：资格复核、完整材料
      → MealPersistenceService.complete（短事务原子落库）
  → MealActionView，终态来自数据库
```

缺人数/数量或时间歧义在理解后停止；无足够候选在组餐前停止。选择路径只有身份→参数→父锁/版本/资格→保存选择，不再走模型。旧 chat_message 与 conversation_turn 不承担餐单历史。

## 2. 为什么不用一个大事务包住模型

外部网关等待可能很慢。如果等待时持有 PostgreSQL 行锁，会阻塞同会话写入，也长期占用连接。实际 submit 标注 `Propagation.NOT_SUPPORTED`，登记、开始、完成由另一 Spring Service 的 `@Transactional` 方法负责。

```java
// 先提交登记；外部等待结束后再原子写成功。
store.start(user, conversation, meal, action);
var result = execute(user, request, registration, metrics);
store.complete(user, conversation, meal, action, result.toString(), metricsJson);
```

注意 Spring 代理：同一个对象内部调用方法不会自动开启新的事务。本实现的 recover→fail 已处在 register/select 的事务内，复用该事务；编排调用独立持久化 Bean 才跨越代理。测试在网关和 QueryEmbedding 替身处断言没有实际事务。

这会出现“数据库已登记，但进程尚未完成”的中间状态，所以必须持久化 PENDING/RUNNING、deadline 和安全恢复，而不能只用内存布尔变量。

## 3. 关系约束、部分唯一索引与版本检查

MySQL 的普通唯一索引也能防重复；PostgreSQL 进一步支持只约束符合条件的行：

```sql
CREATE UNIQUE INDEX uq_meal_active_action ON meal_action(meal_id)
WHERE status IN ('PENDING','RUNNING');
```

历史终态可以很多，活动动作只能一个。复合外键将 ID 与 user_id/conversation_id 一起绑定，防止“餐本身存在，但属于别人”。所选方案外键还带 current_version，使旧版本方案不能成为新版本选择。

版本检查采用父锁下的 expectedVersion 比较：当前值必须一致，修订加一；检测整数溢出。这里不是先读取后无锁更新。所有写按 conversation→meal→action→option，旧 T14 也使用同 conversation 父锁，因此短写事务能协调，但两类历史不互相注入。

SQLSTATE 23503 表示外键违规，23505 表示唯一违规。测试检查具体约束及合法正例；不能只断言“随便抛了异常”。完整材料与动作结果同一事务写入，故插入方案故障不会留下半套成功。

## 4. 幂等与未知结果

requestId 是客户端生成的 UUID；参数哈希排除 requestId，但包含动作类型、目标/版本、精确正文/人数或 optionId。服务器同时比较规范参数对象与原文，避免同键被用于不同内容。

同键同输入在途返回202和动作 URL；终态返回200及该动作自己的历史结果。不能因为当前餐已到版本2，就把版本2结果冒充版本1请求。响应丢失时先读动作/重放同键；生成新键可能产生新的收费动作。U3 不自动重试网关或另付费修复错误 JSON。

同版本选同方案的新键点击返回原成功选择动作，零模型；不同方案409。修订登记即清掉选择，失败仍是新版本 FAILED，旧选择不能悄悄恢复。GET 只读取，不把过期执行“顺手恢复”；新写在父锁内恢复过期旧动作。

## 5. JSONB、严格类型与数值精度

关系字段保存可约束的归属、状态与版本，JSONB 保存不断扩展的需求/材料快照。不是把所有业务塞进 JSONB。Mapper 将快照转为 text，再由局部 Jackson ObjectMapper 解析；不修改全局解析配置或旧接口行为。

写请求和模型输出拒绝未知字段、重复字段、尾随 JSON、数值 ID、小数整数转换。例如 dishCount=4.9 不能变成4。SET/CLEAR 必须引用本次原文的精确片段；KEEP 不能带新值。这是结构约束，不是对自然语言理解正确性的数学证明。

PostgreSQL BIGINT 能超过 JavaScript 安全整数，所以所有 long ID 外发为字符串。原量与参考折算来自 U2 BigDecimal，外发十进制字符串；避免 double 舍入。示例测试原量1克、原份数2、目标人数3得到字符串 `"1.5"`。单位未知、区间和待确认项完整保留，不由 LLM 换算。

厨具 null 表示未知，[] 表示没有厨具，0道汤是合法明确值，null 汤数需要澄清。SQL `WHERE` 条件必须保留这些差异，不能统一改成“空就不限”。已有食材不是库存，预算只是软条件。

## 6. 让模型做有限选择

第一次模型理解完整 changes；第二次只返回候选 ID 和不含步骤/材料数量的搭配说明。服务器校验子集、角色、精确数量、重复 ID 和两套集合不同，再用真实 Service 补材料。候选数使用 `min(20,max(2*n,n+4))`，零需求角色不调用。

RANDOM 对真实合格池按服务器种子抽样，零 T5/Embedding；SEMANTIC 每角色一次现有 T5，保留其排序，不因不足追加查询。随机不等于免费：理解与组餐仍可能调用 LLM。测试使用网关替身，只证明代码约束，不证明供应商输出质量。

两次提示词都将正文/快照/候选标记为不可信。组餐只送材料名称摘要，完整材料存在服务器。所有外发事实文本也检查危险内容；无法安全展示时整份失败，不删掉原材料假称清单完整。保守规则可能误拒绝，不能取代完整安全评估。

## 7. 历史事实与实时权限

快照不是永久访问许可。GET 重新读公开 RecipeMealFactsService：指纹相同 CURRENT；仍可见但变化 CHANGED，展示旧快照并通知；任一相关菜谱删除/撤权 UNAVAILABLE，整份 options 隐藏。

提交/选择除指纹外还调用 recheck 核验硬资格。食材别名可能改变“排除食材”的 SQL 条件，却不改变原食谱事实指纹，所以不能只查 Markdown 哈希或 fingerprint。新增用例给番茄添加被排除别名，验证 GET 仍 CURRENT 但选择409。各次复核是公开短事务，不能承诺对所有管理员并发写形成全局串行化。

## 8. 超时、费用与证据

RecommendationClock 的单调时间计算90秒软预算，阶段前后检查；数据库 clock_timestamp 记录120秒截止，不依赖客户端时间。超限停止后续步骤，不能强制撤销已经发出的供应商请求。

metrics 的网关尝试数不是实际计费数。每次尝试先记录未知 usage，拿到供应商 usage 才填值；语义 Embedding 请求数不可确定时 null，随机0。U2 中途失败时语义次数未知也为 null。只保存固定中文错误，不保存供应商正文、Prompt、Key 或异常链。

验收分层：单元测试验证 policy；真实隔离 PostgreSQL 验证约束/迁移/回滚；真实认证 HTTP 验证 Cookie/CSRF/状态码/越权；完整应用上下文重建验证持久化。固定 READY、空向量 fixture 只是词法检索测试，不是实际 Embedding 或质量签收。

## 9. 新知识清单与建议阅读顺序

需要单独学习：Spring 代理事务与 NOT_SUPPORTED/REQUIRES_NEW、PostgreSQL 部分唯一索引、复合外键、行锁顺序、幂等与未知结果、JSONB 对象约束、Unicode 码点、BigDecimal/JavaScript 安全整数、单调时间与数据库截止、模型结构约束及证据局限。

先读 Controller/MealHttpRequest，再读 submit/execute；随后读 V11 与 register/select/complete，最后顺着 HTTP 测试中并发、过期与回滚路径自证。用自己熟悉的 Spring Boot/MySQL 分层理解职责，再研究 PostgreSQL 特有索引与 SQLSTATE。

## 12. 两个练习

练习一：只在独立测试库中创建一餐，使用两个线程选择不同方案。预测状态码、meal_action 行数与 selected_option_id，再运行现有并发测试比对。解释取消父锁或复合外键分别会失去什么保护。不要修改开发库或调用真实模型。

练习二：用 MealPolicyTest 构造人数 KEEP、SET、CLEAR 与表单冲突，区分初始档案和后来档案。再构造小数 dishCount、重复 JSON 字段及厨具 []/null，先写预期再执行测试。解释 evidence 存在为何仍不足以证明“无糖/过敏条件”已正确理解。
