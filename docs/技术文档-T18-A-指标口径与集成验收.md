# T18-A：指标口径与集成验收

日期：2026-10-08。仅非收费准备；实际执行证据见[工作报告](工作报告-T18-A-非收费集成与评测准备.md)。评测脚本位于测试侧，不作为生产Service、Controller或Spring Bean。

## 1. 三层证据与真实调用路径

20条检索问句回答“找到了相关菜谱吗”；12类整餐场景回答“人数、菜汤数量、选择、指导和采购是否按契约工作”。这两种质量不能合并，也不能用1856个READY块或旧T6成绩代替新库评测。

生产检索路径是`RecipeSearchService.search → RecipeSearchEligibilityService → 词法Mapper → QueryEmbeddingService → 向量Mapper → 按菜谱去重/RRF`。资格为空直接返回，不调用Embedding；向量失败时可只返回词法结果，应标LEXICAL_FALLBACK，不能仍归为真实HYBRID。直接调用Mapper、fuse或资格Service不算生产search路径；替身QueryEmbedding可验证接线，不证明百炼真实质量。

U3创建/修订经`MealPlanningService → ModelGateway理解 → MealCandidateService → ModelGateway选方案 → RecipeMealFactsService/MealPersistenceService`。RANDOM候选零T5/Embedding，但理解和选方案仍可用LLM；SEMANTIC每个非零角色最多一次T5。选择、GET和终态重放零模型，指导是单独动作。

U4经`MealGuidanceService → 所选完整事实/材料 → ModelGateway.completeGuide一次 → policy校验 → 短事务保存`，不重新检索。当前R5采用完整证据无损去重、指导输入64000码点和输出8192档，普通理解/组方案输入20000、输出2048；这些是工程上限，不是收费预估。引用有效并覆盖步骤不等于整句事实忠实，后者需人工评分。

T16经`ShoppingService → conversation公共来源接口 → 原材料确认/有限换算 → 清单快照`；T17经`ProductMatchService → 明确标准ID的MockProductProvider → 合包/BigDecimal成本 → 独立报价快照`。未知量不填0、不按名称猜商品；原事实、权限和幂等由服务器保持，模型不能改这些权威事实。

## 2. 固定资源与人工标注入口

- [20条未审问句模板](../backend/src/test/resources/t18/retrieval-gold.json)：菜名、食材、软偏好、时间、厨具、排除、组合和潜在无结果；全部ID、gold范围和新快照依据为空。
- [12类整餐场景](../backend/src/test/resources/t18/meal-scenarios.json)：固定输入、动作、隔离fixture、预期、复用方法和缺口；预期不算已经观察到的结果。
- [专项复用与缺口清单](../backend/src/test/resources/t18/reuse-and-gaps.json)：6类现有专项及7类缺口。
- [零观测模板](../backend/src/test/resources/t18/observations-template.json)：samples=[]，正式质量及耗时尚未采样。
- [供用户填写的副本](../.data/t18-a/gold-for-user-review.json)：独立副本，不覆盖冻结的未审模板。

人工操作：

1. 在副本中按Q01～Q20先理解问句和硬条件，独立判断相关菜谱；不看当前检索排名选“正确答案”。软偏好也要明确审定标准。
2. 当前无新增新库ID证据。先请主架构追加获准只读依据，核对source类型、原文路径/版本、名称和当前新recipeId；不要复制旧T6或隔离fixture ID。本轮没有连接宿主库取标签。
3. 为每条记录sourceReferences、审定人、goldStatus=REVIEWED及goldScope。COMPLETE表示明确审定的完整相关集合；POOL表示仅审定候选池，应披露池的来源/范围，不能称全库Recall。
4. 确认无相关结果才填空数组[]；不确定继续null/PENDING。null不是“无相关菜谱”，[]也不能因为本次检索没命中而填写。
5. 冻结审定副本和snapshotEvidenceRef，先确定阈值，再由另批T18-B采样；不能看到成绩后修改gold或阈值。填好的gold副本不是汇总器输入，仍须配对独立实际排名和观测字段。

场景candidateSeed=42仅为U2隔离fixture规划。现有U3由服务器登记并保存seed，复用时捕获实际seed而非声称注入42；本轮没有改生产随机规则。12类场景不是12条新端到端执行器，已有测试复用和缺口分别列明。

## 3. 观测文件协议

[汇总器](../scripts/t18/summarize.py)只读取显式JSON文件，无网络、环境变量、数据库或产品执行入口，使用Python标准库。

顶层为`{schemaVersion:1,samples:[],note?:string}`。每个样本都有唯一id、kind、mode、path、environment、retrievalMode、warmth、outcome，durationMs可为null。caseId可关联Q/M编号；path填写实际被测Service或HTTP动作签名，不以脚本名代替被测路径。

| 字段 | 允许值与语义 |
| --- | --- |
| kind | retrieval / meal / guidance / shopping / calls，各层分开 |
| mode | ISOLATED_SUBSTITUTE / REAL_SUPPLIER / LOCAL_MOCK / USER_REVIEW / DATABASE_READ_ONLY |
| retrievalMode | HYBRID / LEXICAL_FALLBACK / VECTOR / RANDOM / NOT_APPLICABLE；须按实际路径判定 |
| warmth | COLD / WARM / UNKNOWN；UNKNOWN不并入WARM |
| outcome | SUCCEEDED / CLARIFICATION / NO_MATCH / FAILED / TIMEOUT / UNKNOWN |
| durationMs | 有限非负数，未知null；布尔值、NaN、Infinity拒绝 |

按指标层、模式、路径、环境、检索模式、冷热、gold范围分组，禁止把替身时延、词法降级或候选池标签混入新库真实混合成绩。原始输入由执行者负责来源核对；工具不能证明其真实调用或标签已被正确审定。

retrieval另有goldStatus、goldScope、goldEvidenceRef、goldRecipeIds和rankedRecipeIds；审定gold必须带明确集合和新快照人工依据。菜谱ID是不重复正整数字符串，失败/超时没有成功排名。例子只用于说明结构，不提供新库ID：

```json
{"schemaVersion":1,"samples":[],"note":"先冻结人工gold，再增加独立实际观测；当前未测"}
```

meal另有options数组，每方案`roleQuantitySatisfied/deduplicated`为布尔或null、`hardViolations`为非负整数或null；两方案请求另记differentSets。CREATE/REVISE的SUCCEEDED应表示实际成套，不能仅根据动作HTTP201或action.SUCCEEDED推断；CLARIFICATION、NO_MATCH和失败分开。不同动作path单独计分母。

guidance另有ratings四项faithfulness/executability/supplementClarity/tone，1～5或null；有评分须ratingsSource=USER且recipeIds明确关联所选菜谱。缺评分不补5，不以引用存在率替换人工事实忠实度。

shopping的lines只列待购买项，足量已有不混入该分母。每项quantityCalculable、matchEligible、matched、costCalculable为布尔或null，reasonCode保留有限未知/待确认原因。无明确标准ID、数量和兼容单位资格，不能matched=true。消耗成本与整包支出取真实已保存快照分别展示；汇总器不会从比例或已知小计猜完整金额。

calls另有methodAttempts、httpAttempts、inputTokens、outputTokens，均非负整数或null。安全观察unauthorizedLeaks、replayCallDelta、factMutations同样可null；没有观察到不能默认安全为0。禁止录入凭证、Prompt、正文等未知字段，重复JSON键和重复观测ID拒绝；一次最多10000行、5MB。

## 4. 算法、分母和未知

| 指标 | 算法与分母 |
| --- | --- |
| Hit@5/10 | 前K至少命中一个审定相关ID的问句数 / 正gold问句数 |
| MRR | 每问句首个相关排名的倒数取均值；未命中0，排名范围限实际输入列表 |
| Recall@K | 每问句命中的不同相关ID数 / 该问句gold总数，再宏平均；POOL只能称池内gold召回 |
| 无结果正确率 | 单列审定空gold问句；完成且返回空集合为正确，失败不是正确无结果 |
| 请求状态率 | 每状态请求数 / 全部同组请求数；UNKNOWN也留在分母并单列 |
| 数量/角色、去重满足率 | 明确通过方案数 / 实际产出方案数；请求数另列，不能只挑成功请求 |
| 两套集合差异 | 仅实际两套请求的不同集合数 / 两套请求数；未知单列 |
| 采购覆盖 | 全部待购买项的匹配比例与仅具备资格项比例同时列；不能将12个Mock商品数当覆盖率 |
| 人工指导评分 | 每项已评分数、未评分数及已评分子样本平均；未评分不填0 |
| 费用与安全计数 | 已知小计、未知行数、完整总数分别输出；有未知总数null，tokens不是实付 |

检索FAILED/TIMEOUT若gold已审，仍在正gold分母并记未命中0；UNKNOWN结果保留未知计数、该组Hit/MRR/Recall留null，不能强行当成功或失败。PENDING gold不进入质量分母，仍列待审数量；0正gold时指标null。空gold的Hit/Recall不定义，改用单独无结果分母。

率字段同时输出numerator/denominator/unknown；有未知判断时rate=null，不能把null当false或0。已知小计0只表示当前已知部分求和为0，不等于完整总数已知为0。

## 5. p95与计时边界

每层从其明确起止点测单调时钟差：检索围绕生产search方法；组餐/指导围绕各Service或各HTTP请求；采购围绕预览/创建/匹配动作；浏览器端到端需另采前端实际起止，本轮不提供浏览器计时。方法durationMs不等于供应商HTTP耗时，外部等待、数据库和浏览器阶段不能混成同一分母。

同组成功且计时已知样本n≥30，排序后p95=第ceil(0.95×n)项（1基下标），即nearest-rank。失败/超时耗时另列，不补入成功p95；未知时延列出缺失数。不足30仅给逐次时间和范围，p95=null/INSUFFICIENT_SUCCESS_SAMPLES。30是本计划最低披露门槛，不代表统计稳定性或线上SLA；第一批4种真人请求只能试用质量。

练习：成功时延1～30ms，p95为第29项，即29ms。添加一次失败99999ms不改变成功p95；只有29例时不报p95。将15个替身和15个真实样本合并成30也是错误，工具会拆组。

## 7. T18-B建议方案，仅供另批

建议首批4个正常请求：随机四菜一汤；显式人数覆盖档案的一菜一汤；番茄偏好的两菜一汤；清淡并排除花生的两菜一汤。前两条RANDOM、后两条SEMANTIC。冻结人数/正文/硬条件后，每条至多一次创建、一次明确选择、一次单独指导，再零模型预览/确认及显式Mock报价；成功不为凑样本重发。

路径：`POST meals → GET/action核对 → POST selection → POST guides → GET guide → GET shopping-preview → POST shopping-lists → POST product-matches → GET历史`。选择/GET/采购应零LLM/query调用；异常/越权/断网留隔离测试，不随意付费造错误。

建议上界：4次创建各最多2次LLM网关方法尝试、4次指导各1次，合计最多12次LLM方法尝试；两条语义请求各2个非零角色，最多4次T5/query Embedding方法尝试，其他两条随机0。建议另冻结真实出站POST总上限为12个LLM、4个query，必须在零费用审查中证明计账、无隐式重试及中断保护后才执行，现有方法计数不能冒充已具备硬HTTP配额。本轮只提交方案，没有实现或打开收费守卫。

20条独立检索采样须先审完gold，并另冻结每条一次search、最多20次query方法尝试的独立批次；不自动并入前述4条整餐。没有完整gold就不正式算Recall；4例也不包装p95。

建议全局停止：401/403、参数/模型错误、额度、超预算、计数/配置漂移、成功重放新增调用或权限/事实异常立即停；超时/结果未知仍占尝试，不当免费。恢复仅做原action GET/同键已完成结果核对，零新供应商调用；失败新UUID、真实重生成或额外轮次均需另批。不得复用已用完的D1-C首轮/恢复账本。

执行前主架构还需冻结精确新库/目录、动作列表、gold/评分人、观测办法、实际HTTP上限与费用风险、停止/回退以及API Key安全注入。T18-A不申请读取或注入Key，不启停、切库或执行业务动作。

## 8. 面试与学习自检

1. Hit@K和Recall@K为什么不同？——前者每问句只看是否命中，后者看相关集合覆盖程度，需完整性明确的gold。
2. MRR为什么比“命中就1”敏感？——首个相关排名越后，倒数越低；须披露输入排名长度。
3. 为何不从当前排名选gold？——会把被测输出当答案，形成循环验证和数据泄漏。
4. 失败为何仍计检索分母？——只统计成功会美化质量；未知需独立标记而非猜结果。
5. 30个样本就能保证稳定p95吗？——不能，它只是本计划最低门槛，仍有波动和环境限制。
6. ModelGateway方法次数为何不是账单？——方法可能本地拒绝或网络结果未知，HTTP和usage要独立观测。
7. Mock匹配100%证明真实平台可用吗？——不能，目录、价格、城市和供应商都只是显式替身。
8. 引用全部存在为何还需人工评分？——结构合法不证明解释语义忠实或步骤可执行。

自检：能画出search与随机候选路径吗；能分辨null与空gold吗；能列请求/方案/采购项三个分母吗；能解释冷暖和失败时延分离吗；能指出现有未知HTTP及usage的证据缺口吗。

练习二：两条正gold问句，一条首相关在第2位且命中全部2个gold，另一条网络失败。Hit@5=1/2，MRR=(1/2+0)/2=1/4，宏Recall=(1+0)/2=1/2；若第二条结果UNKNOWN，则这些率留未知，不把它算作失败。

本轮教学不证明用户已经掌握；需要继续练习概率/抽样、评测泄漏、统计置信与分层可观测性。T18-B/C、Cloud/MQ、部署及Git仍不在本轮范围。
