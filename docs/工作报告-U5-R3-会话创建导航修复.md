## 根因与修改

创建 POST 返回成功后，原状态层先设置 `createdConversationId`，但直到随后的列表 GET 完成、进入 finally 才清除 `createBusy`。页面成功 ID 的 watch 会导航；路由变化又调用实际 `activate → stopWaits(true)`。当列表 GET 尚在等待时，导航就把已成功的创建当成被取消的等待，设置 `createUnknown` 并显示误报。

修复在 `kitchen/state.ts`：核验成功响应仍属于当前账号和创建代次后，先释放已完成的创建控制器并设 `createBusy=false`，再发布成功 ID。成功导航因此不再进入取消未知分支；真正的超时/取消仍走原未知处理，不无条件清除错误状态。页面已有 watch 与路由接线无需修改。

创建请求另记录独立 `creationGeneration`：每次创建、账号变化和会话清理都会更新代次。迟到成功/失败及 finally 只作用于所属创建代次，避免账号 A→B→A 后接受旧响应，也避免旧成功请求的列表刷新收尾清除后一次创建的 busy。

## 异步生命周期学习说明

业务请求终态与页面后续读取应分别判断。服务器已经返回创建成功，列表刷新仍在进行，不会使创建重新变成未知；`finally` 只能清理本次仍拥有的等待状态，不能承担“成功已经确认”的唯一标记。

Vue watch 与路由导航会在后续 await 期间运行。发布供页面监听的成功 ID 等于触发另一条执行链，因此应先把创建状态转为成功终态，再发出导航信号。若先发信号再清理 busy，新的激活逻辑会读取不一致的旧状态。

AbortSignal 表示本地等待被取消，不能证明服务端未创建。真正超时或取消后仍提示先查历史；若后来收到可确认的成功，只能在原账号/创建代次仍有效时接受它。代次还能区分同一账号重新登录后的旧请求，不能仅比较账号字符串。

自检：列表 GET 慢时是否仍不误报创建未知？取消是否仍保留未知？手工离开后是否不抢导航？切回原账号是否仍拒绝旧请求？旧 finally 是否不会清除新请求的 busy？
