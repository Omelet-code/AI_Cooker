## 1. 为什么新增SELECTED_TARGET

用户认可的Q01—Q17是17条示例目标题，目标关联共20个菜谱ID；Q02有4个目标，其他正例各1个。目标之外的菜谱并未被逐个判为不相关。即使排名中还有许多合理菜谱，目标未出现也只是本项目标未命中，不能推断全库相关准确率。

主架构冻结集只读导入[独立目标副本](../backend/src/test/resources/t18/retrieval-targets-v1.json)，源身份、名称、sourceKey及sourceVersion保留。本轮原文比较一致，没有哈希专项。原[待审gold模板](../backend/src/test/resources/t18/retrieval-gold.json)不覆盖；它的历史待审状态不代表本轮人工目标未冻结。主树和原人工填写记录均只读。

[summarize.py](../scripts/t18/summarize.py)保留原COMPLETE/POOL分支及测试，新增SELECTED_TARGET与SELECTED_TARGET_EMPTY分组。新分组直接不生成recallAt5/recallAt10字段，也没有Precision或总体相关准确率。内部goldRecipeIds仅是复用已有校验协议的字段名，新scope不能解释为完整gold。

| 项目 | 算法及分母 |
| --- | --- |
| 目标Hit@5/10 | 前K实际返回ID与人工目标至少一个相交则1，否则0；正例分母17 |
| 首目标MRR | 实际返回截断列表内，第一个目标名次r记1/r；未出现记0；分母17 |
| Q19空结果 | 只核验已完成且返回空；独立分母1；失败/超时记未满足、未知留未知 |
| Q18 | 未确定，不是空集合；不计分、不自动采样 |
| Q20 | 普通烤箱不是星际量子烤箱；独立硬条件审计，不作为检索gold |

失败和超时占正例分母、贡献0；结果未知或尚未采到则保留未知，相关聚合率为null，不强行补0。[selected_targets.py](../scripts/t18/selected_targets.py)拒绝重复caseId、排除题、观测携带自定义gold和混合环境。观测非空时补齐缺测占位，从而不能只交成功题缩小17＋1分母；observedSampleN与补齐后的sampleN明确区分。全空输入维持NO_SAMPLES/groups=[]，不产生17个虚构测量。

Q19确实空资格时，可以用NOT_APPLICABLE/NO_MATCH和methodAttempts=0、httpAttempts=0单列；没有零计数依据则拒绝这种编码。词法降级不能进入混合目标采样器，必须单独报告停止情况。冷热、环境、实际模式和scope继续分组。

例：前三个目标的首目标名次是2、未命中、5，则MRR=(1/2+0+1/5)/3。本例仅教学虚构；正式本批分母仍17，缺14题时不报告这个小集合的正式MRR。18题不足30个同类成功样本，不能报p95或自动补收费样本。

## 4. 方法、HTTP与接收数为何分别记

[SamplingLedger](../backend/src/test/java/com/cooker/t18/SamplingLedger.java)按独立批次、QUERY/LLM通道登记方法与HTTP额度。同步锁覆盖检查及计数，账本CREATE_NEW，每次事件写入并force(true)后才继续。事件只含批次、序号、动作、通道和有限状态；不含Key、Prompt、正文，usage未知保持null。

状态为RESERVED→SENT→SUCCEEDED/FAILED/UNKNOWN。HTTP_RESERVED持久化在执行传输之前，进程崩溃可能留下保守的已占尝试；不能看到没有结果就退额度。文件写失败停止且禁止网络；关闭时未完成SENT记UNKNOWN。没有自动重开或恢复旧额度的入口。

方法与HTTP有不同分母。资格空为0/0；方法进入但HTTP额度为0可能1/0；已发送后断开响应为1/1且结果未知。UNKNOWN是结果/usage未知，并非免费。服务器实际收到数是第三个观察：连接失败可能HTTP预记1、接收0，因此不应要求所有故障都三数相等。本轮成功、返回错误、断开和超时的本机案例均检查接收数，没有只拦方法便声称HTTP受控。

[GuardedLocalTransport](../backend/src/test/java/com/cooker/t18/GuardedLocalTransport.java)只允许127.0.0.1本机替身、准确地址和POST；QUERY只允许text_type=query和单文本，document拒绝。发送前核对票据并登记HTTP；非2xx即FAILED/停止，不跟随重定向；IO异常为UNKNOWN/停止。200仍需调用者成功解码才能记成功。DeepSeek SDK显式maxRetries=0；测试JDK传输不启用应用重试，断开响应和超时专项验证实际只接收一次。

这些证据适用于本轮测试注入的传输和已覆盖故障，不能外推为任意HTTP库/网络故障下的恰好一次供应商计费。该传输明确拒绝真实供应商地址，不能拿本地测试工具直接开启付费采样。

两个批次建议值为检索18 QUERY方法/18 QUERY HTTP、0 LLM；四餐4 QUERY/4 QUERY HTTP和12 LLM/12 LLM HTTP。它们只在离线账本测试中作为参数，尚未授权真实运行。票据由所属账本验证，不跨批共享；一个批次故障或拒绝追加后停止其所有通道。重放成功动作不可再次保留票据，重复动作拒绝并停止；恢复只能另获允许后零调用GET核对既有业务结果。

## 5. 默认生产客户端的阻断与最小接缝方案

**B0非收费准备可以交付，真实执行门槛尚未通过。** 代码检查确认：QueryEmbeddingServiceImpl在embed内部new SimpleClientHttpRequestFactory/RestClient；DefaultDeepSeekChatClientFactory.build也自行创建SimpleClientHttpRequestFactory和RestClient，没有HTTP发送前批次控制注入点。仅替换或装饰Service方法无法约束底层HTTP隐式补发，也不能把document专用IndexRunControl当query/LLM守卫。当前没有证明默认传输的全部HTTP尝试都纳入本账本。

建议最小生产接缝供另卡审定，本轮不实施：

1. query允许注入受控RestClient/请求工厂提供者，默认行为保持；DashScope既有构造器已能接RestClient，不必改资格/排序/Prompt。
2. DeepSeek工厂允许注入同步请求工厂或RestClient提供者，保留固定模型、JSON、thinking、2048/8192与30/60秒档位和SDK零重试；不开放任意前端目标URL。
3. 正式采样上下文由受控操作者入口提供，方法保留及HTTP发送前同一账本；无上下文或已停止则在发送前拒绝。核对底层客户端无隐藏POST重试、无重定向；失败/未知不退额度。
4. 若未来整餐由常规浏览器动作触发，整个执行进程都须持有同一批次保护，创建、指导及额外浏览器请求不能绕过。只给命令行测试注入守卫不足以保护常规网页。
5. 进程恢复采用旧账本只读核对和零调用GET，不自动重启额度。新动作、UUID、重新生成和失败补样本必须另批。

这是具体接缝建议和未满足条件，不是已改生产、自动派发或对收费方案的批准。本轮没有开启模型、连接宿主业务库或执行任何真实采样。

四餐12/4的源码依据：正常创建至多理解与选菜两次LLM，指导一次LLM；选定动作零LLM；SEMANTIC每实际菜/汤角色至多一次T5，RANDOM零query。候选不足或澄清可能少调用，模型意图改变模式也可能耗尽预算；不能按预期“前两随机”硬填计数。指导和采购零检索的原契约保留。动作内部次数上限不等于跨四餐HTTP配额，故12/4是否足够仍须正式输入、实际意图及操作者方案冻结。
