# T18-B1：依赖注入与发送前保护

2026-10-09。只完成默认客户端最小接缝和非收费定向验证，真实两餐、Key/业务库/启停尚未执行。

## 分层与两种模式

以前QueryEmbeddingServiceImpl与DefaultDeepSeekChatClientFactory在内部new请求工厂。Spring提供的拦截/账本无法进入这两个实际HTTP路径。现在两个类的@Autowired构造器注入同一个SyncModelTransport，提供者属于专用evaluation.transport包，只协调模型同步传输，不包含菜谱、身份、事务或采购规则。旧构造器保留用于既有普通模式/协议测试；当前生产源码没有手工new这两客户端的其他调用点，页面路径使用Spring单例提供者，不能通过额外点击换批或绕开它。

普通模式默认enabled=false，仍用SimpleClientHttpRequestFactory和原DeepSeek模型；无Key的query仍返回null，TEXT/JSON和既有模型选项保留。受控模式才包装实际model.call，stream发送前拒绝并停止。固定DeepSeek URL/模型、Bearer鉴权、JSON/thinking关闭、2048/8192与30/60秒读取档位保持；query仍使用服务端原endpoint、text-embedding-v4/1024、query单文本，连接/读取3/5秒。LLM连接5秒，普通读取30秒、指导60秒。

受控模式无批准上下文时可启动为关闭状态，但任何模型请求均发送前拒绝；有批准文件时进程只创建一个账本。该模式用于当前网页同步模型链，不开放document或流式。没有新框架、POM依赖、SQL、迁移、Prompt或产品API。

## 为什么拦截器一次不等于发送一次

受控传输复用JDK21 HttpClient（HTTP/1.1），followRedirects=NEVER。已直接核对本机JDK源MultiExchange：POST隐式重试与连接重试由启动时读取的静态选项决定。因此受控模式必须同时满足JVM启动参数和当前属性值：

```text
-Djdk.httpclient.enableAllMethodRetry=false
-Djdk.httpclient.disableRetryConnect=true
```

缺启动项、版本不是21、属性漂移、禁用TLS主机验证均拒绝/停止。没有在应用里临时setProperty试图影响已初始化的HTTP类。普通模式不强制这些选项；不能把普通工厂的SDK零重试当成底层零补发。

HTTP票据检查在请求工厂execute边界，要求准确目的URI/POST/通道/方法上下文，持久HTTP_RESERVED后才执行底层工厂；SDK也仍maxRetries=0。本机替身独立统计实际接收到的请求，成功、错误、重定向带Location、断开和超时均验证只接收一次。此证据不来自只数上层拦截器。本轮未接真实TLS或供应商，不承诺恰好一次计费；操作系统TCP重传也不是新的应用POST。

## 账本、并发和未知

批准文件提供两通道参数，EvaluationBatch按批次CREATE_NEW、写事件后force(true)。METHOD_RESERVED发生在query实际embed/model实际call前，HTTP_RESERVED发生在HTTP执行前；客户端构造本身不算LLM方法尝试。方法已有票据但HTTP额度0，可为1/0；资格空不进入embed，为0/0；发送前连接失败可能预记1而服务器接收0，尝试不退还。

整个方法在批次锁内完成，其他网页线程排队，不能在失败响应、解码和停止之间插入发送。401/403/429/5xx/3xx均停止，不跟随Location；响应完整有界读取，截断、无效/尾随JSON、网络/超时按FAILED或UNKNOWN保留；未知usage始终null，不当0。文件写失败同样禁止出站。流式/document或不正确协议在发送前拒绝。缺Key的受控query停止，而普通无Key行为保持。

成功后票据不能重复HTTP发送；同一方法若SDK尝试第二次发送会被拒绝。超额即全局停止整个批次的query与LLM，不能把余下另一通道当恢复额度。关闭时未完成发送记UNKNOWN；崩溃可能只剩保守的保留事件。旧账本不能重开，新进程不自动恢复额度。这里按方法序号记发送尝试，业务动作requestId/成功幂等仍由原Service保存；用户重复已完成动作不一定产生新模型调用，但供应商计费不能由业务幂等倒推。

账本只记录batchId、authorizationId、methodSequence、lane、event、usage=null，不存Key、请求/响应正文或Prompt。已有业务usage统计继续由原Service保存；账本本身不替代供应商账单。authorizationId是可追踪操作标识，不是签名/身份认证凭证。正文缓冲上限请求1MB、响应4MB；受控模式串行行为不用于声称普通产品p95。

最小流程：

```text
调用生产默认客户端
  → 共用批准批次核对
  → 持久METHOD_RESERVED
  → 生成原协议请求
  → 请求工厂核对票据/URI/协议
  → 持久HTTP_RESERVED
  → 单次JDK POST（禁连接重试、POST重试、重定向）
  → 完整读取/解码成功：SUCCEEDED
  → 错误/未知：记尝试＋GLOBAL_STOP，后续两通道均拒绝
```

检索Service原有EmbeddingProviderException词法降级未修改。临时PG实测401仍返回词法列表，但账本已停止；采样必须识别这个状态，不能把“HTTP返回了列表”算HYBRID质量。B0冻结17目标＋1空结果＋2排除保持，18检索与真人两餐账本独立。

## 获批后直接启动的方法（本轮未执行）

建议先两餐：随机4菜1汤、语义3菜1汤。最多6 LLM方法/HTTP及4 query方法/HTTP仍是待批准参数，不是费用承诺。批准文件由主架构在集中确认后创建于独立绝对路径；不包含Key或数据库密码。格式示意如下，本轮没有将此示意保存为真实文件：

```json
{
  "schemaVersion": 1,
  "batchId": "USER_APPROVED_BATCH_ID",
  "authorizationId": "USER_APPROVAL_REFERENCE",
  "ledgerPath": "C:/absolute/approved/new-ledger.jsonl",
  "queryMethods": 4,
  "queryHttp": 4,
  "llmMethods": 6,
  "llmHttp": 6
}
```

字段必须精确一致，拒绝重复字段、未知字段/非整数额度/无效标识；额度0—1000参数化。输入≤64KB，批准文件及账本必须绝对路径；账本父目录须已存在，账本不能存在，错误不回退普通模式。18题另批建议18/18 query及0/0 LLM，使用不同批准文件和不同账本；不要复用D1-C或真人批。

现有IDE运行`com.cooker.CookerApplication`，使用JDK21并编译本轮源码，在VM options加入：

```text
-Djdk.httpclient.enableAllMethodRetry=false
-Djdk.httpclient.disableRetryConnect=true
-Dcooker.evaluation.http.enabled=true
-Dcooker.evaluation.http.batch-file=C:/absolute/approved/batch.json
-Dcooker.agent.execution-enabled=true
```

这就是启动保护所需接线，无需再实现管理页、过滤器或新准备任务。Key和数据库沿用另获批准的安全配置，由用户本人设置，不放入上述文件/聊天/日志。模型执行开关、实际账号/最终库、在途核对、前后端精确端口启停及必要业务写入仍需主架构一次集中确认。本轮没有启停程序、创建真实批次或触达业务库。不要先运行旧B0 Jar当成新实现；用户要求真人后再打包部署，可通过IDE的最新编译类先完成真人测试。

故障后只读GET核对原动作，不自动新UUID/生成/重试/补样本；重新启动同账本会拒绝，不能重新开一个文件便声称旧额度恢复。完成窗口后核对在途/账本，再按集中批准方案关闭模型执行与回退。普通模式仍能正常运行，但不能静默用于越过已停止的收费窗口。

## 证据与面试自检

本轮27个不同Java用例通过：原协议15、新增默认客户端11、临时PG1；最终小变更只定向复验受影响用例，不累计重跑。见[工作报告](工作报告-T18-B1-默认客户端HTTP守卫接缝.md)。B0已签收22/13证据复用，未重做；真实供应商、真人浏览器、人评、账单、TLS联调、package与部署未执行。

1. 为什么@Autowired比类内new能接费用保护？两个生产调用点共享提供者，普通与受控策略集中选择。
2. 为什么保留旧构造器？既有普通模式和协议测试兼容；网页实际调用使用Spring注入，不新增前端绕过入口。
3. 为什么用启动参数而非setProperty？JDK重试值可能已静态缓存，晚设置不能证明生效。
4. 方法1/HTTP0是什么意思？方法已保留，但协议/HTTP限额阻止发送，不能混为服务器收到1。
5. 网络未知为什么占额度？可能已发送并计费，缺响应不能推断免费。
6. 为什么锁覆盖整个调用？阻止其他网页线程在失败解码与停止之间抢发。
7. SDK零重试还要测断开/重定向吗？底层HTTP也可能补发，必须独立验证实际接收数。
8. 为什么没有开启真人两餐？生产接缝已交付，收费/启停/必要数据写入仍需集中授权。

自检练习：画出QUERY方法保留1、HTTP保留1、响应断开、GLOBAL_STOP，说明随后指导为何0发送；再说明同键成功业务回读为什么不证明供应商“恰好收费一次”。
