# T17：Mock商品匹配与成本快照

日期：2026-10-06；契约shopping-products-v1。T16独立复审通过后，按用户明确“复审工作，并派发T17”的授权执行。仅后端和非收费测试/教学，不含F3-D、开发部署、真实平台或Git。

## 1. 目标与模块

将服务器保存的T16采购需求匹配到具体Mock商品，按城市、商品规格计算用量成本及整包支出，保存可回看报价快照。不是线上商家搜索，不可下单。沿用模块化单体、Spring MVC、MyBatis-Plus、PG/Flyway；分层controller/service/service.impl/mapper，Provider隔离外部商品来源，纯计算不依赖HTTP或数据库。无需新增依赖或模型调用。

shopping只能通过既有公共Service核验来源；不直调recipe/conversation Mapper，不更改检索、菜谱归一化、餐单选择或指导。T16原始清单、确认值、预算、view_json及shopping-demand-v1接口全部保留；商品匹配为独立资源，不把旧清单matchingStatus=NOT_MATCHED改成最新报价状态。未来页面分别读取原清单和最新匹配结果。

## 2. 输入与HTTP

沿用统一响应、登录/CSRF，schemaVersion=1、HTTP ID正整数字符串。三个接口：

- `POST /api/shopping-lists/{listId}/product-matches`：严格JSON仅requestId（UUID）、cityCode（六位数字字符串）。首次201，同键同内容200。客户端不得提供userId、商品ID、报价、URL、食材或用量。城市已获用户允许手动选择；本切片不收集精确地址或修改个人档案。
- `GET /api/shopping-lists/{listId}/product-matches/{matchId}`：只读指定快照。
- `GET /api/shopping-lists/{listId}/product-matches/latest`：只读最新已保存快照；无结果200且data=null。latest按创建顺序/id确定，不因读取重新计算。

严格拒绝重复键、未知字段、尾随JSON和类型转换；复用shopping局部解析，不改全局配置。401/403沿用认证/CSRF；不属于当前用户或原菜谱不可访问404；400 VALIDATION_ERROR；同键异内容409 SHOPPING_MATCH_REQUEST_CONFLICT；新匹配来源事实已变化409 SHOPPING_SOURCE_CHANGED。Provider整体异常可用502 SHOPPING_PROVIDER_UNAVAILABLE并完整回滚，不暴露堆栈/配置。

新匹配基于T16保存的数量/确认，不重新套个人档案人数、当前选餐或新菜谱内容；先经公共Service核验归属与事实CURRENT。旧成功快照GET/重放仍核验可见性，事实变化仅返回factsStatus=CHANGED，保留原金额，不以当前餐修订拒绝同键旧结果。

## 3. 确定性Mock Provider

Provider输入仅服务端标准ingredientId、确定缺口数量/单位及cityCode。目录由明确配置提供，不能把未归一名称模糊匹配为另一个食材；不查网络、不调LLM/Embedding。支持标准单位G/KG、ML/L、COUNT，质量/体积/计数不得互换，CUSTOM和未知单位安全保留未匹配。

目录项至少含catalogVersion、productId、ingredientId、商品名、支持cityCode、available、packageAmount、packageUnit、packagePrice、currency=CNY；可选referenceUnitPrice及referenceUnit，供独立预估。标准ID绑定由明确本地配置指定，不硬编码假定生产数据库ID、不自动导入/归一化。默认未配置目录返回未匹配，不能伪造商品。交付无密钥配置示例与只读核对/配置ID步骤；演示数据与配置均明确Mock，开发库准备另获授权。配置错误和非法/超范围报价不能静默成为零成本。

对同一标准食材的可用、同维有效候选，确定性按未舍入单位价格、整包支出、productId排序，选一个；城市不支持/缺货/无候选均有独立中文原因。商品量价只来自Provider，不相信客户端。规格或价格缺失保留未知，不用假量假价补齐。

每个响应和保存快照均有provider=MOCK、realData=false、catalogVersion、cityCode、capturedAt；商品purchaseUrl=null，不伪造美团/支付链接。前端后续必须展示模拟标识并禁用购买。

## 4. 汇总与金额

逐个保留T16 itemKey及lineKeys，匹配行包含ingredientId/name、需求和缺口、状态/原因、选中商品规格价格、包装数、可空消耗成本/整包支出及可空预估来源。状态HAVE_ENOUGH、MATCHED、QUANTITY_PENDING、UNIT_UNSUPPORTED、NO_PRODUCT、OUT_OF_STOCK、QUOTE_UNKNOWN；已有足量无需查询Provider，采购成本0。未知量也不查询Provider，其余确定行可继续，允许部分匹配，不因一条未知丢掉整清单。

兼容的同商品/城市/单位已知缺口先汇总再计算包装数，包含T16按optional分开的行，但不得改写T16汇总或原料确认。响应另给purchaseGroups（groupKey、原itemKeys、总量、商品、包装数、整包支出），包装计费仅按组汇总一次；明细消耗成本与组支出不可重复累加。数量有限换算仍遵循T16规则，不依据名称推算密度或把个换g。

沿用BigDecimal纯成本基础，中间充分精度；最终HALF_UP两位、普通十进制字符串，禁止NaN/科学计数法/浮点。数量与金额持久化遵循numeric(24,8)/numeric(18,2)范围，超界明确失败并回滚，不截断或溢出。10g葱、100g/包10元：消耗1.00、采购10.00；110g：11.00、20.00。同商品两个10g需求只买一包。

总costs：currency=CNY、estimatedDemandCost、consumptionCost、purchaseOutlay、knownSubtotal、unknownItemCount、budgetStatus。estimatedDemandCost只基于明确referenceUnitPrice估价；没有独立估价来源则null，不拿成交模拟报价冒充独立估价。可另列estimatedKnownSubtotal和estimatedUnknownItemCount，解释部分预估。consumptionCost/purchaseOutlay任一必需数量/规格/报价未知，则对应完整金额null；knownSubtotal仅已知消耗成本小计，unknownItemCount计未具备且成本未确定的需求项。全部足量已有时三金额0.00。

预算比较使用未具备部分的消耗成本，不用整包支出；已知完整成本时WITHIN_BUDGET/OVER_BUDGET，无预算NOT_SET，有未知成本UNKNOWN。超预算仍保存并提示，不换菜/放宽预算；未知展示已知小计和未知项，不当0，不承诺满足预算。所有“消耗成本”仍是Mock报价折算，不是支付后的实际账单。

整体matchingStatus：无待采购项NOT_NEEDED；所有待采购项量价明确MATCHED；部分明确PARTIAL；全部未能确定NO_MATCH。所有原条目/原因保留，不能根据状态隐藏未知项。

## 5. 持久化与幂等

已核对5b09最高V13；独占新增`V14__create_shopping_product_matches.sql`。不修改V1～V13。独立匹配头/商品明细或采购组表，保存user_id、list_id、request_id/input_hash、来源指纹、城市、Provider/目录版本、时间、状态及完整报价/金额JSONB快照；核心归属/状态和数量金额使用关系列。外键绑定清单归属，唯一(user_id,request_id)，索引支持按清单读最新；金额CHECK拒绝特殊数值。具体表名由实现报告列出，不新增购物清单可变价格列。

输入摘要为listId+cityCode的规范化语义；请求UUID不影响计算摘要。并发通过唯一约束/安全原子写与既有受控锁实现，同键只创建一个快照，不能在PG失败事务继续查询。同键重放先返回旧结果，Provider零调用；新UUID才显式取得新目录价格/新城市快照，旧匹配不更新。Mock为本地确定性调用，可放短事务；不得将未来真实网络请求直接搬入持锁事务。此次不设计异步平台执行。

GET/latest均零写入/Provider/模型/恢复调用。失败无半份报价，历史查询重新核验归属与菜谱可见性，避免数据失权后泄漏。日志仅安全ID/状态/耗时，不含密钥、目录全文、原料正文或用户输入。
