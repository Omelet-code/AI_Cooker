## 1. 目标及推荐推进顺序

已按用户确认分两条可分别验收的纵向业务切片，保持模块化单体与单Agent。

### 3A：自然语言菜谱推荐

用户设置自己的模型API Key，在聊天页表达需求；系统提取并校验约束、调用已验收检索Service，展示真实候选菜谱与有事实依据的解释。用户能追问和修改约束，刷新后回读自己的对话历史，点击候选进入现有菜谱详情。

首次验收不依赖商品匹配。基本推荐成功后再完善受限Tool Calling与SSE，不一次引入所有新能力；具体是否拆成独立任务待确认。

### 3B：选择菜谱后的采购闭环

用户选择真实菜谱，确认份数、已有食材和配送位置，系统生成缺口清单，调用Mock商品Provider匹配具体商品，展示价格来源、购买入口及成本。已有完成烹饪/收藏功能继续复用，不新增家庭库存或自动扣减。

Mock商品必须显示来源标识。Mock价格、库存与演示入口不等于美团真实接口、可下单商品或当前实价；真实平台集成另行验证和授权。

## 2. 业务与模块边界建议

| 模块 | 阶段三建议职责 | 不承担 |
|---|---|---|
| identity | 复用当前用户身份及受控凭证解密接口 | 在HTTP响应或日志暴露完整Key |
| conversation | 会话/消息归属、轮次状态、历史与候选引用 | 把收藏或做菜历史当成聊天历史 |
| agent | 约束理解、受控工具编排、候选解释与错误映射 | 直接访问其他模块Mapper、随意写关键业务 |
| retrieval | 复用生产RecipeSearchService.search | 根据LLM文字伪造菜谱或修改已签收排序 |
| recipe | 复用真实菜谱Service提供事实与详情 | 将不完整事实补成确定值 |
| shopping | 缺口、单位/包装、商品快照、成本计算 | 读取不存在的持久库存或声称已支付 |
| policy | 健康边界、工具及输出规则 | 医疗诊断和治疗承诺 |
| 前端 | Key设置、聊天/候选、购物清单及失败状态 | 静默退回Mock或保存认证令牌 |

这仍是熟悉的Controller → Service → Mapper结构；Agent是在Service层增加“理解需求、选择受控能力”的编排，不替代数据库事实、事务或权限校验。

## 3. 应用交互建议

```text
已登录用户消息
  → conversation保存轮次
  → agent理解与校验约束
  → retrieval生产Service检索
  → recipe事实核验 + policy约束
  → 保存并展示解释、候选及本轮状态
  → 用户明确选菜/确认已有食材与位置
  → shopping确定性缺口及商品/成本计算
```

检索是后端受控能力，不向模型开放SQL。认证身份由服务端获得；模型或前端不能自行指定viewerUserId来扩大可见范围。工具返回的菜谱ID必须属于本轮授权候选或经Service重新校验。

LLM输出与菜谱原文都不可信。约束必须有类型、范围和长度校验；没有结果就如实返回或询问是否放宽条件，不私自突破硬条件。保存对话不代表无限上下文，建议先只携带最近有限轮次与已确认约束，不做复杂长期记忆。

外部模型请求不应占住长数据库事务；先记录请求状态，再完成模型/检索，最后短事务落结果。网络重试应有轮次幂等和失败状态，避免前端重试自动多次付费。SSE断线、刷新和后端重启的语义需在后续契约中明确，不能默认自动重跑模型。

当前凭证解密接口依赖当前认证上下文。如改用异步执行/SSE线程，必须专门设计可信用户上下文传递，不能假设线程中的身份自动存在，更不能由模型传入任意用户ID。

## 4. 数据与预算边界

建议后续通过Flyway增加会话、消息/轮次，以及购物清单/条目；这是设计候选，尚未定表名、迁移编号或字段。不修改已执行V1～V7，不把完整Prompt/Key/工具响应无边界落日志。

会话与消息至少应能表达：所有者、请求幂等、时间/顺序、本轮成功或失败、候选引用和有限执行统计。购物清单保存用户确认条件、食材缺口与商品价格/规格快照，以便解释历史金额来源。

已核对当前T5的RecipeSearchCriteria：支持query、数量、类别、时间及未知时间策略、厨具、排除食材和viewerUserId；没有预算或已有食材覆盖率字段。不能声称现有检索已满足这些额外约束。预算建议先由shopping成本评估候选，再明确筛选/提示规则；需要扩展接口时由主架构另行冻结，不让实现会话自行改排序。

数量为“适量”、单位无法互换、商品规格不完整或价格不可用时，必须标为待确认/不可估算，而不是0元。优先按结构化食材选择“本次已具备”，比让用户随意输入名称再自动抵扣更容易正确实现；自由文本仅作为待确认匹配。

成本沿用既定三类口径：预估菜谱成本、商品单价折算的消耗成本、购买完整包装的采购支出。用户确认已有的食材按既定预算规则不计本次采购需求；这些口径在后续契约中分别命名，不将包装支出混为消耗成本。具体超预算处理待讨论。

## 5. 学习及验收建议

- 先理解结构化LLM输出与Bean Validation：模型负责理解，Java负责校验，类似Controller接收DTO后校验，但输入来自模型。
- 再理解RAG：把真实检索结果提供给模型生成有依据的解释，不是让模型凭记忆编菜谱。
- 然后学习Tool Calling：模型请求调用结构化工具，后端决定能否执行，工具仍只调用已有Service。
- 最后学习SSE与对话状态：区分流式显示、数据库持久化、断线恢复与重新执行。
- 购物侧重点是numeric/BigDecimal、单位换算、价格快照与可替换Provider，而不是用LLM计算金额。

每个后端切片继续交付独立中文教学文档、真实请求流、测试、面试追问与自检；每个前端切片必须真实联调，Mock仅供开发/测试且明确标识。普通回归使用模型Mock，不能自动调用收费API。

推荐验收项：候选存在且可见、硬条件违规、非法工具输入/越权、轮次重试、无结果、凭证缺失、模型错误/超时、历史隔离与持久化、金额/包装计算及未知数量。不把T6检索质量指标当作Agent推荐/健康边界的新评测结果。
