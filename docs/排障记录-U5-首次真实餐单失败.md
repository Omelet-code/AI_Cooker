## 2. 后端定位

当前部署代码来自 5b09。MealPlanningServiceImpl 在需求理解、候选检索返回后，对每个完整 MealRecipeFacts 调用 `policy.safeTree`，然后才构造摘要并进行第二次模型组餐。

本次理解和候选阶段已完成，但只有一次模型调用，UNSAFE_CONTENT 因而定位到组餐前完整候选事实的安全检查；不是 Key 鉴权失败，也不是未设置个人默认人数造成的澄清。

MealPolicy 会递归扫描全部字符串，遇到 URL、HTML、注入指令或诊疗关键词直接抛异常，任意一个候选触发即可终止整餐。完整事实包括步骤、原始食材行和 additionalContent；现有 HowToCook 菜谱附加内容中确有 URL，例如咖喱炒蟹、响油鳝丝、水煮鱼等。完整原文与最终展示内容使用相同拦截策略存在兼容问题。

边界：本次未保存候选 ID、理解输出及具体匹配字段，不能断言本次由上述哪道菜、哪个链接或关键词触发。不新增收费请求以补证。建议修复时保留原始事实与指纹，将模型输入/展示的安全投影与事实存储分开，明确不合格候选的隔离及不足时澄清行为，不直接关闭安全检查，也不删除原始菜谱。

## 3. 前端确定复现

用 Vite 加载实际 kitchen/state.ts，注入无网络 API 替身；按页面相同的 Vue watch，在 createdConversationId 改变后 activate 新会话。

结果：创建返回 true，当前会话 11，但 createUnknown=true，createError 与用户截图中的“会话创建等待已停止，结果未知”完全一致。

原因：设置成功会话 ID 后，createBusy 尚未在 finally 清除；成功导航触发 activate → stopWaits(true)，把已经成功的创建误判为等待被取消。此问题与后端餐单失败独立，不应提示用户再次创建。
