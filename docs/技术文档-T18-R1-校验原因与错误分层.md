# T18-R1：校验原因与错误分层

2026-10-09。对应[工作报告](工作报告-T18-R1-指导诊断与停批错误映射.md)，只讨论最新源码和隔离专项。真人第二餐原响应不存在，不能推导其具体拒绝规则或已通过真实生成。

## 为什么传输成功仍会指导失败

模型返回JSON只是传输/格式层成功。服务器还必须核验该餐菜谱集合、字段类型、证据ID、完整步骤覆盖、材料及数值依据、文本安全。可信事实归服务器，模型不能通过“看起来合理”覆盖原量、未知值或权限。`MealGuidePolicy` 每个原拒绝条件继续执行，仅将统一ApiException替换为携带有限定位的 `MealGuideRejected`；Prompt及数值判断不变。

诊断由服务端固定规则和路径构成。例如漏步骤为 `STEP_COVERAGE / guide.recipes[0].explanations`，虚构数量为 `NUMBER_EVIDENCE / guide.preparation[0].text`。未知字段报固定所属对象，不记录恶意键名。异常不携带cause/触发正文；日志框架只接收字段，不接收异常对象。根路径或容器路径是有意限制：不能通过打印解析异常获取不可信键值。

| 拒绝层 | 规则示例 | 保留的行为 |
| --- | --- | --- |
| JSON与严格结构 | JSON_OBJECT、OBJECT_FIELDS、ARRAY_BOUNDS | 重复/未知/尾随JSON、字段集合、数组上下限仍拒绝 |
| 文本类型/长度/展示 | TEXT_TYPE、TEXT_LENGTH、TEXT_FORMAT、TEXT_SAFETY、MEAL_PROMISE | 非文本、空白/超长、Markdown、HTML/链接/医疗/注入及整餐承诺仍拒绝 |
| 引用与覆盖 | RECIPE_ID、RECIPE_REFERENCE、RECIPE_COVERAGE、STEP_TYPE、STEP_REFERENCE、INGREDIENT_REFERENCE、DUPLICATE_REFERENCE、EMPTY_EVIDENCE、STEP_COVERAGE、INGREDIENT_COVERAGE、MISSING_STEPS_NOTICE | 只接受所选真实引用与原全量覆盖，不自动补事实 |
| 数值与资源 | NUMBER_EVIDENCE、PRICE_NUTRITION、RESPONSE_LIMIT | 精确数值依据/价格营养限制、512KiB指导边界不变 |

## 网关错误分层

`ModelGatewayServiceImpl` 的身份/解密路径仍独立。客户端构建和model.call两处才识别 `EvaluationBatch.Stopped`（包含受限异常链遍历，识别后不转发原链），转换为内部 `ModelGatewayException.Reason.EVALUATION_STOPPED`。停止、缺批准上下文和额度不足共用内部资源原因，不能让用户误以为Key失效。

新增枚举的全部生产消费者为 RecommendationServiceImpl、MealPlanningServiceImpl、MealGuidanceServiceImpl，各自将其映射至原 `RESOURCE_LIMIT`。conversation错误白名单、HTTP成功格式及前端无需改变；这是内部原因细化，外部仍为已有资源限制提示。

| 输入故障 | 网关原因 | 业务错误 |
| --- | --- | --- |
| 没保存凭证 | CREDENTIAL_NOT_CONFIGURED | CREDENTIAL_NOT_CONFIGURED |
| 解密失败/空Key | CREDENTIAL_SERVICE_UNAVAILABLE | CREDENTIAL_SERVICE_UNAVAILABLE |
| 受控构建或call拒绝 | EVALUATION_STOPPED | RESOURCE_LIMIT |
| HTTP401/403 | MODEL_AUTHENTICATION_FAILED | MODEL_AUTHENTICATION_FAILED |
| HTTP429 | RATE_LIMITED | MODEL_RATE_LIMITED |
| 其他HTTP错误 | PROVIDER_UNAVAILABLE | MODEL_UNAVAILABLE |
| 网络读取超时 | TIMEOUT | MODEL_TIMEOUT |
| 截断/无效JSON | INVALID_RESPONSE | MODEL_INVALID_RESPONSE |
| 指导业务Policy拒绝 | MealGuideRejected，不伪装网关错误 | 原MODEL_INVALID_RESPONSE、UNSAFE_CONTENT或RESOURCE_LIMIT |

HTTP守卫原来把非2xx/部分坏响应也抛成Stopped；新增原因识别前必须拆开。现在先停批，再抛仅含状态码、空headers/body的安全HTTP异常；无效响应抛固定响应异常。供应商错误正文、Key和Prompt不进入业务错误。下一次调用面对已经停批的状态才是EVALUATION_STOPPED；不能覆盖第一次真实错误分类。

## 共享锁、业务通知和账本

原 `transport.call` 在返回时释放锁，业务VALIDATE_GUIDE随后才运行。只在Policy catch里stop，会留出另一个线程发送的空隙。新增 `withGuideValidation` 在实际Service中覆盖网关调用与Policy，受控模式持有同一batch monitor；`call` 重入同一锁，不死锁。普通模式直接调用，`guideRejected` 空操作，保持正常失败后用户显式新动作的既有行为。

```text
transport.withGuideValidation(() -> {
    response = gateway.completeGuide(request); // 单次、事务外
    保存已知usage；执行原软预算检查；
    try { return policy.validate(response, 完整事实, 完整材料); }
    catch (业务拒绝) {
        transport.guideRejected(); // 同锁追加拒绝并GLOBAL_STOP
        throw 原安全拒绝；
    }
});
```

账本例序为 METHOD_RESERVED → HTTP_RESERVED → SUCCEEDED → GUIDE_REJECTED → GLOBAL_STOP。SUCCEEDED仅表示该次传输完成，业务失败另行追加，不改写成功、不退款，也不创建新的真实账本。后续两个默认客户端共用该批次，构建或call均在HTTP前被拒绝。独立计数方法尝试和HTTP保留，不把它们等同供应商账单；失败usage未知继续null。

`MealPersistenceService.fail` 的GUIDE分支、事务和GET未改。只有GUIDE动作FAILED，已选套餐保持SELECTED；同键失败不会重新执行，旧成功指导仍可读。新增Spring注入构造器使用全局提供者，原构造器供普通模式兼容。没有在PG事务中等待模型。仅本进程共享锁，不是分布式锁或供应商恰好一次计费保证。若写账本失败，本地stopped已置位；不能声称业务事件必然持久化。若进程在校验前崩溃，不恢复旧账本。

## 验证与证据的分工

新增12个JUnit方法：安全诊断3、网关分类6、实际业务停批链3；多个故障样例在单方法内循环，不增加用例计数。合成事实/持久化替身＋实际默认DeepSeek网关/Service/Policy＋本机HTTP/独立TempDir账本验证业务拒绝接线及并发停发。普通模式和GET接口替身验证调用不被永久禁用。

另5项真实隔离PG/认证HTTP验证合法完整指导、失败保留选择、历史回看及失败同键不调用，外部模型替身；B1默认query的临时PG接线仍通过。加上未改的协议/Policy专项，总计46项独立用例当前通过。精确运行、红灯/测试配置错误/修复后绿灯见工作报告。没有宿主业务库或真实模型验收，也没有全量、哈希、package或业务启停。

## 面试追问与自检

1. JSON合法为什么仍失败？类型/证据/覆盖/数值/安全属于业务契约，不能由传输状态代替。
2. 为什么不用异常消息直接诊断？消息可能含模型正文和秘密；有限规则及固定字段路径足以定位分支。
3. 未知字段怎样定位？报告服务端已知容器路径，禁止回显任意键。
4. 为什么识别Stopped要在两处？构建可先检查已停止，call才保留方法额度，故障发生阶段不同。
5. 为什么非2xx不继续抛Stopped？第一次错误属于供应商分类；已经停批不能反向把401改成资源拒绝。
6. 为什么锁覆盖业务校验？单独stop只能防未来调用，无法挡住返回与校验之间已开始的并发发送。
7. 传输成功能退额度吗？已发生的尝试不能取消或改写，业务拒绝必须追加独立事件。
8. 修复后能宣布第二餐正常吗？不能。原响应未知，真实模型与部署重测需独立授权。

自检：能分别解释模型格式层、指导业务层、凭证层、资源层；能指出三个枚举消费者；能说明固定路径如何避免任意键泄漏；能画出并发QUERY等待的锁范围；能区分mock接缝、真实隔离PG与真实供应商证据。

练习一：画出线程A在Policy拒绝、线程B试图query的时序，标出锁获取、拒绝事件与零新增HTTP的检查点。练习二：给合成合法指导分别注入漏步骤、未选recipeId和新温度，预测规则及固定字段路径，并确认成功输入原文不被自动改写。不要用真实Key或原真人账本练习。
