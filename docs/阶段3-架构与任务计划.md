## 2. 业务与应用架构

```text
Vue聊天/设置
  → conversation Controller/Service（认证、会话归属、幂等轮次）
  → agent编排 → policy规则
      ├─ identity凭证Service → 模型网关 → DeepSeek官方
      ├─ retrieval Service → PG混合检索 + 百炼query向量
      └─ recipe Service → 真实详情与可见性
  → conversation短事务保存结果 → REST/SSE → 用户选菜
  → shopping Service（确认已有食材/份数/位置）
      → 商品Provider → BigDecimal成本 → 购物清单快照
```

业务模块边界沿用根文档。Controller只调Service，跨模块不访问Entity/Mapper。模型理解、工具选择和语言解释不承担金额计算、权限验证、幂等事务或事实来源。

3A-1推荐两次模型请求：第一次结构化输出intent/约束及明确澄清项，经Bean Validation后调用生产检索；第二次根据真实候选返回推荐ID和有依据的理由。ID必须为本轮候选子集，菜名/食材/做法等由Service渲染，不采纳模型捏造事实；不把自然语言看似符合当作资格验证。

3A-2再引入工具循环，建议仅白名单 `search_recipes`、`get_recipe_details`。后一工具只接本轮候选或用户明确选定且已重新验证可见的ID；前者由可信用户上下文注入viewerUserId。所有不受支持的动作都拒绝；没有结果或硬条件冲突时询问是否放宽，不能自动忽略约束。

## 3. 技术选择与初始上限建议

模型使用官方HTTPS、Chat Completions、deepseek-flash和按账号Key。原生Spring AI DeepSeek/通用兼容/自写HTTP的3候选对比见ADR-008；推荐手工原生适配。非思考/普通JSON+Java校验作为MVP默认，strict Beta与思考链后置。

固定流水线 vs 有界工具循环 vs 自主规划：流水线最容易测试和学习，工具循环体现Agent决策但需预算和授权控制，自主规划复杂度不适合本MVP。采用前两者递进，全部在一个运行时Agent中完成。

会话先用自有PG表和有限历史装配，不直接用框架Memory替代业务归属。SSE优先Spring MVC的SseEmitter/等价MVC方案；不为流式功能迁移整套WebFlux。Spring AI内部响应类型不作为前端契约。

建议默认：3A-1每轮LLM最多2次；3A-2最多4次、工具总数最多3次，其中收费query Embedding最多1次，候选最多5道。模型每次输出上限2048 tokens、输入上下文设有限字符/消息预算，最多最近6个完整用户/助手轮次，超过长度再裁剪；字符上限不是精确token计量。工具结果也计入预算，不能绕过限制。

建议模型连接5秒、单次模型响应30秒、整轮90秒，百炼沿用已签收适配的超时并受整轮剩余预算限制；最后以Mock故障测试验证取消和真实终止语义。超时不能只是前端停显示而后台继续无限请求。默认无供应商自动重试；空/截断JSON、未知工具、超过次数均安全失败，暂不加额外收费修复请求。

上限是资源策略，不是费用承诺。记录实际LLM/Embedding调用数、输入/输出tokens及usage是否可用；供应商usage缺失时显示未知，不填0。收费评测另报调用计划并获批准，不在普通mvn/npm测试中触发。

## 4. 数据、状态与事务建议

建议3A用三表：conversation（user_id/title/timestamps）、conversation_turn（会话、用户、UUID requestId、输入哈希、顺序/状态、约束、候选、错误/usage/时间）、chat_message（turn_id/role/content/sequence）。消息是用户历史，不是无限Prompt原样落库；工具正文/思考内容默认不写历史或日志，只保留必要引用/统计。核心状态和归属用关系列，扩展约束/候选快照可用JSONB。

同一用户+会话+requestId唯一；同键同内容返回已有轮次，不重跑模型，同键异内容409。同会话只允许一条运行轮次，跨页提交冲突返回明确状态，不吞掉用户消息。推荐状态PENDING/RUNNING/SUCCEEDED/FAILED；失败原因区分凭证、模型、校验、检索、资源上限和进程中断。

短事务先注册轮次，再执行外部请求，短事务完成消息和结果；不能把模型等待放进@Transactional。后台异常/重启产生的遗留RUNNING需原子标为中断或租约到期，由用户发新轮次，不能自动重放收费请求。该模型不承诺供应商收费恰好一次。

迁移建议V8承载3A会话，V9承载3B购物；只有任务领取时才冻结序号/内容，不提前创建表，不更改V1～V7。购物建议shopping_list/items及商品快照；用户、原菜谱、份数、位置和已有食材确认信息应可追溯。

在已认证线程获取可信执行上下文和受控模型客户端，再交给有界执行器；不要依赖SSE线程自动继承SecurityContext，不暴露任意userId解密接口，不在共享字段缓存明文Key。

## 5. HTTP/SSE契约方向（草案）

复用阶段二Key保存/删除/状态接口，设置页只提交本次输入并在成功后清空，不读回完整Key、不写Web Storage、不预设格式前缀。

建议POST /api/conversations、GET分页会话、GET会话消息；POST /api/conversations/{id}/turns（requestId/content）创建轮次202；GET轮次回读状态和结果；GET轮次events建立SSE。各资源验证当前用户；写操作复用CSRF。旧根文档messages/stream草案不是已发布接口，冻结时明确替换与命名，不能两套都悄悄实现。

POST有CSRF并承担一次执行，GET SSE仅订阅结果，自动重连不得产生新调用。事件建议accepted/status/candidates/answer/done/error；只发送经校验的候选及解释，不发送Key、Prompt、工具原始结果或reasoning_content。首次支持状态与校验后答案分段推送，不冒充供应商token实时透传；若要直接流式输出，先解决结构化结果与输出检查后再单独验收。

MVP不要求逐token断点重放，刷新/重连回读PG权威轮次，最多重订阅当前状态；终态关闭连接，后端中断需明确错误。Cookie认证仍遵循已接受策略，SSE遇401由统一请求层续期一次再连接，不能无限重连。

3B建议POST /api/shopping-lists、GET列表/详情、显式请求匹配商品；生成/匹配是用户确认操作，不将自动保存清单、购买或支付开放成无人确认的模型写工具。

## 6. 采购与预算规则

当前T5没有预算和已有食材覆盖率参数，不修改已签收RRF作为捷径。3A-1记录预算意图但不能声称已精确筛选；3B通过确定性成本评估候选后再提供预算解释与排序。

沿用用户已确认的“已有食材不计本次需求成本、只算实际用量”的预算口径，并另列完整包装采购支出。建议术语为预估需求成本、按商品价折算的消耗成本、整包装采购支出，最终字段名需契约冻结。10g葱/100g包装按比例折算与整包金额分别展示，不能混淆。

已有食材优先选结构化食材并明确“足量/已具备”；无法确认名称或单位时不自动抵扣。份数缺基准、原料适量、g/ml/个不互换、价格不可用均标不可估算。Mock商品无购买能力时URL为null或明确演示，不伪造美团商品链接；生产适配再做域名/跳转安全校验。

**2026-10-06用户已确认：** 超预算时保留清单并提示，不自动换菜或放宽预算；成本未知时展示可估算小计和未知项，不称满足预算，不把未知项当0或免费。具体字段/计算契约仍待终审；此确认不自动授权T16/T17/F3-D实现。
