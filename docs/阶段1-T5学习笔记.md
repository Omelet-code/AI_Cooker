# T5 学习笔记：混合检索为什么这样设计

> 状态：对应已验收的 T5 实现；代码入口见 `RecipeSearchServiceImpl`。

## 1. 从熟悉的查询方式出发

在传统 Spring Boot + MySQL 项目中，你可能会在 Service 里组装查询条件，Mapper 用 `WHERE` 和 `LIKE` 查数据库，再按一个字段排序。Cooker 的检索仍遵循“Service 定规则、Mapper 查数据”，只是排序需要同时考虑三类信息：

| 需求 | 对应技术 | 为什么 |
|---|---|---|
| “30 分钟内、只用电饭煲” | 结构化过滤 | 这是必须满足的事实条件，不能靠相似度猜测 |
| “番茄鸡蛋”“西红柿” | 菜名/食材精确匹配、别名和中文全文检索 | 准确识别具体实体和词语 |
| “想吃清淡一点” | 百炼查询向量 + pgvector | 允许查询和菜谱使用不同措辞 |
| 两路结果合并 | RRF | 两种分数单位不同，先比较名次更稳定 |

调用顺序是“资格筛选 → 两路召回 → 按菜谱去重 → RRF → 返回原因码”。硬条件必须在每路取 Top 30 之前执行。例如先取 30 道再排除超时菜谱，可能剩下很少结果，漏掉第 31 道合格菜谱。

## 2. PostgreSQL 中文词法检索

T4 已把检索块的文本写入 `recipe_search_document.content`。PostgreSQL 的生成列 `tsv` 用项目配置的 `zhparser` 对中文分词；GIN 索引帮助查找包含查询词元的块。它类似 MySQL 全文索引，但这里的中文分词规则由数据库扩展明确提供。

词法检索适合“番茄”“鸡蛋”等明确词语。菜名完全一致和食材别名应优先走确定性匹配；`pg_trgm` 负责近似菜名，例如少字或写法接近的标题。它不是理解“清淡”的语义模型。

## 3. 查询向量与文档向量

导入时，菜谱块用 `text_type=document` 生成 1024 维向量并存储。搜索时，用户输入用相同模型、相同维度、`text_type=query` 临时生成查询向量。

```text
菜谱块 ──document──→ 数据库中的向量
用户输入 ──query────→ 本次请求的临时向量
                         ↓
              与候选块比较余弦距离
```

`pgvector` 的 cosine distance 越小，表示向量方向越接近。T5 只有 1850 个块，先做精确扫描；没有证据表明需要 HNSW 等近似索引。查询向量服务不可用时，已就绪的词法通道仍应返回结果；普通自动化测试使用 Fake Provider，不消耗百炼额度。

## 4. 为什么按菜谱去重

一道菜可能有多个 `steps` 块。若直接把块当成菜谱计算分数，步骤多的菜会凭数量占优。正确做法是每个通道先为一道菜保留最佳块、确定一道菜的名次，再合并两路菜谱名次。

RRF 的形式为 `1/(60 + 词法名次) + 1/(60 + 向量名次)`；未进入某通道就不加那一项。例如词法第 1、向量第 5 的菜得 `1/61 + 1/65`。RRF 不需要把全文分数和余弦距离强行换算到同一量纲。

## 5. 模块边界与数据库迁移

`recipe` 模块拥有分类、时间、食材和厨具事实，因此它对外提供只读资格筛选 Service；`retrieval` 模块拥有检索投影与排序 SQL。这个边界与你熟悉的 Controller → Service → Mapper 一致，只是在同一个 Spring Boot 进程内把业务能力再分包。

数据库结构变更使用 Flyway 新增 V3。已经应用的 V1/V2 即使只改一行注释，也会改变校验和，导致启动校验失败。

## 6. 本阶段建议补学

1. PostgreSQL 全文检索：`tsvector`、`tsquery`、GIN、`zhparser`。
2. PostgreSQL `pg_trgm`：近似字符串匹配及其与全文检索的区别。
3. pgvector：向量维度、余弦距离、精确扫描。
4. Embedding 的 `query/document` 两种输入角色。
5. RRF 与“先过滤、再召回、后融合”的执行顺序。
6. Flyway 迁移校验和、MyBatis 显式 SQL 与参数化查询。
7. Fake Provider 和 PostgreSQL 集成测试各自验证什么。

自检：如果把“没有烤箱”放到 RRF 之后才过滤，会漏掉什么？如果一道菜有 8 个步骤块，为什么只能算一道菜的名次？如果百炼暂时不可用，哪些已经存储的数据仍能参与搜索？

## 7. 建议按这个顺序审查代码

1. 从 `RecipeSearchCriteria` 看输入和 `null`/空厨具集合的区别。
2. 在 `RecipeSearchEligibilityMapper.xml` 找分类、时间、必需厨具、排除食材和当前可见性过滤。
3. 在 `RecipeSearchMapper.xml` 看两个通道如何过滤版本、取每道菜的最佳块、各取 Top 30。
4. 在 `DashScopeEmbeddingModel` 找 `document` 与 `query` 的请求参数。
5. 在 `RecipeSearchServiceImpl` 手算 RRF，确认异常只在查询向量服务故障时降级。
6. 在 `RecipeSearchPostgresTest` 看真实 PostgreSQL 的权限、别名、时间和 chunk 去重断言。

参考资料：[PostgreSQL 全文检索](https://www.postgresql.org/docs/18/textsearch-controls.html)、[pg_trgm](https://www.postgresql.org/docs/18/pgtrgm.html)、[pgvector](https://github.com/pgvector/pgvector)、[百炼向量化](https://help.aliyun.com/zh/model-studio/embedding)。
