## 实现理由

列表和详情的 SQL 都在 `recipe_source` 上限制为系统公开菜谱或当前用户拥有的私有菜谱；未命中统一 404 `RECIPE_NOT_FOUND`，避免通过状态区分“存在但属于他人”和“不存在”。当前用户只由 T7 `CurrentUserService.requireUserId()` 得到，recipe 模块不碰 identity Mapper/Entity，HTTP 不接收 userId。

列表用 `COUNT + SELECT` 两条 SQL，卡片收藏状态在分页 SQL 中一次 `LEFT JOIN favorite_recipe` 获取；详情只固定查询卡片、原料、步骤、厨具四组，不按子项逐条查，避免 N+1。普通菜名 keyword 先按字面量转义 `\\`、`%`、`_`，再作为 MyBatis 参数绑定；列表按 `recipe.id ASC`，收藏按 `created_at DESC, recipe.id DESC`，同一时间也有稳定次序。数据库 BIGINT 在 JSON 中转十进制字符串，`numeric` 用 `BigDecimal.toPlainString()`，未知事实保持 `null`。

收藏先检查资源对该用户可见，再在事务中 `INSERT ... ON CONFLICT (user_id, recipe_id) DO NOTHING`。唯一约束是并发最终裁决；重复添加不更新首次收藏时间。取消使用带 `user_id` 的 DELETE，未收藏亦成功；他人私有菜谱仍先返回 404。收藏与做菜历史是不同事实，T9 没有实现 T10 记录。

## 待验、风险与复现

- F2-B real 浏览器页面的列表、详情、收藏/取消、刷新与换账号隔离仍需前端会话和主架构取得证据；本报告的后端 HTTP 成功不等于浏览器签收。T7 关闭浏览器重开、访问 JWT 实际过期后的续期及双标签 Cookie 竞争也仍待阶段二验收。
- Java HTTP 测试客户端在连续写操作时按冻结契约重新获取 CSRF；浏览器共享请求层对明确的 `CSRF_INVALID` 有一次取新 token 与重试。此项不改变 T7 认证策略。
- 页码很大时 PostgreSQL OFFSET 扫描可能较慢；MVP 当前采用契约指定的页码分页，不宣称大规模性能。私有用户菜谱尚不能上传，测试用独立库构造其可见性边界。
- 当前进程 JWT Secret 是仅在进程环境存在的临时值；正式部署需稳定 Secret/HTTPS，重启会使旧访问 JWT 失效但可按契约尝试续期。PID 会变化，联调前重查健康端点。
- 复现：在指定工作树 `backend` 使用 JDK 21、Docker Desktop，运行 `mvn test`；Testcontainers 自动创建独立库。浏览器/HTTP 先取 `/api/auth/csrf`、注册/登录，再请求 `/api/recipes`；收藏写入送 `X-XSRF-TOKEN`，失败仅按契约有限刷新。代表性只读 SQL：`SELECT version, success FROM flyway_schema_history ORDER BY installed_rank;`、`SELECT count(*) FROM recipe;`、`SELECT count(*) FROM favorite_recipe WHERE user_id = <测试用户ID>;`。不把真实凭证复制到命令输出或文档。
