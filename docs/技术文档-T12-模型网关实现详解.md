# T12 模型网关实现详解与学习指南

## 1. 本切片解决的问题

业务代码不应该到处拼模型 HTTP 请求，更不能让调用方任意提交 API Key、模型名或 URL。T12 在 `agent` 模块提供一个窄的 Service 接口：接收有限消息，按当前登录用户取出已加密保存的 DeepSeek Key，执行一次同步模型调用，再把受控结果交回调用方。

这只是模型访问基础设施，不是完整聊天 Agent。它不会保存会话，不会搜索菜谱，不会调用工具，也没有 HTTP Controller。

## 2. 文件职责与请求路径

```text
调用方
  -> ModelGateway.complete(ModelChatRequest)
      -> 校验消息数量、内容长度、角色与输出模式
      -> CurrentUserService.requireUserId()
      -> LlmCredentialService.decryptCurrentUserCredential()
      -> DeepSeekChatClientFactory.create(本次 Key, 输出模式)
      -> ChatModel.call(Prompt)
      -> 检查响应、JSON 语法、截断状态与 usage
      -> ModelChatResponse
```

- `ModelGateway`：Agent 模块自己的 Service 接口。
- `ModelChatRequest` / `ModelMessage` / `ModelOutputMode`：内部调用 DTO。`toString()` 不暴露正文。
- `DefaultDeepSeekChatClientFactory`：集中固定 API 地址、模型、超时、token 上限、thinking 与 JSON 输出选项。
- `ModelGatewayServiceImpl`：串起当前用户身份、T8 凭证 Service、参数映射、一次调用和错误分类。
- `ModelGatewayException`：只携带安全分类和面向内部调用的简短信息，不保留供应商异常 cause。
- `ModelGatewayProtocolTest`：用本机 HTTP 服务验证真实序列化与凭证头，不访问外网。

## 3. 为什么先校验，再取身份与凭证

输入不合法时应尽早失败，避免不必要地访问身份依赖、解密凭证或调用供应商。当前限制如下：

| 项目 | 规则 | 原因 |
|---|---|---|
| 消息数 | 1 到 16 | 限制请求规模和上下文长度 |
| 总正文 | 不超过 20,000 Unicode 码点 | 按用户感知字符计量，避免 UTF-16 补充字符被算成两个 |
| 角色 | system、user、assistant | 与本次同步聊天契约一致 |
| 正文 | 不可空白 | 避免无意义请求 |
| JSON 模式 | 提示中必须同时提到 JSON 和输出意图 | 让模型指令与 JSON response format 一致 |

码点计数使用 `String.codePointCount`。Java `String.length()` 返回 UTF-16 code unit 数；emoji 等补充字符通常占两个 code unit，因此不能用它代表可见字符数。

## 4. 当前用户凭证与并发隔离

服务不接收 `userId` 或 API Key 参数，而是依赖 `CurrentUserService` 获取安全上下文中的身份，并调用 T8 已有的 `LlmCredentialService` 解密当前用户凭证。这遵循模块边界：Agent 不访问 Identity 的 Mapper 或 Entity。

客户端对象在每次请求中创建，API Key 只被设置为这个客户端的 Authorization header。没有静态字段、单例客户端 Key 或 Key 缓存。并发测试让两个用户同时请求本地服务，并检查正文标记和 Authorization header 成对匹配；另一个断言在 Key 轮换后下一次请求使用新值。

Java 字符串是不可变对象，框架和 JVM 可能暂时保留副本，所以不能承诺请求结束时内存内容会立即清零。能做的是缩短引用生命周期，并避免把 Key 放进全局配置、日志、异常、DTO 或缓存。

## 5. 固定协议与安全界限

客户端固定使用官方 HTTPS 基址和 `/chat/completions`，模型固定 `deepseek-flash`，输出最多 2048 tokens。连接等待最多 5 秒，响应读取最多 30 秒。Spring RetryPolicy 的最大重试次数显式为 0，使一次 Service 调用最多发出一次供应商请求，避免隐式重复计费。

结束原因与正文格式是两条独立校验轴。`finish_reason=LENGTH` 表示生成因输出上限而结束，无法保证正文完整；因此必须在 TEXT/JSON 分支之前统一拒绝，且大小写不敏感。原逻辑把判断放在 JSON 分支内，TEXT 模式只检查正文非空，于是非空截断文本被误当成成功。这是审查发现的 R1。

JSON 模式另通过 Spring AI `ResponseFormat.Type.JSON_OBJECT` 请求结构化输出；返回后仍要用 Jackson 解析正文并拒绝尾随内容。JSON mode 是供应商侧约束，不能替代服务端校验。即使模型返回语法上完整的 JSON，只要结束原因为 `LENGTH` 仍必须拒绝；反过来，`finish_reason=STOP` 也不能免除 JSON 语法检查。协议回归使用真实 Mock HTTP 响应，分别覆盖 TEXT/JSON 与大小写两种 `length`，并保留原有正常结果、空响应和畸形 JSON 断言。

供应商 401/403 表示供应商拒绝 Key，不是 Cooker 用户登录失效；429 单独分类；网络读取超时分类为 TIMEOUT；其他传输错误归为供应商不可用。异常不保留底层 cause，防止之后有人打印异常链时意外带出供应商响应或请求信息。

Spring AI 2.0.1 的 DeepSeek 模型在“空响应”和“没有 choices”分支会以 WARN 记录 Prompt。因此应用配置将该 logger 限制在 ERROR，协议测试实际挂载日志 appender 并确认唯一消息标记不出现在输出中。遇到依赖升级时应重新核对这一行为。

## 6. Spring Boot + MySQL / Controller-Service-Mapper 类比

可以把本 Service 理解成普通 Spring Boot 业务 Service 的一个外部 HTTP 适配场景：

- Controller 将来只负责接 HTTP DTO、校验格式、调用 `ModelGateway`、转换响应；本切片尚未创建 Controller。
- `ModelGatewayServiceImpl` 负责应用业务顺序，相当于 Service 实现。
- 本切片没有 Mapper，也没有 SQL `WHERE`，因为这里没有属于 Agent 的持久化数据。Key 的读取被交给 Identity 的 Service，而不是跨模块直接查表。
- 将来若聊天历史需要存入 MySQL/PostgreSQL，应由 conversation 模块定义 Mapper 和事务规则；不要把消息表或 Mapper 塞入 `common` 或模型适配器。

身份边界与 SQL `WHERE user_id = ?` 的目标相似：每个用户只访问自己的 Key。区别是 T12 通过当前安全上下文和 Identity Service 施加边界，而不是由 Agent 自行写 SQL 条件。

## 7. 错误分类

| 分类 | 示例 | 说明 |
|---|---|---|
| `INVALID_INPUT` | 空消息、超长内容、JSON 指令不匹配 | 调用参数不满足 T12 约束 |
| `AUTHENTICATION_REQUIRED` | 当前请求无登录身份 | Cooker 身份失效 |
| `CREDENTIAL_NOT_CONFIGURED` | 当前用户没有 DeepSeek Key | 由 T8 Service 识别 |
| `CREDENTIAL_SERVICE_UNAVAILABLE` | 解密或凭证读取失败 | 不向调用方泄漏密文或内部原因 |
| `MODEL_AUTHENTICATION_FAILED` | DeepSeek 401/403 | 供应商拒绝 Key，与 Cooker 登录分开 |
| `RATE_LIMITED` | DeepSeek 429 | 供应商限流 |
| `TIMEOUT` | 连接后读取超时 | 有固定等待上限，无自动重试 |
| `PROVIDER_UNAVAILABLE` | 其他 HTTP/网络错误 | 简化为供应商不可用 |
| `INVALID_RESPONSE` | 空 choices、空正文、错误 JSON、截断 JSON | 不把不可用模型输出传给后续 Agent |

未来 Controller 若公开此接口，应另行定义稳定的 HTTP 状态码与 API error code 映射；T12 没有暴露 API，因此没有修改公共错误契约。

## 8. 测试策略

`ModelGatewayProtocolTest` 启动 loopback `HttpServer`，并把测试工厂指向随机本地端口。测试覆盖固定模型与路径、JSON 参数、stream=false、thinking=disabled、不含 reasoning_effort、每次一次请求、两用户并发隔离、凭证轮换、401/429/503、超时、无凭证/解密失败、内容长度、空/错误 JSON、TEXT/JSON 大小写截断、usage 缺失，以及异常与日志不包含假 Key、独特 Prompt 或原始模型正文。

Mock 服务只在回环地址运行，API Key 均为测试构造的假值。这里的协议验证没有证明真实 DeepSeek 账号、额度、网络出口或实时供应商响应可用，也不会产生供应商费用。

## 9. 面试练习题

1. 为什么 Key 必须按当前用户请求时解密，而不是放进 `application.yml` 或全局 `ChatModel` Bean？
2. 并发用户使用共享模型客户端时，哪几种设计会造成 Authorization header 串号？本实现如何避免？
3. `String.length()` 与 `codePointCount()` 的差别是什么？对请求限制有何影响？
4. 为什么设置 JSON response format 后，服务器仍需要解析并验证正文？
5. `finish_reason=length` 时正文可解析，为什么仍应拒绝？
6. 模型 401 与 Cooker 身份 401 为什么不能混为一谈？
7. 禁用重试对费用、用户体验和短暂网络故障分别有什么影响？
8. 为什么供应商异常不直接作为 `ModelGatewayException` 的 cause 保留？
9. 当前用户的隔离在没有 Agent Mapper 的情况下由哪个模块负责？它和 SQL `WHERE user_id = ?` 的边界目标有何相似与不同？
10. 如何用本地 Mock HTTP 服务证明实际发出的 JSON、请求数和 Authorization header？

## 10. 自测题与练习

### 自测

1. 不登录时调用 `complete`，会在哪一步失败？是否会读取 Key 或请求供应商？
2. 假设 20,000 个码点全部是 emoji，`String.length()` 大约是多少？为什么上限仍允许该请求？
3. DeepSeek 返回 HTTP 429 时，内部错误分类是什么？是否会自动再试？
4. usage 对象缺失时，为什么响应里的 usage 应为 `null`，而不是伪造 0？
5. 一个合法 JSON 对象后面又跟文本，为什么应该判为非法响应？

### 动手练习

1. 为最多 16 条消息增加角色序列检查，例如强制最后一条是 USER；写测试证明拒绝发生在读取凭证前。先评估该规则是否属于产品契约，再实现。
2. 为 `ModelGatewayException.Reason` 设计 Controller 层 HTTP 映射测试，确保供应商鉴权失败不会清除 Cooker 登录状态；不要在 Agent Service 中引入 Controller 依赖。

## 11. 后续学习路径

先读 DTO 和 `ModelGateway`，理解模块公共边界；再读 `ModelGatewayServiceImpl`，顺着身份、凭证、参数转换和失败分类走一遍；之后读客户端工厂，核对超时、重试和供应商选项；最后跑 `ModelGatewayProtocolTest`，观察 Mock HTTP 请求。理解本切片后，再单独学习 Spring AI 的 ChatModel/Prompt/Generation 抽象、Spring RetryPolicy，以及 Java Unicode 码点模型。
