## 1. 目标与边界

在阶段 1 已完成的菜谱与混合检索基础上，建立用户身份与个人菜谱记录，并在浏览器完成真实交互。阶段 2 负责：用户名密码注册登录、JWT 与“记住我”、用户隔离、DeepSeek Key 加密保存、真实菜谱列表/详情、收藏、已做菜谱记录与基础统计，以及上述能力的最小前端页面。

不做：家庭库存 CRUD/流水/自动扣减、购物、Agent 对话、聊天历史、用户自定义菜谱上传、Spring Cloud、RabbitMQ，也不调用 DeepSeek 或真实收费模型接口。Key 设置页面留待 Agent 阶段，T8 本阶段以真实接口及数据库测试验收。阶段 2 完成不自动授权阶段 3。

共享接口已冻结为 `docs/阶段2-前后端接口契约.md` 的 s2-api-v1；任务目录、模型配置、汇报和真实联调证据见 `docs/阶段2-双会话任务与真实联调验收.md`。阶段 2 必须是 Vue → Spring Boot → PostgreSQL 的真实闭环，Mock 仅用于尚未就绪接口的开发或测试，不满足签收。

“已有食材”需求暂不取消，但只作为后续单次对话或购物流程的用户声明，不入持久库存。系统不能承诺自动同步、自动抵扣或完成烹饪后自动扣减。如何匹配标准食材与单位的可选后续方案见第 8 节。

## 2. 业务对象与归属

| 对象 | 归属 | 关键语义 |
|---|---|---|
| `app_user` | `identity` | 用户名唯一、密码强哈希、账号状态；主键沿用现有 `BIGINT` 风格 |
| 登录续期凭证 | `identity` | 每次登录/设备对应可撤销凭证；只存随机令牌哈希、到期与撤销信息 |
| `user_llm_credential` | `identity` | 按用户保存 DeepSeek Key 的认证加密密文，不向前端回显明文 |
| `favorite_recipe` | `recipe` 的用户菜谱能力 | 用户与菜谱唯一关联；收藏不等于做过或喜欢评分 |
| `recipe_cook_record` | `recipe` 的用户菜谱能力 | 每次真实完成烹饪记录一条事件；可附 1～5 分主观喜爱评分 |
| `conversation`、`chat_message` | 后续 `conversation` | 历史对话，不属于阶段 2 的“做过的菜谱” |

现有 `recipe_source.owner_user_id` 是未来私有菜谱的预留字段，不代表已经实现用户上传。`recipe` 的个人菜谱 Service 接收身份层给出的当前 `userId`，不得跨模块直接访问 `identity` Mapper/Entity；`identity` 也不应拥有收藏和烹饪记录表。

内部共享身份契约：`identity.service.CurrentUserService` 提供 `requireUserId()`，返回已认证且有效的当前用户 `Long` ID，未登录时产生统一认证异常；Controller 通过该 Service 获取身份，再调用本模块项目 Service。它不接受客户端传入的 userId，不返回数据库 Entity。`RecipeReadService` 提供可见菜谱校验与读取，`RecipeFavoriteService` 和 `RecipeCookingService` 复用它；跨模块不得用 Mapper 绕开边界。HTTP 中仍把 Long ID 输出为字符串。

## 3. 主要流程与接口契约

1. 注册：校验用户名和密码；统一用户名规范并保证数据库唯一；密码只存强哈希。
2. 登录：验证密码后签发短有效期访问 JWT 和随机续期令牌；“记住我”只影响续期凭证及 Cookie 的持久性，不延长访问 JWT。
3. 访问：Cookie 中的 JWT 经 Spring Security 验签并校验到期、签发方、受众；业务从已验证身份取得 `userId`，不接受客户端自行传入的用户所有者 ID。
4. 续期：有效续期凭证原子轮换，生成新访问 JWT；退出登录撤销续期凭证并清 Cookie。访问 JWT 的剩余有效期不能被清 Cookie 直接撤销。
5. 收藏：对可见且存在的菜谱做添加/移除；同一用户、同一菜谱不会重复收藏；其他用户的数据不可读写。
6. 做过：用户明确触发“完成烹饪”，写入完成事件；同一事件幂等重试返回既有结果，新烹饪事件可再次增加次数。可选 1～5 分评分；未评分保持未知。
7. 展示：按用户汇总菜谱的完成次数、最近完成时间和最近一次有效评分；熟悉度仅是由次数计算的展示等级，不视为技能测评。首版展示规则：1～2 次“初尝”、3～5 次“熟悉”、6 次及以上“常做”；0 次不进入做过列表。阈值集中管理，后续可按产品反馈调整。

接口统一使用现有 `/api` 上下文路径：

- `POST /auth/register`、`POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`、`GET /users/me`；登录输入包含 `rememberMe`。
- `PUT /users/me/llm-credential`、`DELETE /users/me/llm-credential`、`GET /users/me/llm-credential/status`；状态只返回是否已配置等非敏感信息。真实 Key 验证留待 Agent 阶段。
- `GET /auth/csrf`、`GET /recipes`、`GET /recipes/{id}`；菜谱浏览是普通数据库读取，不调用混合检索收费 API。
- `POST /recipes/{id}/favorites`、`DELETE /recipes/{id}/favorites`、`GET /favorites/recipes`。
- `POST /cooking-records`、`GET /users/me/cooked-recipes`；写入请求包含 `recipeId`、客户端单次烹饪事件幂等键和可选 `rating`。DTO、分页、错误码、Cookie 和续期规则遵循 s2-api-v1。

同源 Vue 页面可使用 Cookie 请求后端；认证 Cookie 为 `HttpOnly`，生产环境 `Secure`，设置适当 `SameSite`。由于 Cookie 自动随请求发送，写操作仍需 CSRF 令牌；首次登录/注册也需考虑 CSRF 初始化，不能简单全局关闭。前端与后端均不得记录或输出 JWT、续期令牌、明文 Key。

## 4. 数据与事务约束

- 所有新表通过 V4 起的新 Flyway 迁移添加，不能修改 V1～V3。主键风格与现有 `recipe` 表保持一致。
- `favorite_recipe` 唯一键建议为 `(user_id, recipe_id)`；`recipe_cook_record` 对 `(user_id, idempotency_key)` 唯一，但不能对 `(user_id, recipe_id)` 唯一，否则无法重复做同一道菜。
- 两表的 `recipe_id` 引用当前有效的菜谱；展示时从 `recipe` 公共 Service 获取必要快照或摘要，不跨模块直接用 Mapper。
- 评分若存在，仅能为 1～5 整数。展示“喜爱程度”使用最近一次用户主动给出的评分；没有评分时展示“未评分”。“熟悉度”依据完成次数计算，不存成不可追溯的独立真值。
- 完成事件的幂等判定与落库应处于同一事务；重复请求返回相同记录，不新增次数。`POST /cooking-records` 绝不触发库存扣减。
- 续期令牌必须由高熵安全随机数生成，数据库仅存哈希，轮换与撤销采用事务；访问 JWT 的签名密钥仅从环境变量或 Secret 注入，并支持密钥版本标识。
- DeepSeek Key 与密码采用不同处理：密码单向强哈希；Key 需要使用带随机 IV 的认证加密（例如 AES-GCM），密钥主材料由服务端 Secret 注入。前端只能获知“已配置/未配置”。

## 7. 与后续阶段的衔接

- 阶段 3 的 `conversation` 单独保存历史对话；`agent` 通过 `identity` Service 取得当前用户的 DeepSeek Key，不直接读凭证表。
- 阶段 2 最小前端已要求展示收藏、做过的菜谱与评分；阶段 4 打磨全产品页面并联调 Agent/购物。历史对话仍不等于烹饪完成事件。
- 后续购物清单根据本次用户确认的已有食材计算差额；无库存持久化时，“预估消耗成本”和“实际采购支出”必须区分，并说明用户声明食材未经过库存核验。
- Spring Cloud、RabbitMQ 与持久库存仍为后续演进，不在阶段 2 插入空转框架。

## 8. 持久库存的后续可选方案（非 MVP）

以现有 `ingredient` 和 `ingredient_alias` 作为选择器候选：用户先搜索，再选择标准食材 `ingredient_id` 并输入数量、单位；无法匹配的自由文本只保存原文并标记待确认。只有已确认的标准食材、可换算单位与明确用量才允许自动抵扣；“适量”、缺失用量、跨质量/体积转换不得猜测。再次引入库存时，应先做匹配率和单位覆盖率评测，再决定自动扣减的范围。

## 9. 前端技术与学习节奏

沿用 Vue3、TS、Vue Router、Pinia、Vitest；本阶段使用共享原生 fetch 请求层和简单原生组件/CSS。fetch 与 Axios 均能发送 HTTP，当前接口规模下 fetch 不需新增依赖；先集中实现超时、CSRF 和有限续期，再在业务模块里定义 API。暂不引入完整 UI 组件库，避免在最小交互前增加一套组件学习成本。

先解释“页面状态”与“数据库事实”的区别：Pinia 保存当前登录和界面状态，刷新后从真实接口恢复；做菜次数由 PostgreSQL 汇总，不能只在浏览器内加一。熟悉度由服务端给出 code/label，前端不另写不同阈值。阶段结束的自检问题：为什么 Cookie 登录仍需 CSRF？记住我与访问 JWT 有何区别？为什么 ID 用字符串？重复完成与再次做同一道菜如何区分？刷新后如何证明数据来自数据库？
