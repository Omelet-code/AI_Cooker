# D1-B：审批、事务审计、幂等与回滚

日期：2026-10-07。实现目录：`C:\Users\Omelet\.codex\worktrees\5b09\Cooker`。

本文说明显式治理工具的真实实现。数据库验证只使用临时 Testcontainers PostgreSQL；审定包全部默认 DEFER，开发库应用数为 0。D1-A v2 的解析器、固定快照、提案和旧日志均未改。

## 1. 从候选到动作的边界

固定输入是 `.data/d1-a/database-input.jsonl`，固定提案是 `.data/d1-a/manifest.jsonl`，规则为 `d1-a-parser-v2`。读取时先校验文件 SHA-256，再用既有 `RecipeParsePreviewTool` 和同一个 `HowToCookMarkdownParser` 重算，逐字段比较提案。数字表示先规范化，避免 JSON 整数节点和长整数节点造成假差异。

审定包包含 1416 个稳定候选键、每项内容 hash、来源/菜谱/原行 ID、原行及原文 hash、旧新字段和依据。分类为名称数量单位 866、新增漏料 53、移除误解析 6、人数基准 18、词典冲突 52、不确定材料 127、缺人数待复核 294。530 个材料候选带不确定量/单位标识；其中一部分同时属于字段变化或新增类，不能将 530 再加到候选总数。

52 组词典冲突包含原 ID/规范名及每条关联行。已有标准 ID 仅是候选，不表示同名必然同商品。没有逐组批准和逐行明确映射时，不合并身份，不删除旧 ID，也不全表设为 REVIEWED。

审批格式由 `RecipeRepairApproval` 定义。全量覆盖候选，每项决定为 APPROVE、REJECT 或 DEFER，并写明理由。审批没有可任意改写的 `newFields`，未知 JSON 字段直接拒绝。材料还需明确身份处理；新增需确认固定追加排序，移除需确认该原行为非材料误解析。未知量/单位保留 null，纯待复核项不能批准以补造事实。

审批绑定输入 hash、提案 hash、规则版本、审定包 hash、请求 UUID、准确数据库名、JDBC 主机端口/库标识、审定人、允许动作和所有决定。`seal-approval` 只计算内容 hash，既不批准也不连接数据库。内容 hash 不是审定人的数字签名：实际用户授权仍须另行取得，工具本身不能证明外部审批人身份。

## 3. dry-run 与 apply

`dry-run` 是默认治理模式，在只读 REPEATABLE READ 事务里验证目标、源事实、候选和身份处理，不加写锁，不写事实或审计。默认待审模板会在建立数据库连接前被拒绝。它不能当作未来 apply 的保证；apply 必须在自己的事务里重新检查。

apply 顺序如下：

1. 验证固定证据、完整审批和 APPLY 动作；准确数据库名、实际连接元信息与审批目标都必须一致。
2. 在事务内取得治理 advisory lock，锁同请求键的已有批次。相同 hash 返回原收据；不同 hash 拒绝。
3. 以固定顺序对 15 张受保护历史/原文/投影表及 `ingredient_alias` 加 SHARE 表锁；按 ID 升序锁目标 recipe/source/document、材料行、必要规范身份和关联引用。
4. 对照固定公开快照重验系统来源、PUBLIC/null owner、source/document 主键和版本、Markdown/content_hash、人数、菜名、整道目标菜的材料字段、原行和排序，以及必要词典名称/状态。
5. 所有前置校验通过后执行获批身份动作和事实动作。旧行使用原 ID 更新；新增行追加到固定 sort_order；移除仅处理获准误解析行；人数使用固定政策提案。
6. 记录 before/after、影响 recipeId、原行/新增行 ID 映射、新标准 ID、批准决定和保护摘要。事实、批次、条目审计在同一事务提交。

采用 `TransactionTemplate` 明确划定事务，避免依赖同类内部调用的代理行为。Mapper 语句默认超时 20 秒，独立入口事务默认超时 30 秒。全局治理锁使同工具的并发批次串行；表锁封闭“摘要检查完但提交前发生历史写入”的窗口。外部业务事务若交叉持锁仍可能被 PostgreSQL 判定死锁，整批失败并回滚，不能当作部分成功。

SHARE 表锁会暂时阻塞受保护表的写入，适合低频人工维护。本实现保守保护全范围，数据量大时摘要和表锁会增加开销；未来若优化为按依赖保护，需要新的契约和测试，不能直接去掉保护。全表摘要只用于变化检测，不是加密凭证；不查询用户凭证表、不将用户历史原文存入审定包或审计。

## 4. 标准身份与排序

| 动作 | 规则 |
| --- | --- |
| KEEP | 保留原 `ingredient_id`（包括 null）；不能偷偷附加目标 ID 或规范名 |
| REUSE | 明确固定公开词典已有 ID；涉及冲突组时，逐组批准同一规范 ID，并逐行批准映射 |
| RENAME | 只能改本行旧标准 ID 的固定提案名称；所有关联行都须在批准范围，含未批准/私有引用则拒绝；不改变审核状态 |
| CREATE | 明确批准固定提案规范名；已有同名标准身份时拒绝盲插，需改为明确复用；新身份为 UNREVIEWED |

CREATE 涉及冲突组时也需要逐组批准同一新规范名。新增标准 ID、旧材料 ID→新标准 ID 的选择和执行结果写入审计。旧规范 ID 即使不再被本次行使用仍保留，因为历史或 Mock 服务可能引用它。没有新增虚构别名或商品等价关系。

新行按“该菜原最大 sort_order + 此菜新增候选的固定序次”追加。仅批准部分新增时允许空缺序号，旧行不移动；`UNIQUE(recipe_id,sort_order)` 继续兜底。已有字段变化使用固定提案原位置，旧行 ID/raw_line 不变。REMOVE 回滚按原 ID、原事实、原行、原排序插回；序列空洞不表示重复应用或事实丢失。

## 5. 审计表和幂等

V15 只建两个审计表及索引，不改 V1～V14、不改 recipe 表。批次唯一 UUID、hash、规则、精确目标、状态与时间使用关系列；条目 `(batch_id,candidate_key)` 唯一。JSONB 保存可变的 before/after、批准内容、映射和原收据，不能替代唯一键或实际业务字段。

状态只有 APPLIED 和 ROLLED_BACK：失败事务没有残留的“半成功”批次。数据库唯一冲突、审计后置异常、业务校验异常均使整批事实和审计一起回滚。并发同键先经过同一事务 advisory lock，后来的调用看到原收据，不创建第二组 ID。

同键同内容重放返回原收据，不重新推断现在的事实是否仍相同；收据代表原批次执行结果。若已回滚，apply 的同键重放也返回 ROLLED_BACK，不会静默重新应用。要支持同一审批的显式回滚，原审批应包含 ROLLBACK；修改 allowedActions 会改变审批 hash，不能用同键异内容覆盖原批次。

## 6. rollback 的前置条件

rollback 只接受原批次的同一审批/hash和准确目标。事务内先锁批次与保护范围，再核对目标菜全量事实/原文等于审计 after，规范身份/引用/别名也等于 after，历史/投影摘要等于保存摘要。任何后续修改或新依赖都拒绝整批恢复。

恢复顺序为删除本批新增关联、原 ID 恢复旧关联/字段和人数、删除无引用无别名的本批新规范 ID、恢复本批规范名称；最后再比对 before 和保护摘要，并在同事务记录 ROLLED_BACK。旧 ID 从不删除。唯一冲突或新依赖不会被强行覆盖。

保护范围包括原Markdown/parse_warnings、步骤、厨具、收藏、做菜记录、餐单/动作/候选、指导、采购/报价各层快照及检索投影。全范围摘要意味着即使无关的新指导/采购记录也会保守阻止回滚，这是当前实现的明确限制。原餐单因新事实被业务读接口判为 CHANGED 属正常保护，不应改写旧快照来掩盖变化。

## 7. 与 MySQL 手工 UPDATE 的对照

例如原材料关联中食材名夹带数量，单独 `UPDATE recipe_ingredient SET raw_name=...` 只能完成一个字段变更，无法证明审批、标准 ID、原文和旧事实仍符合条件，也无法在并发下知道这次 UPDATE 属于哪个批次。MySQL 同样可实现事务、行锁、唯一键和审计，但要同时设计这些机制，而不是依靠一条手工 SQL。

这里 PostgreSQL 的事务同时包住事实与审计；固定 Mapper SQL 用参数绑定，FOR UPDATE 锁定受控事实，SHARE 表锁保护历史，UUID 唯一键保护重放，JSONB 保存恢复证据。工具 rollback 是经业务前置校验的反向操作；它与 SQL ROLLBACK（撤销尚未提交的事务）是不同阶段的机制。

## 8. 面试问答

1. **为什么 dry-run 通过后还要检查？** 两次运行之间数据可能变化；只有 apply 自己事务内锁后的检查才能决定是否写入。
2. **为什么原文 hash 一致还不够？** 同一个原文下结构化字段或标准 ID 也可能已被改动；只验原文会覆盖他人修正。
3. **为什么审批不能填写 newFields？** 审批只能选择已签收事实提案和明确身份策略，不能变成任意数据库编辑入口。
4. **为什么批次审计必须与事实同事务？** 分开提交会出现事实已改但无法追溯/回滚，或审计成功但事实失败。
5. **如何证明幂等？** 同 UUID/hash返回原 result；不同内容拒绝；并发调用在事务锁与唯一键下只产生一个批次及同一映射。
6. **为什么不直接删重建菜谱？** 会破坏 recipe/source/document/旧材料 ID、收藏/历史引用和原文证据，且扩展了治理范围。
7. **为什么回滚不是简单恢复 before？** 若应用后有新事实或外部引用，恢复旧数据会覆盖用户修改或删除仍被使用的新身份；必须先核对 after 和依赖。
8. **JSONB 是否可以存所有关键字段？** 不可以；请求唯一性、候选键、状态、目标和索引关系使用关系列，JSONB只保存可变审计证据。
9. **名称修复后可直接匹配商品吗？** 不可以；商品采购依赖明确标准食材 ID，不能依据同名猜测等价。
10. **hash 能证明用户批准吗？** 不能。它只能检测内容变更；真实审批人身份和应用授权仍属于外部明确授权流程。
