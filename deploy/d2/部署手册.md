# D2 参数化部署准备手册

此包用于 D2-B 准备与复审。用户已确认 Ubuntu 22.04、2核/4GB、无域名、先用公网 IP 并允许公开注册；服务器实际架构、磁盘、防火墙和证书尚未核验。安装、上传、真实系统菜谱导出及上线仍需另批。模型与百炼 Key 默认关闭；D2-B1允许用户在部署env中显式开启厨房LLM/query，评测 HTTP、导入和document索引仍关闭，采购维持显式 Mock。入口限流不替代长期费用配额。IP证书、首次引导、续期、Ubuntu安装及镜像离线传输见 [IP部署与续期](IP部署与续期.md)。

## 文件与依赖

`compose.yaml` 组织 PostgreSQL、Spring Boot、Nginx；仅 Web 暴露 80/443。数据库使用 Compose 项目独立 `pg-data` 卷，PG18 挂载 `/var/lib/postgresql`。后端和 PG 位于内部网络；Web 另接入口网络以支持端口发布，后端另有出站网络，默认不配置模型 Key，显式启用流程见下文。证书只读挂载，日志每服务 10 MiB × 3 轮转。不要复用开发 Compose 项目名、容器、卷或端口。

`backend/Dockerfile` 与 `frontend/Dockerfile` 分别从白名单源码多阶段构建。后端运行 JRE21 并使用非 root 用户，前端由 Nginx 托管，`/api` 代理保持 URI，关闭代理缓冲并延长 SSE 读取超时。`postgres/Dockerfile` 基于 PG18 pgvector，加入 zhparser2.3 和 SCWS1.2.3。基础镜像必须核对官方来源并固定 digest；扩展源码归档必须核对发布来源及 SHA256，不能编造摘要。

官方来源：[Docker Official Images](https://github.com/docker-library/official-images)、[pgvector](https://github.com/pgvector/pgvector)、[zhparser](https://github.com/amutu/zhparser)、[SCWS](https://github.com/hightman/scws)。镜像锁例文件所有值为空，故直接使用会拒绝构建。不同 Linux 平台需选择一致架构；运行镜像可采用受控仓库 RepoDigest，或离线 save/load 后核对的本地 sha256 image ID；两者不可混称。构建基础镜像仍固定官方仓库 digest。

## 本机白名单装配

在 5b09 工作树执行（以下命令只装配，无 Git 整合）：

```powershell
python deploy/d2/scripts/assemble.py --backend C:/Users/Omelet/.codex/worktrees/5b09/Cooker --frontend C:/Users/Omelet/.codex/worktrees/0f47/Cooker --output .data/d2-release
```

输出必须不存在或为空且不得为链接。脚本锁定后端 5b09 和前端 0f47，拒绝错误来源和关键文件缺失。仅复制 main 源码、固定配置、迁移、前端源码与构建配置及部署工具；不读取真实 `.env`、`.data`、账本、备份、node_modules 或 Maven 缓存。`release-manifest.json` 记录来源和完整发布文件清单，不代表 Git 干净或生产签收。

装配后将核验过的 `scws-1.2.3.tar.bz2`、`zhparser-2.3.tar.gz` 放入发布包 `deploy/vendor/`。在发布包外复制并填写 `images.lock.example.json`：MAVEN_IMAGE、JRE_IMAGE、NODE_IMAGE、NGINX_IMAGE、PGVECTOR_IMAGE 都为对应批准仓库 `tag@sha256:...`；另填写 SCWS_SHA256/ZHPARSER_SHA256。例如选定 JDK21 Maven/JRE、Node24、Nginx 稳定版及 PG18 基础镜像后，先查看并核对 registry manifest，再填写实际摘要。

```powershell
python .data/d2-release/deploy/scripts/build.py --release .data/d2-release --lock <显式镜像锁文件> --component backend --tag cooker-d2-backend:<发布版本>
python .data/d2-release/deploy/scripts/build.py --release .data/d2-release --lock <显式镜像锁文件> --component frontend --tag cooker-d2-web:<发布版本>
python .data/d2-release/deploy/scripts/build.py --release .data/d2-release --lock <显式镜像锁文件> --component postgres --tag cooker-d2-postgres:<发布版本>
```

这些命令只构建、不启动。网络不可用时保持未验证状态，不换不可信镜像，不安装额外软件或改变网络。生产依赖下载应使用可信 HTTPS；首次构建需依赖仓库网络，不能假设本机缓存随包复制。

## 参数与 HTTPS

获部署授权后在服务器包外安全创建显式 env 文件，参考 `.env.example`。必需：独立 RELEASE_PROJECT、三个发布镜像 RepoDigest 或本地 image ID、DB名/角色/强密码、至少32字符 JWT 秘密、Base64 编码32字节加密主密钥、DOMAIN（规范公网IP或域名）、匹配的 PUBLIC_ORIGIN、绝对 TLS_DIRECTORY 和 ACME_WEBROOT。示例不含可用秘密。env 格式为未加引号的 `KEY=value`，不要使用变量展开或换行值；秘密建议采用足够长度的随机十六进制及 Base64。主密钥必须安全保管，丢失后不能解密用户凭证。数据库角色可用于初始化迁移，不应向公网暴露数据库。

Nginx 读取 TLS_DIRECTORY/current 下的 fullchain.pem、privkey.pem，整个证书根目录只读挂载。current 由受控证书工具原子切换；私钥权限 0600。公网 IP 用 IP SAN 验证，IPv6 的 PUBLIC_ORIGIN 带方括号，未来域名用 DNS SAN。首次无证书只启动独立 HTTP-01 引导组件，其他业务路径返回503；生产可信证书验证后再开放HTTPS。具体步骤见 IP部署与续期.md。本轮不申请证书、不创建 ACME 账户。

```bash
python3 deploy/scripts/render.py --compose deploy/compose.yaml --env-file /安全绝对路径/production.env
```

只执行 `config --quiet`；不要将完整渲染输出写到日志，因为其中含秘密。脚本先验证 env 值，缺少秘密、摘要或非法入口地址或源不一致立即失败。模型开关和百炼Key由显式env注入，缺项默认false/空；true必须通过非占位Key形状校验。评测、导入、document索引固定关闭，启动不重建向量。静默校验不验证供应商Key真实性。

## 系统菜谱白名单迁移（另批后才能执行）

先使用当前后端 Flyway 创建 V1～V15 空目标库；只迁移结构，不复制源 `flyway_schema_history`。可在后续批准部署时仅启动独立 PostgreSQL 和后端完成迁移，停止目标后端再恢复。任何已有业务表非空都会拒绝恢复，禁止为绕过保护自动清库。源也须为当前 V15。不得连接宿主业务库；工具必须显式指定容器/数据库/角色并重复确认库名。

```bash
# 以下是后续授权操作模板，本轮未对真实库执行
python3 deploy/scripts/recipes.py export --container <批准源容器> --database <批准源库> --role <批准角色> --confirm-database <批准源库> --file /安全路径/system-recipes.json
python3 deploy/scripts/recipes.py check --container <批准目标容器> --database <批准目标库> --role <批准角色> --confirm-database <批准目标库> --file /安全路径/system-recipes.json
python3 deploy/scripts/recipes.py restore --container <批准目标容器> --database <批准目标库> --role <批准角色> --confirm-database <批准目标库> --file /安全路径/system-recipes.json
```

源导出使用只读 repeatable-read 快照。11张白名单表保留系统原始 Markdown、结构化事实、投影与已有1024维向量及原ID。必要 import_batch 元数据保留，诊断正文和 source_uri 清空，source_key 必须为相对路径。金额/数量转文本避免 JSON 浮点损失；`null`/未知保持原样。历史系统文档也保留以满足外键。12个已审定食材ID及名称必须完全一致，迁移不重新推断食材或数量。用户、凭证、Token、收藏、档案、历史、聊天、餐单、指导、采购及修复审计表不导出。

恢复在单事务内锁表确认全部业务表为空；按外键顺序写入，保留约束，错误整体回滚。identity 使用事务化 ALTER SEQUENCE RESTART 到最大ID+1；全文 `tsv` 不直接恢复，由当前 zhparser 配置重算。向量只允许 text-embedding-v4/1024/template1，不调用模型。JSON重复字段、额外表/列、私有记录、缺绑定、READY无向量或非有限向量会拒绝。包限制256MiB，超过后应独立设计分批协议，不改保护直接执行。

## 后续部署与回滚边界

以下只供实际部署另批后实施：核对服务器版本/资源、镜像摘要、公网IP或域名、证书和访问策略；安全传输发布包及另批导出；渲染检查；创建独立目标卷并执行 Flyway；恢复并核对三层行数/IDs/FKs/生成列/序列/12绑定及私有表空；再开放 Web，执行 HTTPS/Cookie/CSRF/SSE/权限/Mock 冒烟。用户2026-10-10已允许本次演示启用厨房模型并自愿承担调用费用；按下节显式配置。该允许不代表本轮已启动服务或产生模型请求。

回滚先关闭入口，在数据库兼容范围内切回先前镜像 digest。结构或数据不兼容时用部署前经授权备份恢复至独立新卷，禁止自动 down -v 或删除原卷。生产备份含用户资料后须制定访问、加密、保留、演练策略。本任务未实际上传、启停、导出或部署。

## 自检

- 所有镜像和扩展来源/摘要实际核验；首次完整 Linux 镜像构建通过。
- 必需参数无默认秘密；配置校验输出不泄露秘密。
- PG及后端无公网端口，证书只读，Cookie安全标记与同域代理一致。
- 默认模型关闭；显式厨房启用已获本次演示允许，评测/导入/document索引仍关闭，Mock身份明确；累计费用缺口如实告知。
- 当前迁移空库、外键、序列、生成全文、向量和私有表空有真实隔离证据。
- 迁移工具通过不等于真实菜谱质量、线上可用性或生产签收。


D2-A 的镜像构建与隔离 PG/HTTP 证据保持为历史验证；D2-B 仅追加工具和隔离 Nginx 专项，资源值未经目标服务器压测。

## D2-B1：显式启用厨房LLM/query（2026-10-10）

用户已允许厨房模型调用并自愿承担费用，覆盖D2-B中“累计配额缺口必须保持禁用”的演示前置。长期累计配额尚未实现；公共百炼Key可被多个用户query请求消耗，Nginx限流不是供应商费用硬上限。本轮仅配置准备，以下实际操作由用户在部署时执行，未替用户执行。

在发布包外的受限服务器env文件中设置 `COOKER_AGENT_EXECUTION_ENABLED=true`，另填写 `DASHSCOPE_API_KEY` 的真实百炼Key（此处不提供可用示例）。仅接受小写true/false；启用时拒绝缺Key、非sk-形状、明显占位及单字符重复值。校验只是形状，不证明供应商授权/余额/地域有效。关闭用false并清空该Key。真实env权限0600，不提交、不输出、不写镜像，不把Key粘入聊天或命令参数。

DeepSeek仍固定官方地址 https://api.deepseek.com 与模型deepseek-flash；每位用户登录网页后在模型设置中保存自己的官方Key，服务端沿用账户AES-GCM加密。没有共享服务端DeepSeek Key。只启用LLM/query，不激活recipe-index/recipe-import或evaluation，不恢复GLOBAL_STOP账本，不自动生成document向量。

```bash
# 模板：发布路径、项目及env须与批准部署一致。本轮未执行。
cd /srv/cooker/release
# 避免当前shell的同名变量优先于--env-file；不要打印环境内容。
unset COOKER_AGENT_EXECUTION_ENABLED DASHSCOPE_API_KEY
python3 deploy/scripts/render.py --compose deploy/compose.yaml --env-file /etc/cooker/production.env
# 已部署时先停新增厨房流量并核对在途请求终态，再受控重新创建后端。
# 不仅restart：restart不会更新旧容器环境；此命令不重新创建PG/Web。
docker compose --env-file /etc/cooker/production.env -p <批准项目名> -f deploy/compose.yaml up -d --no-deps --force-recreate backend
```

紧急禁用：先停新增厨房流量，核对在途LLM/query与后台作业，不擅自取消；将受限env开关改false并清空百炼Key，重新静默校验，受控重新创建同一backend。仍在执行的供应商请求不保证立即取消或停止计费。不要down -v、重建数据库、删除用户凭证或替换LLM主密钥。恢复使用同一经批准配置流程；配置启用与真实业务/供应商验收分别记录。
